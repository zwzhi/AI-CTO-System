# AI 能力持续评估标准

## 1. 目的与适用范围

本标准规定 AI 项目进入运营后如何持续评估能力变化、保存历史基线并识别退化或演进机会。它扩展 Phase 6 的 [AI 评测标准](../testing/AI_EVALUATION_STANDARD.md)，不替代功能、安全、数据和用户验收。

任何依赖模型、Prompt、检索、工具调用、Agent 编排或 AI 输出的项目都适用。非 AI 项目必须记录经批准的 N/A 及复核触发器。

## 2. 评估基线

每次评估建立唯一 `AI-CAP-XXXX`，冻结：代码 Commit、Release、模型与参数、Prompt / System Instruction、工具与权限、检索 / 索引、数据集、环境、依赖、流量分组、时间窗口、成本口径和评测方法。

不同基线、用户群、数据集或统计口径的结果不得直接宣称改善或退化。无法保持可比性时，必须同时报告旧口径、新口径和桥接验证。

## 3. 七个持续评估维度

| 维度 | 必须回答 | 典型指标 |
|---|---|---|
| 输出质量 | 输出是否有用、完整、清晰并符合任务要求 | 评分量表、偏好胜率、任务完成质量 |
| 准确率 | 事实、分类、提取或决策是否正确 | Accuracy、Precision / Recall、事实核验率 |
| 稳定性 | 重复运行、输入扰动和环境变化下是否一致可靠 | 方差、失败率、漂移、重试成功率 |
| Agent 成功率 | 端到端 Agent 或 AI 工作流是否完成目标 | Success Rate、步骤失败、人工接管率、工具错误率 |
| Prompt 效果 | Prompt / 输入模板是否提升目标且没有破坏其他能力 | 相对基线提升、回归项、指令遵循率 |
| Token 成本 | 每个有效任务的 Token 与费用是否可控 | Input / Output Token、Cost per Success、预算偏差 |
| 响应时间 | 用户可感知和端到端延迟是否满足目标 | P50 / P95 / P99、首 Token、任务完成时间 |

幻觉、安全、隐私、越权和有害输出继续作为强制红线，按 Phase 6 AI Evaluation 与 Security Review 管理，不能因七维平均结果良好而忽略。

## 4. 评估频率与触发器

项目必须定义固定周期和事件触发评估。以下情况必须重新评估受影响维度：

- 模型、参数、Prompt、工具、权限、检索、数据集、代码或依赖变化；
- 重大 Release、Incident、用户投诉或人工接管率变化；
- 数据分布、用户群、语言、区域或业务规则变化；
- Token 成本、响应时间、成功率或质量越过预警 / 失败阈值；
- 供应商版本、价格、配额、服务条款或安全状态变化。

不得只在效果变差时评估，也不得看到结果后修改阈值。阈值、统计口径、样本量和停止规则必须在运行前冻结。

## 5. 历史记录

每次能力变化必须追加到 AI Capability History，不覆盖旧记录。每条历史至少包含：Record ID、父基线、候选基线、七维结果、红线结果、数据集和时间窗、统计方法、Confidence、Evidence、变化原因、批准人、Rollout、回滚和实际线上结果。

历史记录必须能回答：何时变化、改了什么、为什么改、相对哪个基线、改善了什么、退化了什么、成本如何、谁批准、是否回滚以及长期效果是否保持。

## 6. 趋势与判定

结果使用 `IMPROVED`、`UNCHANGED`、`DEGRADED`、`INCONCLUSIVE`，并同时报告效应大小、置信区间或等价不确定性。单次波动、平均值或离线提升不能自动证明长期线上改善。

- 红线触发、核心质量显著下降或生产用户受损：创建 Incident / Bug，先控制影响。
- 单一、边界明确且可逆的问题：进入 Maintenance Task。
- 持续退化、跨模块瓶颈、模型路线变化或多维能力不足：创建 Evolution Proposal。
- Evidence 不足：保持 `INCONCLUSIVE`，补充数据或缩小结论，不直接升级。

## 7. 候选能力比较与上线

候选模型、Prompt 或 Agent 方案必须与当前生产基线在相同评测合同下比较，报告质量、准确、稳定、成功率、成本和时延的权衡。任何模型或 Prompt 替换都属于行为基线变化，必须执行适用 Design、Development、Testing、AI Evaluation、Security 和 Release Gate。

Evolution Proposal 或用户审批只批准演进方向，不替代实现与上线授权。线上灰度、监控、停止条件和回滚必须在执行前定义。

## 8. 记忆与知识沉淀

每个评估周期更新 `PROJECT_STATE.md`、`PROJECT_MEMORY.md` 和相关 Progress。评测方法、Prompt 模式、失败案例和优化经验必须先按 Knowledge Governance 以 `CAPTURED` 状态进入权威 `knowledge_base/`；只有完成验证、脱敏并保留适用范围后才能成为 `ACTIVE` Knowledge。
