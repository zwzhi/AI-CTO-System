# 项目文档恢复规范

## 1. 目的

当已有项目缺少、过期或相互冲突的文档时，AI CTO 必须从代码、Git、配置、数据库和接口证据恢复当前可验证事实，并明确区分历史事实、当前实现、推断和未知。

文档恢复不是创作理想设计，也不是补写看似完整的项目历史。恢复结果首先描述“系统现在是什么”，再由用户决定“未来应该是什么”。

## 2. 证据来源与边界

| 来源 | 可支持的结论 | 不能单独证明的内容 |
|---|---|---|
| 代码 | 实现模块、接口、分支逻辑、错误处理和依赖调用 | 原始产品意图、线上启用状态、历史决策原因 |
| Git 记录 | Commit、作者记录、时间、变更和可见演变 | 未提交历史、口头决策、Commit Message 未陈述的动机 |
| 配置 | 环境键、Feature Flag、构建、部署和外部连接定义 | 秘密值、实际生产值、配置一定已生效 |
| 数据库 | 当前 Schema、约束、索引、Migration 和数据访问方式 | 未保留的历史 Schema、业务语义和数据合法来源 |
| 接口 | API / Event / File 契约、调用方和返回行为 | 所有消费者、真实流量、未记录的兼容承诺 |
| 测试与运行证据 | 被验证行为、环境、结果、故障和指标 | 未覆盖路径、长期稳定性和其他版本表现 |
| 维护者确认 | 责任人记忆、业务语境和当前选择 | 未经证据支持的技术事实或第三方历史 |

凭据、生产数据和敏感日志只保存安全引用，不复制到恢复文档。

## 3. 真值标签与 Confidence

每项恢复结论必须使用一个真值标签：

- `OBSERVED`：从当前版本或可复核记录直接观察；
- `INFERRED`：由多个事实推导，仍需验证；
- `USER_CONFIRMED`：有权限的维护者确认其选择、语义或风险接受；
- `CONFLICTED`：来源互相冲突，尚未解决；
- `UNKNOWN`：没有足够证据。

同时按 [Confidence 模型](../evaluation/CONFIDENCE_MODEL.md)标记 L1–L4，并绑定 Evidence ID、版本 / Commit、环境、验证日期、适用边界和复核触发器。用户确认只能证明用户作出了确认，不能把未经验证的代码或运行事实自动提升到 L3。

## 4. 恢复流程

1. 冻结 Original Source、Commit / Snapshot、Git 状态、环境和现有文档清单。
2. 建立 Evidence Register，给代码、Git、配置、数据库、接口、测试和用户确认分配稳定 ID。
3. 对现有文档执行 `CURRENT`、`STALE`、`CONFLICTED`、`MISSING` 分类，不静默覆盖。
4. 从权威证据恢复当前 PRD、Architecture、Database Design、ADR 和 PROJECT_MEMORY。
5. 为每项关键结论标记真值、Confidence、冲突、未知和补证动作。
6. 由代码、数据、产品、运维或安全责任人按领域复核。
7. 将通过复核的内容从 `RECOVERED_DRAFT` 更新为 `VERIFIED_CURRENT`；历史仍未知的字段继续保留 `UNKNOWN`。

## 5. PRD 恢复规则

恢复 PRD 至少覆盖实际用户角色、当前场景、已有功能、核心流程、范围、限制、可观察成功指标和验收现状。

- 代码和界面可以证明功能存在，但不能证明它仍有用户价值。
- Analytics、工单、运行指标或用户确认可以支持实际使用结论，但必须绑定时间窗口。
- 无法确认原始需求时，写“当前实现行为”和 `UNKNOWN` 的历史意图，不得反向编造产品背景。
- Requirement ID 是接管时新建的追踪标识，不伪装成历史项目原有编号。

## 6. Architecture 恢复规则

从入口、模块依赖、调用、数据流、网络、部署配置、队列、存储和外部服务恢复：

- 系统边界、模块划分、服务关系和部署拓扑；
- 核心成功路径、失败传播、权限边界和可观测性；
- 当前技术选型及其可见约束；
- 与现有架构图或说明的差异。

静态依赖只能证明潜在关系；运行流量、Tracing 或等价实测才能证明实际运行关系。无法运行时明确降低 Confidence。

## 7. Database Design 恢复规则

从 Schema、Migration、ORM、查询、备份和实际环境元数据恢复：

- 实体、字段、类型、约束、关系、索引和所有权；
- 数据生命周期、敏感等级、访问、审计、备份与恢复；
- 应用模型与数据库实际 Schema 的差异；
- Migration 已应用状态、缺口、不可逆变化和漂移风险。

缺少 Migration 历史时不得根据当前 Schema 伪造历史脚本。记录当前基线、已知缺口和未来基线化方案；任何生产迁移修复必须另走 Change Impact、设计与发布门禁。

## 8. ADR 恢复规则

恢复 ADR 只记录可证明的决定或当前需要重新确认的决定：

- 重建日期使用当前恢复日期，不回填未知原始日期；
- 原决策者、替代方案或理由无法证明时写 `UNKNOWN`；
- 未经维护者确认的历史推断使用 `Proposed`，并标记“Retrospective Reconstruction”；
- 当前责任人确认后，可以记录当前 `Accepted` 决定，但不得声称它证明了过去的原始理由；
- 技术选择变化继续新建 ADR，不覆盖恢复记录。

## 9. PROJECT_MEMORY 恢复规则

PROJECT_MEMORY 只保存对未来工作有用的摘要和源链接，包括：

- 当前可证实目标与运行状态；
- 技术选择及其版本；
- 已确认决策和 `UNKNOWN` 历史；
- 重要修改、故障、风险和恢复记录；
- 当前状态、限制、下一动作和复核触发器。

详细代码、扫描日志、敏感信息和未验证长篇推断保留在源文档或受控 Evidence 中，不复制进记忆。

## 10. 冲突与未知处理

证据冲突时保留全部来源，比较直接性、版本、环境、时间和可复现性。冲突解除前标记 `CONFLICTED`，采用能被共同证据支持的最低 Confidence，并阻止依赖该结论的高风险决定。

以下行为视为伪造历史并禁止：

- 把首次 Commit 时间写成项目创建时间而不加限定；
- 从当前技术选型编造当初选择理由；
- 把未运行的代码写成已上线功能；
- 把 Schema 反推成不存在的 Migration 历史；
- 为未知决策补写决策者、日期或会议结论；
- 为了提高完整度而隐藏 `UNKNOWN`、冲突或失败证据。

## 11. 恢复输出与验收

每份恢复文档必须包含 Recovery Record ID、Source Baseline、文档状态、Evidence Register、关键结论表、总体 Confidence、短板、冲突、未知、领域评审和最后复核日期。

恢复完成表示当前可验证事实已被忠实记录，不表示历史已经完整。关键结论仍为 L1、存在未解决冲突或缺少安全 / 数据边界时，迁移门禁必须为 `ONBOARDING_BLOCKED`。
