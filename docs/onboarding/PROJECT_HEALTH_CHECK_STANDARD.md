# 项目健康检查标准

## 1. 目的

AI CTO 接管已有项目后，必须以可复核证据评估代码、文档、测试、架构、技术债、安全、维护与扩展能力，并输出 100 分制健康评分。

健康评分描述当前项目状态，不评价团队或个人，也不单独授权重构、迁移、停止或发布。评分、Confidence、风险红线和迁移门禁必须分别报告。

## 2. 评估基线

健康报告必须绑定唯一 `HEALTH-XXXX`、Original Source、Branch、Commit / Snapshot、工作区状态、文档版本、环境、扫描时间、评估人和 Evidence Register。使用“当前版本”“最新版”或混合不同 Commit 的证据不能形成最终评分。

每项结论标记 L1–L4 Confidence。总体 Confidence 取决定健康等级与建议的关键结论中的最低等级，不得对等级求平均。

## 3. 权重与公式

| 维度 | 权重 | 核心检查 |
|---|---:|---|
| 代码质量 | 15 | 结构、可读性、复杂度、重复、错误处理、静态检查和 Review 能力 |
| 文档完整度 | 10 | 目标、架构、数据、接口、部署、运维、决策和更新状态 |
| 测试覆盖 | 15 | 测试层级、关键路径、失败路径、可重复执行、结果与 Evidence |
| 架构合理性 | 15 | 边界、耦合、数据流、依赖、故障隔离、部署和需求适配 |
| 技术债情况 | 10 | 债务清单、影响、增长趋势、Owner、处置与遗留版本风险 |
| 安全状态 | 15 | 密钥、权限、用户数据、依赖、存储、日志、漏洞与事件响应 |
| 可维护性 | 10 | 构建、调试、部署、监控、人员依赖、运行手册和变更成本 |
| 扩展能力 | 10 | 容量、性能、模块扩展、数据演进、兼容、供应商与退出能力 |
| **合计** | **100** | 八维全部评估 |

每个维度先评 0–5 分，再按以下公式折算：

`维度得分 = 维度权重 × 原始评分 ÷ 5`

`Health Score = 八个维度得分之和`

最终分数保留一位小数；等级区间按原始数值判断，不四舍五入跨级。

## 4. 通用原始评分标尺

| 原始评分 | 含义 | 最低判定要求 |
|---:|---|---|
| 5 | 健康且可持续 | 控制完整、自动或稳定执行，有当前项目证据和历史验证 |
| 4 | 良好 | 主要控制有效，仅有有限且有 Owner 的非关键缺口 |
| 3 | 可接受 | 核心工作可维护，但存在明确技术债、手工步骤或覆盖短板 |
| 2 | 薄弱 | 多项重要缺口，维护风险高，需要有计划优化 |
| 1 | 严重 | 核心能力不可证明或频繁失效，依赖高风险人工经验 |
| 0 | 不可接受 | 已发生或极可能发生严重故障、安全 / 数据风险，缺少可信控制 |

4 分和 2 分必须满足相邻等级之间的明确证据，不能仅凭主观印象插值。

## 5. 八维评分标准

| 维度 | 5 分示例 | 3 分示例 | 1 分示例 | 0 分条件 |
|---|---|---|---|---|
| 代码质量 | 模块清晰、复杂度受控、重复低、检查与 Review 稳定 | 核心可读但局部复杂、重复或风格不一致 | 核心逻辑高度耦合、难以定位和安全修改 | 代码无法构建 / 解析或存在已知灾难性错误且无控制 |
| 文档完整度 | PRD、架构、数据、接口、运维和 ADR 与当前基线一致 | 关键文档存在但部分过期或缺少追踪 | 只能依靠口头知识，核心目标和运行方式不明 | 文档误导且会直接造成高风险操作 |
| 测试覆盖 | 多层测试覆盖核心、失败、回归并可重复生成 Evidence | 有自动测试但关键非功能或失败路径不足 | 测试无法稳定运行或只覆盖少量 Happy Path | 无可信测试且变更会造成不可控生产 / 数据风险 |
| 架构合理性 | 边界清晰、数据流可追踪、故障隔离和部署适配目标 | 架构可运行但耦合、单点或边界债务明显 | 模块关系不清、共享状态和隐式依赖广泛 | 架构导致不可恢复数据 / 安全风险或系统无法稳定运行 |
| 技术债情况 | 债务已登记、量化、排序并持续偿还 | 债务已知且有部分计划，但增长或遗留依赖明显 | 债务未知或长期累积，升级和修改成本失控 | 债务已阻断安全维护且没有可行恢复路径 |
| 安全状态 | 六类安全控制有当前审核、测试和响应证据 | 基础控制存在，非关键缺口有计划和监控 | 权限、依赖、日志或数据保护存在高风险缺口 | 有效密钥 / 数据泄露、可利用越权或适用红线未遏制 |
| 可维护性 | 构建、调试、部署、监控和 Runbook 可由多名维护者复现 | 维护可完成但依赖手工步骤或少数关键人员 | 构建 / 部署不可复现，知识集中且无交接 | 无法安全恢复、部署或定位核心故障 |
| 扩展能力 | 容量、性能、接口兼容和数据演进有验证与退出方案 | 可满足当前规模，但扩展需局部重构或手工扩容 | 核心单点、供应商锁定或数据模型限制明显 | 现有结构无法满足已确认需求且迁移 / 隔离不可行 |

## 6. 证据覆盖与未评估项

没有证据的维度标记 `UNASSESSED`，不得主观赋分。此时必须同时输出：

- 已评估维度的小计；
- 未评估权重；
- Health Score 区间：已评估小计至“已评估小计 + 未评估权重”；
- Provisional 标记、总体 Confidence 和最小补证动作。

只有八维全部有可复核证据，且代码、测试、架构和安全关键结论达到当前风险所需 Confidence 时，才能发布 Final Health Score 与等级。Evidence Coverage 为：

`已有有效证据的维度权重 ÷ 100 × 100%`

## 7. 健康等级

| Health Score | 等级 | 默认建议 |
|---:|---|---|
| 90–100 | 健康 | 继续维护，保持监控与周期复核 |
| 70–89.9 | 可维护 | 可纳管维护，按优先级关闭明确缺口 |
| 50–69.9 | 需要优化 | 建立限期优化或局部重构计划，控制新增债务 |
| 0–49.9 | 建议重构 | 评估重构、迁移、隔离或停止；未通过门禁前不得直接实施 |

分数不抵消安全、隐私、合规、数据完整性、许可证、不可恢复故障或来源不明代码等红线。即使总分达到 90，存在未关闭红线仍必须 `ONBOARDING_BLOCKED`。

## 8. 健康报告必填内容

健康报告至少记录：

| 字段 | 要求 |
|---|---|
| Health Report ID / Baseline | 唯一 ID、Source、Commit / Snapshot、Git 状态、环境和时间 |
| 八维评分 | 原始分、权重、折算分、证据、Confidence、问题和 Owner |
| Health Score | Final 或 Provisional、分数 / 区间、等级和 Evidence Coverage |
| 关键风险 | 风险 ID、影响、概率、红线、缓解、Owner 和复核触发器 |
| Recommendation | 继续维护、重构、迁移或停止，以及适用条件和替代方案 |
| Decision Boundary | 当前结论能支持和不能支持的决定 |
| Next Actions | 顺序、Owner、完成条件和目标门禁 |

## 9. 评分复核

发生代码、依赖、配置、Schema、部署、测试、安全事件、维护团队或运行规模变化时，相关维度旧证据失效并重新评分。不得覆盖旧报告；新报告引用上一版本并说明变化。

评分人必须核对分母、权重、证据版本、Confidence、红线和未评估项。自动化扫描可以提供证据，不能独立给出最终健康结论。
