# Deployment & Rollback Standard

## 1. 目的与边界

本标准规定软件版本从获得发布授权到完成部署、验证或回滚时必须执行和记录的控制。它与 [Release Approval Gate](./RELEASE_APPROVAL_GATE.md)、[Testing Release Gate](./TESTING_RELEASE_GATE.md)、[Monitoring Standard](./MONITORING_STANDARD.md) 和 [Release Report 模板](../../templates/RELEASE_REPORT_TEMPLATE.md) 配套使用。

`READY_FOR_RELEASE` 只授权当前精确基线进入 RELEASE，不表示部署已经执行或成功。没有有效发布授权时，不得对目标环境执行生产部署、数据库迁移或不可逆配置修改。

## 2. 核心原则

1. 每次部署都必须绑定不可变版本、Artifact、Commit、配置和文档基线。
2. 部署步骤、验证步骤和回滚步骤在发布授权前完成评审，不得在故障现场临时设计。
3. 配置、数据库和依赖变化必须显式列出；“与上次相同”必须引用可核验基线。
4. 数据保护优先于恢复速度。不能安全回滚的数据变化必须提供前滚、兼容窗口和人工处置方案。
5. 部署与回滚均以证据判定，不以“命令执行完”“服务已启动”或口头确认判定成功。
6. 凭据、密钥、令牌和敏感配置只记录引用与版本，不得写入发布文档、日志或 Git。

## 3. 角色与责任

| 角色 | 责任 |
|---|---|
| Release Owner | 冻结授权范围、版本与时间窗，作出继续、暂停或回滚决定 |
| Deployment Owner | 按获批步骤执行部署，记录每一步结果与证据 |
| Rollback Owner | 核验回滚触发器、执行恢复并验证回滚结果 |
| Test Owner | 执行部署前、部署后和回滚后验证 |
| Data Owner | 审核数据库变化、备份、恢复、数据一致性和不可逆风险 |
| Security Owner | 核对凭据、权限、配置、依赖与敏感日志控制 |
| Monitoring Owner | 确认监控、告警、观察窗口和升级链就绪 |
| 用户 / 业务责任人 | 确认业务窗口、可见影响、停机边界和验收责任 |

高风险部署不得由同一人同时完成实施、验证和最终放行。自动化可以执行步骤和收集证据，不能代替有权限责任人的发布或回滚决定。

## 4. 部署记录必填字段

每次发布必须创建唯一 `DEPLOY-XXXX` 记录，至少包含：

| 字段 | 最低要求 |
|---|---|
| 项目与 Release ID | 项目名称、Release ID、Release Gate Record ID |
| 部署环境 | 环境名称、区域 / 租户、用途、访问边界和环境 Owner |
| 版本号 | 唯一版本号、Artifact ID / 哈希、Git Commit SHA 和构建来源 |
| 配置变化 | 配置键或配置集、旧版本、新版本、作用域、敏感级别、兼容和恢复方式；不得记录秘密值 |
| 数据库变化 | Migration ID、Schema / 数据变化、兼容窗口、备份、验证、前滚与回滚策略，或可审计 N/A |
| 依赖变化 | 直接 / 外部依赖、旧版本、新版本、兼容性、安全、许可和失败影响，或可审计 N/A |
| 部署策略 | 全量、滚动、蓝绿、金丝雀或其他获批方式，以及选择依据 |
| 时间与窗口 | 计划开始、停止决策点、最晚回滚点、业务冻结和沟通窗口 |
| 责任与批准 | Release / Deployment / Rollback / Test / Data / Monitoring Owner 及批准记录 |
| 验证与监控 | Smoke / Health / 业务检查、指标阈值、观察窗口和证据位置 |
| 回滚基线 | 上一个稳定版本、配置、数据库与依赖基线的不可变引用 |

数据库、配置或依赖确实未变化时，可以使用 Approved N/A；N/A 必须记录当前 Diff、核验方法、评审人和基线变化触发器。

## 5. 部署前就绪条件

部署开始前必须同时满足：

- 当前精确版本取得有效 `READY_FOR_RELEASE`，且授权未因新 Commit、配置、依赖、数据或测试变化失效。
- 部署环境、Artifact、版本、配置、数据库、依赖和 Feature Flag 基线已冻结。
- 部署步骤、暂停点、停止条件、回滚触发器和责任人已评审。
- 所需备份、快照、恢复凭据、容量、权限和外部服务窗口已验证可用。
- Monitoring Standard 要求的仪表盘、日志、告警、Owner、Runbook 和观察窗口已就绪。
- 发布沟通、用户影响、维护窗口和必要审批已完成。
- 目标环境不存在未解释漂移、正在进行的冲突变更或未关闭高优先级事件。

任一条件不满足时，部署状态为 `BLOCKED`，不得以发布窗口、人员在线或已生成 Artifact 为理由开始。

## 6. 部署计划与执行

### 6.1 计划结构

部署计划必须按顺序列出：

1. 前置检查与环境冻结。
2. 备份、快照或恢复点创建及验证。
3. Artifact、配置、数据库和依赖变更步骤。
4. 每一步的执行人、预期结果、验证方法、超时和停止条件。
5. 流量切换、灰度比例、Feature Flag 或兼容窗口操作。
6. 部署后 Smoke、健康、关键用户旅程和数据一致性验证。
7. 观察窗口、扩大流量条件、回滚决策点和最终确认。

步骤必须可逐项勾验。不得使用“正常部署”“检查系统”“必要时处理”等不可执行表述。

### 6.2 执行状态

部署状态只允许：

| 状态 | 定义 |
|---|---|
| `PLANNED` | 计划存在但尚未满足全部就绪条件 |
| `READY` | 获得当前发布授权且全部部署前检查通过 |
| `IN_PROGRESS` | 正在按记录步骤执行 |
| `SUCCEEDED` | 部署步骤、验证与规定观察窗口均满足成功条件 |
| `FAILED` | 部署或验证不满足成功条件，必须暂停并决定回滚或隔离 |
| `ROLLED_BACK` | 已恢复到获批基线且回滚后验证通过 |
| `BLOCKED` | 无法安全开始或继续，等待明确解除条件 |

执行中每一步记录开始 / 结束时间、执行人、输入版本、实际结果、证据、偏差和决定。发生未计划偏差时立即暂停，创建事件或 Change 记录；不得在未评审情况下扩大变更范围。

## 7. 部署成功判定

只有以下条件全部满足，部署才可标记 `SUCCEEDED`：

- 实际环境、版本、配置、数据库和依赖与授权基线一致。
- 部署步骤无未解释失败或跳过项。
- Smoke、健康检查、关键用户旅程、权限和数据一致性验证 PASS。
- 系统状态、错误、性能和 AI 质量指标在规定观察窗口内满足阈值。
- 没有新触发的 P0 / P1 Bug、安全红线、数据损坏或回滚触发器。
- Release Report、PROJECT_STATE 和 PROJECT_MEMORY 已更新实际结果与下一动作。

部署步骤完成但观察窗口未结束时，状态保持 `IN_PROGRESS`，不得提前声明成功。

## 8. 回滚方案必填内容

每次发布都必须定义可执行回滚方案，至少包含：

| 字段 | 最低要求 |
|---|---|
| 触发条件 | 可观测信号、阈值、持续窗口、触发后允许的判断时间和决策人 |
| 回滚步骤 | 按顺序列出流量、应用、配置、数据库、依赖与缓存恢复动作 |
| 数据恢复方案 | 恢复点、备份位置引用、RPO / RTO、回填 / 补偿、冲突与重复数据处置 |
| 验证方式 | 回滚后版本、配置、Schema、数据、功能、权限、安全、指标和用户旅程检查 |
| 责任与沟通 | Rollback Owner、执行人、验证人、通知对象、升级路径和状态更新位置 |
| 最晚决策点 | 超过该点后回滚是否仍安全；不安全时采用的前滚或隔离方案 |

“恢复上一版本”“必要时回滚”或只提供工具命令，均不构成可执行回滚方案。

## 9. 回滚触发条件

以下任一情况满足预设阈值时必须暂停扩大部署并由 Release Owner 作出回滚或隔离决定：

- 系统不可用、核心功能异常或新出现 P0 / P1 Bug。
- 安全、隐私、权限、秘密或合规控制失效。
- 数据损坏、丢失、重复、不可接受漂移或迁移验证失败。
- 错误率、延迟、资源、容量或可用性越过发布阈值。
- AI 输出质量、准确率、幻觉风险、Agent 成功率或成本出现不可接受退化。
- 关键外部依赖失败且降级方案无效。
- 部署步骤偏离获批计划，当前状态不可证明安全。

CRITICAL 信号要求立即隔离或回滚；不得等待观察窗口结束。尚未达到自动触发阈值但风险持续上升时，记录事实、趋势、Owner 和下一决策点。

## 10. 数据库与不可逆变化

- 数据迁移优先采用向后兼容、可分阶段验证的 Expand / Migrate / Contract 或等价策略。
- 破坏性 Schema 变化、不可逆转换或批量删除必须有独立备份验证、停止阈值和 Data Owner 批准。
- 应用回滚后数据库不兼容时，不得声称“可回滚”；必须提供兼容版本、前滚修复、双写 / 读兼容或隔离方案。
- 回滚不得覆盖部署后新产生的有效业务数据。必须说明保留、重放、补偿和人工核对方式。
- 恢复完成后执行数量、校验和、约束、抽样、关键业务查询和审计验证，并保存证据。

## 11. 回滚执行与关闭

1. 记录触发信号、时间、当前版本、影响范围和决定人。
2. 冻结流量扩大与非必要变化，保护日志、指标和数据证据。
3. 按计划执行流量、应用、配置、数据库和依赖恢复。
4. 执行回滚后功能、数据、安全、性能与 AI 质量验证。
5. 监控至回滚观察窗口结束；未稳定时继续隔离或升级事件。
6. 将部署标记为 `ROLLED_BACK` 或 `FAILED`，不得复用原 `READY_FOR_RELEASE` 直接重发。
7. 创建根因、Bug / Incident、Change 和重新发布所需的新基线记录。
8. 更新 Release Report、PROJECT_STATE、PROJECT_MEMORY 和可复用知识条目。

重新发布必须修复并验证原因、更新受影响文档和风险，重新执行完整 Testing 与 Release Gate；旧授权自动失效。

## 12. 证据与审计

部署和回滚证据至少保存：Gate Record、版本 / Artifact / Commit、环境与配置清单、Migration / Dependency 记录、逐步执行日志、验证结果、监控快照引用、决定与批准、沟通记录、偏差、最终状态和 Release Report。

证据必须可访问、带时间和版本，并遵循最小权限与敏感信息脱敏。截图可以补充上下文，不能替代可搜索、可复核的结构化记录。
