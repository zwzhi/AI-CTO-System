# Post-Release Monitoring Standard

## 1. 目的与适用范围

本标准规定版本上线后的可观测性、告警、观察窗口和反馈闭环。监控设计必须在 [Release Approval Gate](./RELEASE_APPROVAL_GATE.md) 前完成，并与 [Deployment & Rollback Standard](./DEPLOYMENT_ROLLBACK_STANDARD.md)、测试证据和 [Release Report 模板](../../templates/RELEASE_REPORT_TEMPLATE.md) 使用同一版本基线。

监控不是上线后的补充工作。无法发现失败、无法定位版本、没有责任人或没有处置路径的发布，不具备发布条件。

## 2. 监控原则

1. 每个指标绑定用户或系统目标、数据源、版本、阈值、窗口、Owner 和处置动作。
2. 告警必须可行动；没有责任人、Runbook 或升级路径的告警不得作为门禁证据。
3. 发布前记录基线，发布后比较变化；只看绝对值可能掩盖退化。
4. 系统指标与用户结果同时观察，不能用服务存活代替产品可用。
5. AI 项目必须持续监控效果、风险、成本和延迟，不能只监控基础设施。
6. 日志、反馈和评测数据遵循最小收集、权限控制、脱敏、保留和删除规则。

## 3. 责任

| 角色 | 责任 |
|---|---|
| Monitoring Owner | 维护指标、仪表盘、阈值、告警、Runbook 和证据 |
| Service Owner | 对系统健康、错误、性能和容量作出响应 |
| Product / User Owner | 判断用户反馈、业务指标和验收影响 |
| AI Quality Owner | 维护 AI 质量样本、阈值、漂移与人工复核 |
| Security / Data Owner | 监控安全事件、敏感信息和数据完整性 |
| Release Owner | 在观察窗口内作出扩大、暂停、回滚或关闭发布决定 |

自动告警可以触发流程，但不能代替风险接受、发布成功或回滚关闭的责任人决定。

## 4. 必需监控域

### 4.1 系统状态

至少覆盖可用性、健康检查、关键服务 / 队列 / 作业状态、外部依赖、容量、资源饱和、部署版本和区域 / 租户差异。每个关键用户旅程应有端到端或等价合成检查。

### 4.2 错误日志

监控错误数量、错误率、异常类型、失败路径、重试、超时和新错误指纹。日志必须包含可关联 Release / Request / Trace 的标识，但不得记录 API Key、Token、密码、完整个人数据、Prompt 中的敏感原文或其他秘密。

### 4.3 性能指标

根据架构和非功能要求监控延迟分位数、吞吐、并发、队列、资源、超时、缓存、依赖耗时和容量余量。平均值不能替代尾延迟与异常窗口。

### 4.4 用户反馈

记录反馈渠道、时间、版本、用户场景、影响、严重度、复现信息、关联 Requirement / Bug / Incident 和处置状态。单一投诉不自动等于系统性失败，但不得因样本少而丢弃高影响信号。

### 4.5 AI 质量指标

AI 项目至少根据 [AI Evaluation Standard](../testing/AI_EVALUATION_STANDARD.md) 持续观察适用的输出质量、准确率、稳定性、幻觉风险、Prompt 效果、Agent 成功率、Token 成本和响应时间。监控记录模型、Prompt、工具、知识源、数据集和配置版本，区分真实退化、样本变化与评测漂移。

非 AI 项目可以对 AI 质量域使用 Approved N/A，但必须证明当前范围没有模型、Prompt、Agent、检索或生成式输出。

## 5. 指标定义

每个发布范围内的监控项必须记录：

| 字段 | 要求 |
|---|---|
| Metric ID | 唯一 `METRIC-XXXX` |
| 目标与关联 | 关联 Requirement、SLO / 验收标准、Release ID 和风险 |
| 定义 | 计算公式、单位、分子 / 分母、去重和缺失值规则 |
| 数据源 | 系统、日志、追踪、反馈或评测集及版本 |
| 维度 | 环境、版本、区域、租户、模型或其他必要切片 |
| 基线 | 发布前窗口、样本量、结果和 Confidence |
| 阈值 | 正常、预警、阻断 / 回滚阈值及持续窗口 |
| 采样与延迟 | 频率、聚合窗口、数据到达延迟和完整性检查 |
| Owner | 观察、响应、升级与复核责任人 |
| Runbook | 诊断、隔离、降级、回滚和沟通路径 |
| 证据 | 仪表盘、查询、原始记录和快照位置 |

阈值必须在发布前获批。发布后为了避免告警而放宽阈值，需要 Change 记录、影响分析和重新批准，不能静默修改。

## 6. 告警与事件分级

| 等级 | 示例 | 响应 |
|---|---|---|
| `CRITICAL` | 系统不可用、数据损坏 / 泄露、安全红线、核心 AI 输出造成高影响错误 | 立即通知 Release Owner；停止扩大，执行隔离 / 回滚决策 |
| `HIGH` | 核心功能明显退化、P1 Bug、错误或延迟越过发布阈值、AI 关键指标失败 | 在当前观察窗口内处理；不得关闭发布观察 |
| `MEDIUM` | 重要但有可验证绕行的局部退化 | 创建 Bug / Incident，明确 Owner、时限和趋势监控 |
| `LOW` | 体验、噪声或非关键优化信号 | 纳入反馈或后续计划，持续观察是否扩大 |

同一事件命中多个条件时采用最高等级。告警去重或抑制只能减少重复通知，不能隐藏实际事件或降低等级。

## 7. 发布观察窗口

每个 Release 必须在部署前定义：

- 观察开始和结束条件，不只写固定时长。
- 灰度 / 流量阶段、每阶段最小样本量和扩大条件。
- 必看 Metric ID、阈值、负责人和检查频率。
- 自动与人工检查、用户反馈入口和沟通节奏。
- 停止、隔离、回滚和升级触发器。
- 数据延迟、低流量或季节性导致证据不足时的延长规则。

观察窗口结束前，即使部署步骤完成，也不得将发布结果标记为最终成功。证据不足时状态保持观察中，不得把“没有告警”解释为通过。

## 8. 监控就绪门禁

申请 `READY_FOR_RELEASE` 前必须证明：

- 五类必需监控域均已覆盖，或有当前基线的 Approved N/A。
- 关键指标有数据、版本标签、基线、阈值、Owner 和 Runbook。
- 告警路由、升级链和通知渠道已通过受控验证。
- 仪表盘与原始证据可访问，时间、环境和版本一致。
- 日志脱敏、访问、保留和删除控制通过 Security Review。
- 回滚触发器与 Monitoring Metric ID 一一对应。
- AI 项目的线上质量指标与离线评测口径能够解释差异。

任一关键指标不可观测、告警不可达、责任人缺失或回滚触发器无法判定时，发布门禁必须为 `CHANGES_REQUIRED` 或 `BLOCKED`。

## 9. 上线后处理流程

1. 确认实际 Release ID、版本、环境和部署时间已进入所有监控维度。
2. 执行部署后健康与关键旅程检查，保存起始快照。
3. 按观察窗口检查系统、错误、性能、反馈和 AI 质量。
4. 触发阈值时创建 Bug / Incident，记录事实、影响、版本、Owner 和下一动作。
5. 达到回滚条件时按部署回滚规范暂停、隔离或回滚。
6. 指标恢复后继续观察至恢复条件与最小窗口同时满足。
7. 在 Release Report 中记录结果、事件、偏差、剩余风险和后续计划。
8. 更新 PROJECT_STATE、PROJECT_MEMORY；可复用事件经验进入 Knowledge Base。

## 10. AI 质量漂移与复评

以下情况必须重新执行对应 AI Evaluation：模型、Prompt、工具、知识源、检索索引、策略、数据分布或安全过滤变化；线上指标持续偏离离线基线；新高影响失败类型出现；成本或延迟达到停止阈值。

复评期间不得用总体平均掩盖高风险切片。应保存失败样本、脱敏输入、期望、实际、版本、分类和人工复核；涉及敏感数据时只保存必要引用与安全位置。

## 11. 监控结果与记录

每次发布至少形成：监控基线、发布期快照、告警 / Incident / Bug 列表、用户反馈摘要、AI 质量结果（适用时）、回滚触发器状态、观察窗口结论、剩余风险、Owner、下一动作和证据链接。

Monitoring Conclusion 只允许：

- `STABLE`：规定窗口、样本和阈值全部满足，未关闭发布阻断为 0。
- `OBSERVING`：仍在规定窗口或证据不足，尚不能作最终判断。
- `DEGRADED`：存在未达到回滚阈值但需处置的退化。
- `ROLLBACK_REQUIRED`：已触发获批回滚条件。
- `BLOCKED`：数据源、版本标签、权限或监控能力失效，无法可信判断。

结论必须指向当前 Release 和版本。旧版本的 `STABLE` 不能继承给新发布。
