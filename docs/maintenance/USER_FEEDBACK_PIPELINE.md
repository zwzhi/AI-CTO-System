# 用户反馈闭环规范

## 1. 目的

本规范确保用户反馈从接收到验证结果形成可追溯闭环，同时保护个人信息，避免高声量代替真实价值，也避免 Feedback 直接绕过需求、设计、开发和发布门禁。

## 2. 标准流程

`用户反馈 → 记录 → 分类 → 价值评估 → 进入 Backlog → 排期 → 开发 → 验证`

| 阶段 | 必须动作 | 输出 |
|---|---|---|
| 用户反馈 | 接收渠道、时间和原始语义；敏感信息最小化 | 原始 Feedback Evidence |
| 记录 | 创建 Feedback ID，去重但保留来源数量 | Feedback Record |
| 分类 | 确认类型、影响对象、候选严重性和关联项目 | 类型与路由结果 |
| 价值评估 | 评估用户、业务、频率、证据、风险、成本和战略关系 | 价值结论、Confidence、Priority 建议 |
| 进入 Backlog | 关联 Bug、Requirement、Debt 或 Evolution Proposal | 可追踪 Backlog Item |
| 排期 | 按批准的维护或产品计划确定 Owner 与版本 | 排期记录或延期依据 |
| 开发 | 执行适用设计、Task、TDD、Review 和 Git 规则 | Commit 与变更证据 |
| 验证 | 对反馈用户群和目标指标验证结果并回传 | Test / UAT / Metric Evidence 与闭环状态 |

## 3. 反馈类型

| Type | 定义 | 默认路由 |
|---|---|---|
| `Bug` | 实际行为偏离已批准预期 | 创建或关联 Bug；生产影响同时评估 Incident |
| `Feature Request` | 请求新增能力、范围或工作流 | Idea / Requirement；重大变化评估 Evolution Proposal |
| `Optimization` | 改善性能、成本、体验、质量或效率 | Maintenance Task、Debt 或 Evolution Proposal |
| `Complaint` | 表达不满、信任或服务体验问题，原因可能未明确 | 先确认事实和影响，再路由 Bug、Incident、产品或运营处理 |

分类可以更新，但必须保留原分类、变化原因、批准人和时间。Complaint 不能因缺少技术复现而被自动关闭。

## 4. Feedback Record 必填字段

至少记录 Feedback ID、类型、来源渠道、接收时间、脱敏后的原始描述、用户 / 场景、影响、发生频率、地域或版本、相关 Evidence、重复数量、关联 Bug / Incident / Requirement / Debt / Proposal、价值评估、Confidence、Priority 建议、Owner、状态、目标版本、验证方式、用户沟通和关闭证据。

个人身份、联系方式、对话内容和生产数据遵循最小必要记录。知识库只保留脱敏模式，不复制原始敏感反馈。

## 5. 价值评估

价值评估至少考虑：受影响用户与频率、问题严重性、用户目标受阻程度、业务价值、战略一致性、风险与合规、数据质量、实现成本、复用价值和当前 Confidence。

声量、单一大客户、内部职位或社交媒体热度可以是证据，但不能单独决定优先级。证据不足时记录补证动作，不把推测写成用户普遍需求。

## 6. Backlog 与排期规则

- 每个进入 Backlog 的反馈必须有稳定 ID、Owner、状态和复核时间。
- 重复反馈合并到主记录并累计来源、版本和频率；不得删除原始引用。
- `Bug` 按 Bug 严重性和维护 Priority 处理；P0 / P1 不得等待普通 Backlog 评审。
- 重大产品、架构、数据或 AI 行为变化必须生成 Evolution Proposal，不能从 Feedback 直接进入编码。
- 延期或拒绝必须记录依据、有效期、替代方案和对用户的沟通方式。

## 7. 验证与闭环

反馈只有在目标行为或指标已针对受影响场景验证、相关用户或授权代表完成验收、文档和监控同步、沟通已完成后才能标记 `CLOSED`。发布不等于反馈闭环；结果未改善时必须重新打开并关联新 Evidence。

闭环指标至少包括：首次响应时间、分类时长、有效反馈率、重复率、Backlog 年龄、交付率、验证通过率、重新打开率和用户结果改善。指标必须按类型和优先级分层，不能只报告平均值。
