# 项目归档与淘汰标准

## 1. 目的

本标准用于判断项目在生命周期后期应继续维护、重构、归档或停止，并确保用户、数据、合同、安全、依赖和知识资产得到可审计处理。历史投入不是继续运行的充分理由，短期维护成本也不是立即停止的充分理由。

## 2. 决策输入

每次 Retirement Review 必须冻结项目版本、运行状态、用户与业务数据时间窗，并评估：

| 因素 | 核心问题 | 证据示例 |
|---|---|---|
| 用户价值 | 是否仍解决真实问题，活跃用户和结果是否持续 | 使用、留存、反馈、UAT、替代方案 |
| 维护成本 | 人力、基础设施、供应商、Incident、升级和机会成本是否合理 | 财务、工时、故障、依赖和支持记录 |
| 技术状态 | 健康、安全、测试、架构、技术债和可恢复性如何 | Health Report、Debt、Security、Postmortem |
| 业务价值 | 收益、战略、合规义务、数据资产和生态关系是否成立 | 业务指标、合同、战略和风险记录 |

每项结论必须携带 Evidence、时间窗和 Confidence。无法获得关键数据时，结果为补证或受控风险判断，不能用主观分数代替。

## 3. 四种结论

| 结论 | 适用条件 | 后续动作 |
|---|---|---|
| `CONTINUE_MAINTENANCE` | 用户与业务价值仍成立，技术风险和成本可接受 | 保持 Maintenance，更新路线图、指标和复核日期 |
| `REFACTOR` | 价值仍成立，但架构、债务、安全或维护成本不可持续且有可行改造路径 | 创建 Evolution Proposal，经门禁批准后执行重构 |
| `ARCHIVE` | 当前不再主动运营，但代码、数据、文档或恢复价值仍需保留 | 停止活跃变更，建立只读归档、保留和恢复规则 |
| `STOP` | 价值不足、风险不可接受、替代完成或继续投入不合理 | 执行通知、迁移、数据处置、依赖下线和关闭验证 |

`ARCHIVE` 与 `STOP` 是项目处置结论，不是绕过运行关闭工作的状态标签。归档项目不得继续承诺生产服务；停止项目不得留下无人负责的公开入口、密钥、数据或付费依赖。

## 4. Review Record 必填字段

记录 Review ID、项目与版本、评估时间窗、四项因素及 Evidence、当前用户与合同、替代方案、数据与知识资产、依赖方、成本、风险、Confidence、候选结论、反对意见、用户 / 业务审批、执行计划、回滚或恢复边界、最终结论和下一复核日期。

项目 Owner 不能单独批准涉及用户数据删除、合同终止、安全风险接受或不可逆停止的决定；必须取得相应业务、数据、安全和用户责任人授权。

## 5. 继续维护与重构

- `CONTINUE_MAINTENANCE` 必须定义下一周期目标、预算、风险和退出触发器。
- `REFACTOR` 必须创建 Evolution Proposal，说明继续维护、渐进重构、替换和停止的比较。
- 重构不得直接开始编码；必须重新经过适用 Research / Evaluation / Design / Development / Testing / Release Gate。

## 6. 归档检查

归档前必须完成：版本与 Git Tag 冻结、文档与 PROJECT_MEMORY 更新、运行入口关闭、写权限撤销、密钥轮换或吊销、数据分类与保留、构建物和依赖清单保存、恢复说明与验证、Owner 和复核日期确认、用户与依赖方通知。

归档物必须只读、可验证完整性并具有访问审计。恢复项目时重新执行 Existing Project Onboarding 或经记录的恢复协议，不能把旧健康与安全结论直接视为当前有效。

## 7. 停止检查

停止前必须完成：用户迁移或替代、合同与通知、数据导出 / 保留 / 删除批准、第三方和基础设施终止、域名 / API / 队列 / 定时任务关闭、密钥与权限吊销、监控关闭条件、财务结算、最终 Release / Incident / Risk 记录、知识提取和停止后验证。

存在法定保留、用户导出、安全调查或依赖方迁移未完成时，项目可以进入受控停用，但不能宣称完全停止。不可逆数据删除必须有单独授权和可复核 Evidence。

## 8. 周期复核与重新激活

活跃项目至少按约定周期执行 Retirement Review；连续价值下降、成本失控、重复重大 Incident、关键技术 EOL、替代方案成熟或战略变化会提前触发复核。

归档项目重新激活前必须确认来源、权限、依赖、安全、数据、测试、文档与当前需求，并取得新的生命周期入口和门禁。旧审批、旧测试或旧风险接受不能自动复用。
