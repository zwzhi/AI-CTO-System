# Incident 故障管理标准

## 1. 目的

本标准规定生产故障从发现到复盘的统一流程，使 AI CTO 在优先保护用户、数据和业务连续性的同时，保留可复核的处理证据，并把临时恢复与永久修复分开管理。

Incident 是对生产影响的管理对象；Bug 是导致预期行为偏差的缺陷对象。一个 Incident 可以关联多个 Bug、Security Finding、Maintenance Task 和 Change，二者不能互相替代。

## 2. 处理流程

`发现 Incident → 影响评估 → 故障隔离 → 临时恢复 → 根因分析 → 永久修复 → 复盘`

| 阶段 | 核心动作 | 退出条件 |
|---|---|---|
| 发现 Incident | 创建 Incident ID，记录告警、时间、症状和当前基线 | 已指定 Incident Commander 和初始严重程度 |
| 影响评估 | 确认用户、业务、数据、安全、区域、时间窗口和扩散可能 | 影响边界、沟通对象和响应目标明确 |
| 故障隔离 | 限流、降级、关闭入口、隔离依赖或停止高风险操作 | 影响不再扩大，隔离动作有证据和回退方式 |
| 临时恢复 | 执行已授权回滚、切换、恢复或安全缓解 | 核心服务恢复到受控状态，监控确认稳定 |
| 根因分析 | 建立时间线、直接原因、系统根因和控制失效原因 | 根因和贡献因素达到所需 Confidence |
| 永久修复 | 建立 Task、TDD、Change Impact、Review、测试和发布记录 | 修复在目标基线验证，相关风险关闭 |
| 复盘 | 完成 Postmortem、行动项、经验沉淀与复发检查 | 行动项有 Owner、期限和验证标准 |

## 3. 严重程度

| Severity | 定义 | 响应边界 |
|---|---|---|
| `SEV-0` | 正在发生的灾难性安全、数据、人身或全局不可用风险 | 立即启动最高级响应，停止扩大影响，连续指挥与沟通 |
| `SEV-1` | 核心服务大范围不可用或关键结果严重错误 | 立即响应，优先恢复核心服务并保留现场 |
| `SEV-2` | 重要能力明显退化但影响有界或存在受控绕行 | 在约定响应窗口处理，持续监控影响 |
| `SEV-3` | 低影响、短时或局部生产异常 | 纳入维护处理并确认没有升级条件 |

严重程度由实际影响决定，不由修复难度决定。影响未知但可能达到更高级别时，按较高候选级别控制；证据确认后才能降级并保留变更历史。

## 4. Incident Record 必填字段

每个 Incident 必须记录：

- Incident ID；
- 发生时间、发现时间、确认时间、恢复时间和关闭时间，均含时区；
- 发现来源、当前状态、严重程度及分级依据；
- 影响范围，包括用户、业务、数据、安全、区域、接口、依赖和持续时间；
- 受影响的 Release / Commit / 配置 / 模型 / Prompt / 数据集 / 环境基线；
- Incident Commander、技术 Owner、沟通 Owner 和决策权限；
- 按时间排序的处理过程、命令 / Change / 决策与 Evidence；
- 故障隔离与临时恢复方案、结果、风险和回退方式；
- 直接原因、根本原因、贡献因素和为什么未提前发现；
- 永久修复方案、Task、Commit、测试、Review、发布和验证记录；
- 预防措施、行动项、Owner、期限、成功标准与复核状态；
- 关联 Bug、Security Finding、Debt、Feedback、Postmortem 和 Knowledge Entry。

## 5. 状态管理

Incident 状态只允许：`DETECTED`、`TRIAGED`、`MITIGATING`、`RECOVERED`、`ROOT_CAUSE_ANALYSIS`、`PERMANENT_FIX`、`POSTMORTEM`、`CLOSED`。

`RECOVERED` 只表示临时恢复和影响受控，不表示根因已清除。只有永久修复完成、验证通过、Postmortem 行动项已登记并且剩余风险获得授权处理后，Incident 才能 `CLOSED`。问题复发时保留原记录并重新打开或建立关联 Incident，不得覆盖旧时间线。

## 6. 指挥、沟通与安全

- Incident Commander 负责优先级、协调和决策记录，不应同时承担所有技术操作。
- 沟通必须区分已确认事实、推断和未知，不承诺未经验证的恢复时间。
- 日志、截图和聊天记录不得泄露密钥、用户数据或受限安全细节。
- 生产修改必须使用受控访问、双人复核或紧急变更记录，并在事后补齐常规验证，但不能补造事前证据。
- 对用户、监管方或合作方的通知遵循适用合同、法律和安全响应规则。

## 7. 根因与复盘要求

根因分析至少回答：发生了什么、为何发生、为何扩大、为何没有提前发现、哪些控制失败、哪些条件会再次触发。不得以“人为错误”“模型不稳定”“代码问题”作为终点。

`SEV-0`、`SEV-1`、重复 Incident、重大用户 / 数据 / 安全影响或暴露系统性控制缺陷的事件必须使用 `templates/POSTMORTEM_TEMPLATE.md`。复盘不以追责个人为目标，但必须明确责任、期限与验证证据。
