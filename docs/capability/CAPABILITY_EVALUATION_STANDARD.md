# Capability 质量评估标准

## 1. 评估基线

每次评估冻结 Capability ID、Source、Version / Commit / Model、License、输入输出合同、依赖、权限、环境、测试集、指标、成本口径、责任人和时间。任何影响行为、权限或兼容性的变化都会使旧分数失去当前性。

Quality Score 与 Mission Alignment、Risk Redline、Registry Status、Admission Result 和 Invocation Authorization 分开报告。

## 2. 100 分模型

| 维度 | 分值 | 评分重点 |
|---|---:|---|
| 功能有效性 | 25 | 目标任务成功率、输出正确性、边界和失败行为 |
| 稳定性 | 20 | 重复运行、错误率、超时、恢复、并发和长期一致性 |
| 兼容性 | 15 | Runtime、接口、Schema、平台、升级、回滚和项目适配 |
| 维护状态 | 15 | Owner、发布、Issue 响应、路线、依赖更新和替代能力 |
| 安全 | 15 | 最小权限、数据、供应链、隔离、日志、撤销和 Incident |
| 复用价值 | 10 | 跨项目适用、合同稳定、配置成本、可组合和资产贡献 |
| **合计** | **100** | 分数、Confidence 与红线分别判断 |

## 3. 分项评分锚点

每个维度按其满分比例使用：

- 90%–100%：多场景真实证据充分，边界和失败已验证。
- 70%–89%：核心场景通过，存在已知但可控缺口。
- 50%–69%：证据有限、波动明显或只适合受限场景。
- 0%–49%：目标未证明、关键失败、证据缺失或风险不可接受。

评分必须引用 Test Case 和 Evidence；不得因其他维度高分补齐缺失项。

## 4. 总分解释

| Score | 建议 | 使用边界 |
|---:|---|---|
| 90–100 | 推荐默认使用 | 仅在 `ACTIVE`、适用范围和权限完全匹配时作为默认候选 |
| 70–89 | 允许使用 | 记录已知限制、监控和 Fallback |
| 50–69 | 谨慎使用 | 仅限明确低风险 / 隔离范围、额外批准和更强监控 |
| <50 | 不推荐 | 不得激活；补证、替换或拒绝 |

50–69 分并不保证可以 `ACTIVATE_CAPABILITY`。项目若要求更高阈值、安全或稳定性，必须使用更严格标准。

## 5. 红线

以下任一情况独立阻断 `ACTIVATE_CAPABILITY`，不受总分抵消：

- 来源、Artifact 或 Publisher 无法验证；
- License 未知、冲突或不允许目标用途；
- 存在未关闭 Critical / High 安全风险；
- 权限超出目的且无法最小化，或要求直接暴露生产凭据；
- 不可逆副作用没有预演、停止和回滚；
- 核心兼容性、数据边界或失败行为未知；
- 无 Owner、无替代 / 退出方案且会成为 Core 强依赖；
- Evaluation Evidence 与当前版本、环境或权限不一致。

## 6. Evaluation Result

单次评估结果使用：

- `PASS`：达到目标用途阈值，Evidence 完整且无红线。
- `CONDITIONAL`：部分场景达到要求，但限制、监控和关闭条件明确；不能直接激活超出范围。
- `FAIL`：未达到功能、质量或风险要求。
- `BLOCKED`：环境、License、权限、数据或安全条件使评估无法完成。

只有 `PASS` 可以作为 `ACTIVATE_CAPABILITY` 的质量输入；它仍不能替代 Registry、Risk Review 和人类批准。

## 7. Evidence 与 Confidence

至少保存测试集、输入、输出、重复运行、失败、时延、成本、副作用、日志、兼容矩阵、安全 / License 结论、评分计算和评审人。Confidence 使用现有 L1–L4 模型，并说明证据覆盖、样本、环境差异和可推广边界。

公开资料或供应商声明通常最高只能支持 L2；项目隔离验证可支持 L3；跨版本和长期真实使用才可能达到 L4。

## 8. 复评触发器

版本、Source、License、依赖、权限、合同、环境、价格、维护状态、Incident、质量趋势或适用项目变化时重新评估。定期复评不得只重跑成功案例；旧结果保留并标记失效原因。
