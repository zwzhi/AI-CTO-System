# 数据库设计标准

## 1. 目的与适用范围

本标准规定 Database Design 在进入开发授权评审前必须提供的内容、证据和完成条件。这里的“数据库设计”涵盖项目拥有或使用的全部持久化数据，包括关系型、键值、文档、图、时序、向量、对象、文件、嵌入式存储及由外部系统托管的数据；不要求项目选择其中任何一种，也不把某一种数据库设为默认。

数据库设计文档应使用[数据库设计模板](../../templates/DATABASE_TEMPLATE.md)，并遵守[文档关联规则](../protocol/DOCUMENT_RELATIONSHIP.md)和[阶段门禁检查清单](../evaluation/PHASE_GATE_CHECKLIST.md)。数据模型、生命周期和迁移以 Database Design 为权威来源；产品目标、范围、需求和验收标准仍以 PRD 为权威来源。

本文中的“必须”是开发授权前的硬性要求；“应”表示除非有经评审的理由，否则需要满足；“可以”表示可按项目特点选择。逻辑设计与验收证据是强制的，具体存储产品、物理语法和实现方式由项目约束与 ADR 决定。

## 2. 文档信息、边界与版本基线

Database Design 必须记录项目名称、文档标识、版本、状态、作者、数据责任人、评审人、确认人和最后更新日期，并引用以下明确基线：

- PRD 的路径及版本号或提交标识。
- Architecture 的路径及版本号或提交标识。
- 获准进入 DESIGN 的范围和门禁记录。
- 相关接口契约、数据规范、法规或政策及其版本。
- 影响数据模型、存储选型、一致性、安全、迁移或恢复的 ADR 编号、路径和状态。

文档必须明确设计覆盖与不覆盖的数据域、租户或用户边界、环境和外部数据系统。评审确认后的数据模型、数据字典、生命周期、迁移策略和上述引用共同构成版本基线。字段语义、键与约束、关系、访问路径、保留规则、权限、一致性或迁移方式发生变化时，必须更新版本、影响分析、追溯关系和验证证据；重大变化还必须按 ADR 规则处理，不得静默覆盖已确认版本。

## 3. 数据所有权与需求追溯

### 3.1 数据所有权

每个数据域和关键实体必须记录：业务所有者、数据责任人或维护者、权威写入方、事实来源系统、允许的处理方和消费方、质量责任、共享边界及争议处理路径。外部系统托管的数据仍必须说明本项目是所有者、处理者、缓存方还是只读消费者，并记录契约责任和退出时的数据处置。

同一事实存在多个副本时，必须指定权威副本、同步方向、允许延迟、冲突解决方式和副本销毁规则。所有权不能只用团队名称代替，必须有可执行的角色或责任位置。

### 3.2 需求追溯

1. 每个数据域、实体、关键约束、关键访问路径和迁移设计必须拥有稳定且唯一的 Design ID；实体还必须拥有稳定的 Entity ID。
2. 每个 Design ID 必须引用一个或多个 Requirement ID、非功能需求 ID 或经批准的约束。
3. 文档必须包含需求到数据设计的对照表，至少记录 Design ID、设计对象、Requirement ID、非功能需求 ID、相关 Architecture Design ID、ADR 和验证证据或计划。
4. 必须执行正向和反向孤儿项检查：所有需要持久化支持的已批准需求均有数据设计落点，所有数据设计项均有需求、约束或经批准决策作为来源。
5. Traceability Matrix 是端到端关系的权威索引；Database Design 保存具体定义和本地映射。需求或数据设计变更后，两处必须同步更新。

## 4. 六项必备数据库设计内容与验收规则

以下六项均必须有独立、可定位的章节。章节不得仅有标题。所选数据技术不提供删减信息的理由；不具备传统表、外键或索引概念时，必须记录实现同等语义的逻辑结构、完整性机制和访问路径。

### 4.1 实体

每个实体必须记录 Entity ID、业务名称、定义、数据域、用途、粒度、事实来源、所有者、创建与更新来源、预估数量级、关联 Requirement ID 和 Architecture Design ID。实体可以映射到表、集合、对象、文件、图节点或其他持久化单元，但逻辑含义不得由具体产品名称代替。

验收时，每个持久化事实都有唯一且明确的主要实体归属，实体边界没有未解释的重叠；名称和定义在模型、字典、图示、接口和追溯表中一致，所有实体均能追溯到需求或约束。

### 4.2 字段

每个字段或数据元素必须记录稳定标识、所属 Entity ID、业务名称、定义、逻辑类型、格式或单位、允许值或值域、是否必需、缺失语义、默认值语义、来源、计算或派生规则、敏感级别、约束、示例和版本变化。逻辑类型应表达业务含义，不要求使用某一数据库的物理类型名称。

验收时，字段含义足以使生产者和消费者得到一致解释；必填、缺失、未知、空值和默认值不会混淆；敏感数据、派生数据和枚举值有明确来源及校验规则，字段可追溯到需求和实体。

### 4.3 关系

必须记录实体之间及实体与外部权威数据之间的语义关系，包括关系 ID、双方 Entity ID、业务含义、方向、基数、可选性、拥有方、生命周期依赖、引用完整性、删除或失效行为、一致性边界和跨域同步方式。

验收时，每条关系能在关系图或关系表中定位，基数与可选性无歧义；父子生命周期、孤儿处理、跨边界引用和一致性要求都有可验证规则，不因技术不支持物理外键而省略逻辑完整性设计。

### 4.4 索引

必须从已编号的查询、写入和检索模式推导索引或等价访问路径，记录访问路径 ID、服务的场景、过滤与排序维度、唯一性、预期选择性、覆盖范围、数据分布假设、读收益、写入与存储成本、维护方式和退役条件。全文、向量、分区键、对象前缀或外部检索结构等可以作为等价访问路径，但必须说明其语义和限制。

验收时，每个关键查询都有可解释的访问路径和性能验证计划；每个索引或等价结构都有实际访问需求，不存在无法说明用途的冗余结构；唯一性、热点、放大效应、数据倾斜和维护成本均已评估。

### 4.5 数据生命周期

必须按数据类别说明创建、校验、使用、更新、共享、归档、保留、冻结、匿名化或去标识、导出、删除和最终销毁。每个阶段必须记录触发条件、时限、所有者、权威状态、允许操作、自动或人工执行方式、审计证据和异常处理，并覆盖用户删除请求、法定保留、诉讼保全或同等限制中的适用项。

验收时，每类数据都有从产生到销毁的闭环；主数据、副本、缓存、搜索结构、导出、日志和备份的保留与删除规则一致或差异有批准依据；删除能够定义可验证的完成状态，不把“不可见”误作“已销毁”。

### 4.6 迁移方案

必须说明当前与目标模型版本、变更范围、前置条件、向前步骤、兼容窗口、数据回填或转换、双写或并行运行中的适用策略、切换条件、停机影响、资源预算、责任人、监控、验证、回滚或前滚路径以及终止条件。新项目也必须说明初始模型建立、版本记录和后续演进机制。

验收时，迁移可按步骤执行和中止；每一步都有输入、输出、成功标准和失败处理；旧版与新版读写兼容边界明确；回滚不会依赖已被不可逆破坏的数据，无法回滚的步骤有预先批准的前滚恢复方案和数据保护措施。

## 5. 约束、键与数据完整性

每个实体必须定义逻辑身份、主标识生成和稳定性、候选键、唯一性、引用键、必填和值域、跨字段不变量以及状态转换规则。若数据技术不提供主键或外键，仍必须说明如何唯一定位、去重和验证引用完整性。

文档必须区分由存储层、应用层、消息处理、批处理或人工流程执行的约束，记录执行时点、并发行为、违规处置、监控和修复责任。默认值不能掩盖缺失信息；自然键、代理键或复合键均需基于业务语义、稳定性和迁移影响选择，本标准不指定默认方案。

验收时，关键不变量有唯一的权威定义和至少一种强制或检测机制；重复、孤儿、越界值和非法状态转换均有处置路径及验证证据。

## 6. 容量、查询与性能

必须建立可复核的容量基线，至少记录初始数据量、增长驱动、增长率或场景、保留期、记录或对象大小假设、峰值与常态读写量、并发、热点、数据倾斜、批量处理、复制与索引开销以及容量告警阈值。没有历史数据时，估算必须标为假设并记录依据、可信度、验证时间和责任人。

关键访问模式必须拥有 Query ID，并记录调用方、目的、过滤、排序、聚合、返回规模、新鲜度、一致性要求、频率、峰值、延迟或吞吐目标、访问路径和降级行为。性能目标必须引用非功能需求 ID，并明确测量口径、数据规模、环境和通过条件。

验收时，可从查询清单推导访问路径和容量预算；关键查询、写入和维护任务都有代表性数据下的验证计划；扩容、归档、分区或等价策略由测量信号触发，而非只依赖主观判断。

## 7. 事务与一致性

必须按业务场景定义事务或原子操作边界、必须同时成功的变更、读写可见性、隔离或顺序要求、一致性模型、并发冲突、重复提交、幂等、失败后的补偿或重放、跨系统同步和最终收敛条件。不得用“强一致”或“最终一致”等标签代替对用户可见行为和时间边界的说明。

跨实体、跨存储或跨系统流程必须明确权威状态、提交点、部分成功的处理、消息丢失或重复的影响、对账方式和人工修复入口。若场景不需要事务，也必须记录不变量为何不会被破坏以及相应的验证证据。

验收时，每项关键业务不变量都能映射到一致性与并发控制设计；已分析中断、超时、重试、乱序、重复和并发更新，且恢复后有可判定的收敛与对账条件。

## 8. 权限、隐私与审计

必须按数据分类和处理目的定义主体、角色、允许操作、授权范围、最小权限、职责分离、访问审批、定期复核和撤销方式。敏感数据必须说明收集依据、目的限制、告知或同意、地域或跨境约束、保留与删除、展示与导出控制、脱敏或去标识、传输与存储保护、密钥或机密信息责任以及非生产环境使用规则。

审计设计必须记录需要留痕的读取、写入、导出、权限、配置、迁移和恢复事件，及其主体、时间、对象、结果、关联标识、保留期、防篡改要求、访问权限、告警和调查入口。诊断、分析和审计记录自身也属于受治理数据，必须纳入生命周期和敏感信息控制。

验收时，每类敏感数据都能映射到合法目的、授权主体、控制、保留规则和审计证据；高权限和批量访问可检测、可追责，且日志或备份不会绕过主数据的隐私边界。

## 9. 备份与恢复

必须按数据类别和业务影响定义恢复点目标、恢复时间目标、备份或副本范围、生成频率、保留周期、存放边界、加密与访问控制、完整性校验、目录与版本管理、失效和销毁方式。复制或高可用副本只有在能满足独立故障场景和历史恢复需求时才能作为备份证据。

恢复方案必须说明触发条件、决策人、依赖、执行顺序、目标环境、数据校验、服务切换、权限恢复、下游重放或对账、用户影响、失败处置和恢复完成标准。必须按风险设定恢复演练频率，记录最近演练的基线、结果、缺陷和关闭证据。

验收时，备份覆盖范围与生命周期一致，关键数据能够在目标时间和目标恢复点内还原；恢复验证同时覆盖可读性、完整性、一致性、权限、接口和业务抽样，而不以备份任务“执行成功”代替可恢复性证明。

## 10. 迁移回滚与验证

迁移计划除第 4.6 节内容外，还必须设置逐阶段进入与退出条件、变更冻结范围、备份或快照点、可逆性分类、停止阈值和责任分工。回滚方案必须明确触发信号、最晚决策点、模型和应用版本配对、回滚顺序、回填数据处置、外部消费者协调及回滚后的验证。

迁移验证至少应覆盖：记录或对象数量与控制总量、必填和值域、唯一性与引用完整性、关键业务不变量、抽样内容、权限与审计、关键查询性能、上下游契约、备份可恢复性以及新旧结果差异。校验规则、容差、样本方法、执行人和证据位置必须预先定义。

涉及不可逆转换、数据丢弃或超出回滚窗口的操作，必须在执行前完成恢复演练、风险接受和批准记录，并提供可执行的前滚修复路线。迁移完成后，旧结构、临时副本和双写路径必须有明确退役条件和删除责任人。

## 11. 数据字典

Database Design 必须包含或引用单一权威数据字典。数据字典至少记录数据域、Entity ID、字段或数据元素 ID、业务名称、定义、逻辑类型、格式或单位、值域或枚举、缺失语义、约束、敏感级别、所有者、事实来源、血缘、生命周期、版本和变更说明。

字典中的名称、定义和标识必须与模型、接口、查询、迁移和追溯表一致。枚举、代码集和业务术语必须有权威维护者和演进规则。引用外部字典时必须固定路径与版本，并说明本项目使用的子集；不得复制后形成无法同步的第二份定义。

验收时，生产者、消费者、测试和运维人员能依据字典对同一数据得到一致解释，且每个关键数据元素都能追溯到来源、所有者、约束和使用方。

## 12. 无持久化项目的可审计 N/A 规则

只有在项目范围内不存在任何需要在一次进程、会话或请求结束后保留的状态时，Database Design 的六项必备内容才可整体判定为不适用。不能因数据由第三方托管、只写文件或对象、使用浏览器或设备存储、仅保存配置、缓存、队列、日志、审计、备份、模型或向量而判定为无持久化；这些内容只要跨越运行边界保留，就属于本标准范围。

无持久化项目不得省略记录，必须创建可审计的 Database Design N/A 文档，至少包含：

- N/A 记录 ID、项目、范围、结论、作者、评审人、确认人和确认日期。
- PRD 与 Architecture 的明确路径和版本，以及进入 DESIGN 的范围基线。
- 对输入、输出、内存状态、临时文件、缓存、队列、日志、审计、配置、客户端状态、导出和外部服务逐项检查的结果与证据位置。
- 所有数据的产生、使用、传输和销毁边界，并证明其不会跨越约定的运行或会话边界保留。
- 外部数据系统的所有者、责任边界、接口契约和本项目不持有副本的证据。
- 相关 Requirement ID 和 Architecture Design ID、隐私与安全影响、已知风险、重新评审触发条件。
- 正向与反向追溯检查结果，证明没有持久化需求或未解释的数据设计孤儿项。

N/A 必须由数据责任人、Architecture 责任人和用户对当前版本明确确认。新增持久化需求、日志或审计留存、离线能力、外部数据副本、缓存跨会话保留或恢复要求时，N/A 立即失效，项目必须在继续开发授权评审前完成正式 Database Design。

## 13. 数据库设计完成定义

Database Design 只有同时满足以下条件才可标记为“已确认”：

- 实体、字段、关系、索引、数据生命周期和迁移方案六项必备内容全部存在并通过各自验收，或无持久化 N/A 记录满足第 12 节的全部证据与确认要求。
- PRD、Architecture、范围门禁、相关契约、政策和 ADR 的路径及明确版本已形成基线。
- 数据域、实体和关键数据元素的所有权、事实来源、处理方、消费方和责任边界明确。
- 键、约束、不变量、访问路径、容量、关键查询、事务与一致性设计可验证，不存在未解释的完整性缺口。
- 权限、隐私、审计、生命周期、备份与恢复相互一致，并覆盖副本、缓存、日志、导出和外部托管数据。
- 迁移、回滚、前滚和验证方案有明确触发条件、步骤、容差、责任人和证据位置；不可逆步骤已完成风险接受。
- 数据字典完整且为单一权威定义，模型、接口、查询、迁移和字典中的标识与语义一致。
- 所有相关 Requirement ID 与非功能需求均有 Design ID 落点，正向和反向孤儿项检查通过。
- 重大数据决策均有 Accepted ADR，评审问题均已关闭，不存在未接受的高风险或开发阻断项。
- 指定评审人已完成数据、架构、安全、隐私、运维和迁移评审，并留下当前版本的确认记录。

数据库设计完成不等于自动授权进入 DEVELOPMENT。最终转换仍必须满足 Design Approval Gate 和阶段门禁的全部要求，并由用户确认当前文档版本。
