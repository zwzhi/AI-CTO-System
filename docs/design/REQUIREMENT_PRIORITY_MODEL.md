# 需求优先级模型

## 1. 目的与原则

本模型用于 AI CTO 对具有稳定 Requirement ID 的产品需求给出 P0–P3 优先级，并记录可复核的判断依据。优先级表达“该需求对当前批准目标的重要性和延期后果”，不等于实现顺序、排期承诺、项目评分或开发授权。

本模型与[产品设计标准](./PRODUCT_DESIGN_STANDARD.md)配套使用。需求只能在当前 PRD 范围和证据基线上评审；范围、证据或目标版本变化后必须重新判断。模型采用明确条件和专业判断，不创建自定义复杂数学评分，也不得用总分掩盖硬门槛、证据缺口或风险。

## 2. P0–P3 定义

| 优先级 | 定义 | 可执行判断 | 延期后果 |
|---|---|---|---|
| **P0 核心生存功能** | 当前批准版本能够成立、合法、安全运行并完成关键用户闭环所不可缺少的最小功能或控制 | 缺失时，至少一个批准的关键场景无法完成，或产品会触发不可接受的合规、安全、隐私、数据完整性或业务连续性风险；当前版本没有可接受替代方案 | 当前版本不得发布或不得宣称达到目标；P0 是例外级别，必须通过严格门槛 |
| **P1 重要功能** | 对主要用户结果或已批准业务结果有显著贡献，但产品在受限、降级或人工替代方式下仍能形成最小闭环 | 缺失会明显降低完成率、质量、采用、运营能力或业务成效；有可接受但成本较高或体验较差的临时替代 | 可以分阶段交付，但必须说明降级方案、影响和补齐触发器 |
| **P2 优化功能** | 改善效率、体验、成本、质量或可维护性，缺失不妨碍当前关键闭环和强制控制 | 主要价值是减少步骤、提升便利性、优化性能或降低非关键成本；现有路径仍可接受 | 可在核心闭环稳定后安排，延期不会使当前版本失去成立条件 |
| **P3 未来探索** | 面向未来机会、尚待验证的假设或依赖后续条件的能力 | 用户或商业证据不足、目标人群尚未确认、依赖未就绪，或只与未来版本相关；有明确研究问题和纳入触发器 | 不进入当前交付承诺；先研究、原型验证或等待触发条件 |

优先级必须针对一个具体版本判断。同一需求在不同版本或证据基线下可以变化，但变更必须保留记录。

## 3. P0 的严格门槛

只有以下条件全部满足，需求才能标为 P0：

1. **当前基线**：需求属于当前批准范围和目标版本，而不是未来愿望。
2. **独立需求**：需求已拆成可独立验收的最小行为，不是把多个功能捆绑成一个“全都必需”的大包。
3. **生存必要性**：能够指出具体角色和关键场景，并证明缺失会使关键闭环无法完成，或触发当前不可接受的强制性风险。
4. **没有可接受替代**：人工、降级、已有工具或收窄范围均不能在当前目标下提供可接受结果；若存在可接受替代，默认不高于 P1。
5. **证据充分**：必要性有当前 Research、Evaluation、法规、事故、运营数据、用户证据或已接受决策支持，而不是仅凭职位、声音大小、紧急措辞或个人偏好。
6. **结果可测试**：Requirement ID、场景、量化或明确的验收标准、失败后果均已记录。
7. **风险双向评估**：既说明它降低什么风险，也说明实现它会引入什么安全、隐私、数据、运营、依赖或回滚风险；引入风险有责任人和处置方案。
8. **明确批准**：产品或用户批准人确认 P0 结论及其版本；涉及专业风险时，对应风险责任人同时确认。

任一条件不满足时，不得批准为 P0。证据不足通常标为 P3 并先验证；价值明确但仍有可接受替代时通常标为 P1；只改善现有可用路径时通常标为 P2。

“老板要求”“客户说很急”“开发已经开始”“其他产品都有”“可能以后需要”和“实现成本很高”均不能单独构成 P0 依据。

## 4. 四个判断因素

每项需求必须分别记录用户价值、商业价值、开发成本和风险。可以使用高/中/低等相对等级帮助讨论，但不得将等级换算成一个自动决定优先级的自定义总分。

### 4.1 用户价值

判断问题：

- 服务哪个已定义角色和场景？
- 痛点的频率、严重度、覆盖人数和当前替代方式是什么？
- 需求会改变什么可观察的用户结果？
- 证据来自访谈、行为数据、工单、实验还是假设？Confidence 如何？

| 判断 | 标准 |
|---|---|
| 高 | 直接决定主要角色能否完成高频或高后果关键任务，或避免严重用户伤害；有当前证据 |
| 中 | 明显改善任务成功率、时间、质量或可访问性，但存在可接受替代路径 |
| 低 | 便利、偏好或小众改善；影响面、频率或证据有限 |

用户价值高不自动等于 P0；仍须检查当前范围、商业目标、替代方案和风险。

### 4.2 商业价值

判断问题：

- 对应哪个已批准目标或 Metric ID？
- 对收入、成本、留存、转化、交付能力、战略承诺或强制合规有什么可观察影响？
- 价值发生在什么时间窗口，若延期是否错过不可逆窗口？
- 影响有数据、合同、政策或决策记录支持吗？

| 判断 | 标准 |
|---|---|
| 高 | 决定当前版本的批准业务结果、强制义务或产品可持续运行，影响可量化且时间相关 |
| 中 | 对批准指标有显著贡献，但可以延期、分阶段或由其他方式部分实现 |
| 低 | 与当前目标联系间接、价值较小或主要面向尚未批准的未来机会 |

强制合规或安全控制可以主要体现为商业连续性和风险价值，但仍须说明对用户权益的间接影响。

### 4.3 开发成本

开发成本必须同时考虑：设计与实现工作量、依赖、数据或迁移、外部采购、测试、上线、运维、支持、机会成本和长期维护。成本估算应记录范围、假设、负责人和日期，可用小/中/大或组织现有估算方法表达。

- 高成本不自动降低重要性；对高价值需求应优先考虑拆分最小切片、复用、Build vs Buy 或分阶段交付。
- 低成本不自动提高重要性；“顺手做”不能把 P2/P3 变成 P0/P1。
- 成本和资源约束主要影响范围切片与实施顺序；优先级仍由价值、延期后果和风险决定。
- 估算不确定性高时，应先安排调研或验证，并把不确定性写入风险，不得伪造精确数字。

### 4.4 风险：降低与引入

风险必须分两面记录，不能只写需求带来的好处：

| 风险方向 | 必须回答 | 对优先级的影响 |
|---|---|---|
| 风险降低 | 需求降低哪一项现有风险；触发条件、可能性、影响、证据和剩余风险是什么；是否涉及红线或强制控制 | 若它是当前版本关闭不可接受风险的必要控制，可支持 P0；若只是改善一般风险，通常支持 P1 或 P2 |
| 风险引入 | 实现或运行会新增哪些安全、隐私、合规、数据、可用性、运营、供应商锁定、成本或不可逆风险 | 引入风险不会提高优先级；它可能要求拆分、缓解、试验、回滚方案、风险接受或阻断实施 |

风险降低和风险引入不得相互抵消成一个模糊的“净风险分”。一个需求可以因生存必要性保持 P0，同时因引入风险而处于 `Blocked` 状态；这表示它仍然重要，但尚未具备实施或发布条件。优先级、风险接受和开发就绪状态必须分别记录。

## 5. 判定流程

AI CTO 应按以下顺序完成每项需求的优先级判断：

1. 核对 Requirement ID、需求行为、目标版本、核心/非核心分类和范围批准状态。
2. 分别记录用户价值、商业价值、开发成本、风险降低与风险引入的证据和 Confidence。
3. 检查需求是否可独立验收；不能独立验收时先拆分，再分别判断。
4. 尝试 P0 时逐项执行严格门槛；未全部通过不得标为 P0。
5. 根据延期后果和替代方案，在 P1、P2、P3 定义中选择唯一匹配项。
6. 记录冲突、裁决理由、批准人和评审日期；未裁决时状态为 `Proposed`，不得宣称优先级已批准。
7. 单独制定实施顺序、依赖与就绪状态，不按 P0 → P3 机械排序。
8. 在范围、证据、成本、风险、依赖或目标版本变化时重新评审。

每项需求在一个版本基线上只能有一个批准优先级。

## 6. 冲突裁决规则

当四个因素给出不同方向时，按以下规则裁决，不进行加权求和：

1. **先守硬门槛**：已触发且未关闭的红线、违法、不安全或数据完整性问题不能被用户热度、商业收入或低成本抵消。必要控制是否为 P0，仍须满足当前基线、无替代和证据要求。
2. **回到批准目标**：用户价值与商业价值冲突时，检查当前批准的角色、场景和成功指标。P0 至少要有一项高价值依据，另一项不得与批准目标相冲突；纯内部便利或纯偏好不能成为 P0。
3. **重要性不被成本改写**：高价值高成本需求保留其真实重要性，再通过拆分、替代方案或分期处理成本；低价值低成本需求仍保持 P2/P3。
4. **风险必须双向展示**：风险降低可以提高紧迫性，风险引入则影响方案、就绪状态和实施顺序。高引入风险没有责任人或处置方案时，需求不能进入开发门禁。
5. **证据强度优先**：证据与意见冲突时，展示来源、日期、适用范围和 Confidence。关键结论只有 L1 或证据冲突未处理时，不得批准为 P0。
6. **最小可行切片优先**：若需求的一部分满足 P0、其余只提供优化，必须拆成独立 ID，分别设为 P0 与 P1/P2，不得整体抬高。
7. **明确责任归属**：产品或用户批准人对价值、范围和最终优先级负责；工程、测试、安全、合规、数据和运营责任人提供成本与风险判断。AI CTO 负责形成建议和记录，不能替代授权人决定。
8. **无法裁决就不假装确定**：未解决冲突必须记录责任人、所需证据和复核触发器；在此之前保持 `Proposed`，且不能用 P0 获得排期优势。

## 7. 禁止把所有需求标为 P0

P0 表示维持当前版本生存条件的最小集合，不是“很重要”的同义词。本模型不设置任意百分比配额，但出现全部或大多数需求均为 P0 时，评审必须暂停并执行以下检查：

- 对每项需求单独写出“若删除，哪个关键场景会失败或哪条强制风险会触发”；
- 验证是否存在人工、降级、复用、收窄目标或延后到下一版本的可接受替代；
- 拆分混合了生存功能、重要增量与体验优化的需求包；
- 重新确认当前版本是否仍是完成批准目标的最小闭环；
- 逐项提供证据、验收标准和批准记录。

任何一项无法独立通过 P0 门槛，就必须降为 P1、P2 或 P3。用“全都重要”“需求方都很急”或统一 P0 回避取舍，视为优先级评审失败。

## 8. 优先级与实施顺序分离

优先级回答“延期会损失什么”，实施顺序回答“在依赖、学习、风险和资源约束下先做什么”。两者必须使用不同字段记录。

实施顺序可以考虑：

- 技术、数据、采购和外部审批依赖；
- 先验证高不确定性或高风险假设；
- 先建立测试、观测、迁移或回滚能力；
- 团队与环境可用性；
- 可逆性、集成窗口和发布批次。

因此，P1/P2 的验证或支撑工作可能早于某项 P0 的完整实现，P0 也可能因未关闭风险而暂时 `Blocked`。这不改变 P0 的发布阻断性质。排期不得仅按优先级排序；每个开发任务仍须在 Development Plan 中记录依赖、顺序、责任人、验证方法和完成条件。

## 9. 标准输出格式

每次优先级评审至少输出以下字段：

| 字段 | 记录要求 |
|---|---|
| Requirement ID / 名称 | 稳定 ID 与单一、可验收的需求行为 |
| 目标版本 / 范围分类 | 具体版本；核心或非核心 |
| 建议优先级 / 状态 | P0、P1、P2 或 P3；`Proposed`、`Approved`、`Blocked` 或 `Superseded` |
| 用户价值 | 角色、场景、结果、证据、Confidence 与高/中/低判断 |
| 商业价值 | 目标或 Metric ID、量化影响、时间窗口、证据与高/中/低判断 |
| 开发成本 | 相对估算、范围、关键假设、依赖、运维与维护影响 |
| 风险降低 | 风险、触发条件、可能性、影响、控制效果和剩余风险 |
| 风险引入 | 新风险、缓解、监控、回滚、责任人和接受状态 |
| P0 门槛 | 逐项通过记录；非 P0 写明最关键的不满足条件 |
| 优先级理由 | 延期后果、替代方案和冲突裁决 |
| 实施顺序 | 独立于优先级的批次或序号、前置依赖和就绪状态 |
| 决策记录 | 评审人、批准人、日期、证据基线和 PRD 版本 |

### 示例：AI CTO 的 PRD 生成流程

| Requirement ID | 需求 | 范围 | 优先级 | 四因素摘要 | 风险双向判断 | 实施顺序 | 判定理由 |
|---|---|---|---|---|---|---|---|
| REQ-PRD-001 | 批准前校验 PRD 十项必需内容及核心需求的可测试 AC | 核心 | P0 | 用户价值高：避免不可执行交付；商业价值高：直接支撑设计门禁；成本中 | 降低遗漏与误批风险；引入规则误判风险，以人工复核和带理由的驳回记录缓解 | 批次 2 | 缺失时无法形成可验收 PRD，当前流程没有可接受替代；P0 门槛全部通过 |
| REQ-PRD-002 | 展示事实/假设登记及证据缺口警告 | 核心 | P1 | 用户价值高：看清不确定性；商业价值中：降低返工；成本中 | 降低把推断当事实的风险；引入敏感证据暴露风险，以最小权限和引用脱敏缓解 | 批次 1 | 显著提高质量，并为后续校验提供结构，但当前可由人工登记降级完成 |
| REQ-PRD-003 | 提供两个 PRD 版本的逐项差异视图 | 非核心 | P2 | 用户价值中：减少人工比对；商业价值中：提高评审效率；成本中 | 降低静默变更风险；引入历史版本保存成本，设置保留期 | 批次 3 | 现有版本记录仍可完成评审，主要价值是效率优化 |
| REQ-PRD-004 | 自动推荐跨行业产品机会 | 非核心 | P3 | 用户价值未验证；商业价值低且不属于当前目标；成本大 | 可能发现机会；会引入错误类比、幻觉和额外数据合规风险 | 研究队列 | 属于未来假设，先验证用户需求、证据质量和风险边界 |

示例中 REQ-PRD-002 的实施顺序早于 REQ-PRD-001，但 P0 仍是发布阻断项，说明实施顺序不改变优先级。

## 10. 优先级变更记录

优先级发生变化时，Requirement ID 保持不变，并追加以下记录：

| 字段 | 内容 |
|---|---|
| Change ID | 唯一变更编号 |
| 日期与 PRD 版本 | 生效日期和对应基线 |
| Requirement ID | 被调整的需求 |
| 原优先级 / 新优先级 | P0–P3 的明确变化 |
| 触发原因 | 范围、证据、目标版本、成本、风险、依赖或法规变化 |
| 四因素变化 | 用户价值、商业价值、开发成本、风险降低与风险引入的旧判断和新判断 |
| 影响分析 | 对核心/非核心、成功指标、验收、实施顺序、架构、测试、风险和发布的影响 |
| 证据与 Confidence | 来源、版本、日期和关键结论等级 |
| 决策 | 批准、驳回或退回补证；批准人、风险接受者和记录位置 |

升为 P0 必须重新通过全部 P0 门槛。P0 降级或核心/非核心联动变化属于实质范围决定，必须按产品设计标准重新评审 PRD、更新版本基线，并检查对 Architecture、Development Plan 与验收测试的影响。不得覆盖旧值或删除历史理由。

## 11. 完成检查

一次优先级评审只有同时满足以下条件才算完成：

- [ ] 所有需求使用稳定 ID，并在一个版本基线上唯一归类为 P0、P1、P2 或 P3；
- [ ] P0、P1、P2、P3 均按本文定义判断，没有用紧急程度替代证据；
- [ ] 每项需求分别记录用户价值、商业价值、开发成本、风险降低和风险引入；
- [ ] 每项 P0 均逐条通过严格门槛，且全部 P0 已接受“最小生存集合”复核；
- [ ] 核心/非核心与优先级不存在冲突，P0 未被列为非核心；
