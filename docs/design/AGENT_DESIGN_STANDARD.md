# AI 项目 Agent 设计标准

## 1. 目的与适用范围

本标准规定 AI 项目在进入 DEVELOPMENT 前必须完成的 Agent 设计内容。它用于描述 Agent 的责任边界、交互契约、权限、安全控制和验证门槛，不包含具体 Agent 代码、实现框架或供应商绑定方案。

项目应使用 [Agent Design 模板](../../templates/AGENT_DESIGN_TEMPLATE.md) 形成设计文档，并遵守 [文档关联规则](../protocol/DOCUMENT_RELATIONSHIP.md) 与 [阶段门禁检查清单](../evaluation/PHASE_GATE_CHECKLIST.md)。是否获得开发授权以 [Design Approval Gate](./DESIGN_APPROVAL_GATE.md) 的结果为准。

本标准中的“必须”表示开发授权的硬性要求；“应”表示除非有明确、可审计理由，否则必须满足。AI 项目中的每个 Agent 都适用本标准。多个 Agent 协作时，既要分别设计，也要补充它们之间的路由、委派、冲突处理和终止条件。

## 2. 文档信息与需求追溯

每份 Agent Design 必须记录：

| 项目 | 必填内容 |
|---|---|
| 项目与 Agent 标识 | 项目名称、稳定且唯一的 Agent ID、Agent 名称 |
| 设计标识 | 稳定且唯一的 Design ID；变更时保留历史，不复用已废弃 ID |
| 版本与状态 | 文档版本、状态、最后更新日期；状态至少区分 Draft、In Review、Approved、Superseded |
| 责任与批准 | 设计责任人、评审人、批准人 |
| 上游基线 | 当前 PRD、Architecture 及其版本或提交引用 |
| 需求映射 | Agent ID 与 Design ID 对应的 Requirement ID 列表 |
| 决策引用 | 相关 ADR 的路径、编号和状态 |
| 下游引用 | Development Task ID、Test Case ID 或对应文档位置 |
| 适用环境 | 开发、测试、预发布、生产等允许运行的环境 |

每项 Agent 能力必须能追溯到至少一个已批准 Requirement ID。一个 Agent 可以实现多个需求，一个需求也可以由多个 Agent 或设计共同实现，但必须在 Traceability Matrix 中展开成完整链路，不得使用笼统的“相关需求”代替 ID。

## 3. Agent 职责、边界与非职责

设计必须说明 Agent 为什么存在、负责什么，以及明确不负责什么，至少包括：

- 目标、成功结果和停止条件。
- 允许执行的判断、建议、生成、查询和变更动作。
- 禁止执行或必须交由其他组件、其他 Agent 或人工处理的事项。
- 业务边界、系统边界、数据边界、地域边界和时间边界。
- 上游输入方、下游消费方、依赖服务与人工责任人。
- 自主程度：只读建议、受控执行、需逐次审批执行或仅人工执行。
- 多 Agent 场景中的委派条件、最大委派深度、循环检测、冲突裁决和最终责任归属。

非职责不得只写“无”。所有会造成资金、权限、数据、外部承诺、合规或不可逆影响的动作，都必须明确由谁负责最终决定。Agent 不得把业务责任转移给模型或工具。

## 4. 输入契约

每类输入必须作为独立契约记录：

| 字段 | 设计要求 |
|---|---|
| 输入名称与来源 | 标明用户、系统、Agent、文件、事件或工具等来源 |
| 格式与结构 | 定义字段、类型、必填项、长度、语言、编码和附件限制 |
| 语义与时效 | 说明含义、时间戳、有效期、顺序要求和重复事件处理 |
| 信任边界 | 标明可信、已验证或不可信；外部内容默认不可信 |
| 数据分类 | 按本标准的数据分类标记输入及字段 |
| 验证与清洗 | 定义结构校验、权限校验、来源校验、恶意内容检测和最小化处理 |
| 无效输入处理 | 定义拒绝、澄清、隔离、降级或转人工条件 |
| 追溯信息 | 保留请求 ID、来源引用和必要的授权证据 |

输入验证必须在任何高影响推理或工具调用之前完成。来自网页、文件、Memory、工具返回值或其他 Agent 的内容都可能包含指令，不能因为它们位于内部系统中就提升其指令优先级。

## 5. 输出契约

每类输出必须说明：

- 输出名称、用途、消费者、格式、结构和必填字段。
- 质量标准、完整性标准、允许的不确定性和置信度表达方式。
- 事实、推断、建议和未验证内容的区分方式。
- 来源、证据、时间戳、Agent ID、Prompt 版本、模型版本和请求 ID 等追溯字段。
- 数据分类、脱敏规则、允许的传输渠道和保留位置。
- 重复提交、部分成功、超时和消费者拒绝时的处理方式。
- 输出能否直接触发动作；如能，必须说明审批、幂等、回滚和审计要求。

当证据不足、输入冲突或无法达到最低质量标准时，Agent 必须输出明确的受限结果或失败状态，不得伪造事实、引用、成功状态或工具执行结果。

## 6. Prompt 策略、版本与注入防护

### 6.1 Prompt 策略

设计必须描述 Prompt 的目标和组成，而不是仅附一段提示词。至少包括：

- 指令层级：系统规则、项目政策、Agent 任务、运行时上下文和用户输入的优先顺序。
- 稳定指令与动态上下文的分离方式。
- 任务拆解、澄清、拒绝、工具选择、结果校验和终止策略。
- 输出格式、证据要求、不确定性表达和自检要求。
- 上下文长度、截断、摘要、语言和多轮一致性策略。
- 模型、关键参数、外部策略文件和评测集的版本关联。

### 6.2 版本管理

每个可发布 Prompt 必须有唯一版本。设计必须记录版本变更原因、受影响的 Requirement ID、Design ID、工具、Memory、评测集和回滚版本。Prompt、模型、工具权限或检索策略发生实质变化时，必须执行影响分析并重新评估；重大决策变化按 ADR 规则处理。

### 6.3 Prompt 注入防护

设计至少必须包含以下控制：

- 把用户内容、检索内容、文件内容、网页内容、工具输出和其他 Agent 消息视为数据，不视为高优先级指令。
- 使用结构化边界区分可信指令与不可信内容，不允许不可信内容覆盖系统政策、权限或审批要求。
- 对请求进行目标、权限、数据分类和预期副作用校验，再决定是否调用工具。
- 对敏感数据外传、秘密提取、越权操作、策略绕过和间接注入设置检测与拒绝规则。
- 对高风险工具执行前后的参数与结果进行独立校验；审批必须绑定具体动作、对象、环境和有效期。
- 不把密钥、令牌、隐藏系统指令或完整敏感上下文提供给模型、Memory 或不需要它们的工具。
- 将疑似注入事件记录为安全事件，并按设计的停止、隔离和人工接管流程处理。

## 7. 工具调用、契约、权限与审批

所有工具默认不可用，只有设计清单中明确允许的工具才可调用。工具清单必须逐项记录：

| 项目 | 必填内容 |
|---|---|
| 工具与能力 | 工具名称、版本、用途和对应 Requirement ID、Design ID |
| 调用契约 | 输入结构、前置条件、输出结构、错误类型、超时和速率限制 |
| 数据访问 | 可读写的数据分类、资源范围、租户、地域和环境 |
| 权限身份 | 使用的服务身份、最小权限范围、凭据来源与轮换责任 |
| 副作用等级 | NONE、READ、WRITE、EXTERNAL 或 IRREVERSIBLE |
| 审批方式 | 自动、预批准范围内、逐次人工批准或仅人工执行 |
| 可靠性控制 | 幂等键、重试条件、最大次数、退避、去重和并发限制 |
| 失败恢复 | 补偿动作、回滚方式、安全状态和人工接管条件 |
| 审计证据 | 请求 ID、调用者、参数摘要、批准记录、结果、时间和成本 |

权限设计必须遵守最小权限、默认拒绝、环境隔离和职责分离。只读任务不得授予写权限；测试身份不得访问生产数据；一个审批不得扩展为对其他对象、其他动作或无限时间有效。

有副作用的工具调用必须在执行前展示或记录动作对象、预期变化、影响范围和回滚能力。EXTERNAL 与 IRREVERSIBLE 级动作必须逐次获得明确人工批准；无法可靠回滚的动作还必须有预演、二次确认或等价的风险控制。工具返回“成功”不能替代对实际结果的验证。

## 8. 工作流程与状态控制

设计必须用步骤、状态图或等价方式说明：

1. 输入接收、身份与权限验证。
2. 数据分类、内容安全和注入检测。
3. 上下文与 Memory 读取。
4. 推理、计划或候选结果生成。
5. 工具选择、审批、执行和结果验证。
6. 输出校验、交付与审计记录。
7. Memory 写入、保留和清理。
8. 正常终止、失败终止、降级和人工接管。

每个状态必须定义进入条件、退出条件、最大停留时间和允许的下一状态。循环、重试和多 Agent 委派必须有上限，并提供可中止机制。

## 9. Memory 使用、读写、保留与隔离

Memory 仅用于已说明的业务目的。设计必须区分会话上下文、短期工作记忆和长期记忆，并逐类记录：

| 项目 | 设计要求 |
|---|---|
| 目的与内容 | 为什么需要保存、允许保存哪些字段、禁止保存哪些字段 |
| 读取规则 | 谁可读、何时读、检索范围、排序、时效和来源可信度 |
| 写入规则 | 谁可写、触发条件、结构校验、去重、冲突处理和批准要求 |
| 数据分类 | 逐字段分类，并说明脱敏、加密和访问控制 |
| 来源与质量 | 来源引用、写入时间、有效期、置信度和验证状态 |
| 保留与删除 | 保留期限、过期方式、用户删除、法律保留和备份清除 |
| 隔离 | 用户、租户、项目、环境和 Agent 之间的隔离边界 |
| 审计 | 读取、写入、更正、导出和删除的记录要求 |

未经验证的信息不得作为确定事实写入长期 Memory。过期、冲突或低置信信息必须标记并在使用前重新验证。密钥、访问令牌、完整身份凭据和与目的无关的敏感数据不得写入 Memory。Memory 删除必须覆盖主存储、索引、缓存和按政策到期的备份副本。

## 10. 数据分类、安全与隐私

项目必须采用已有组织分类政策；如无更严格政策，至少使用以下分类：

| 分类 | 最低处理要求 |
|---|---|
| Public | 可公开，但仍需验证来源、许可和完整性 |
| Internal | 仅限授权项目成员、Agent 和工具；不得发送到未批准外部服务 |
| Confidential | 包含个人、客户或敏感业务数据；必须最小化、加密、脱敏、限域并审计 |
| Restricted | 包含密钥、认证材料、受监管或高影响数据；默认禁止进入 Prompt、日志和 Memory，仅可在专项批准与隔离控制下处理 |

设计还必须覆盖身份认证、授权、租户隔离、传输与静态加密、秘密管理、数据最小化、目的限制、同意与删除、供应商边界、内容安全和安全事件响应。日志与评测数据同样适用数据分类，不得因“用于调试”而降低保护等级。

## 11. 失败处理、降级与人工接管

设计必须形成失败模式清单，至少覆盖输入无效、模型不可用、输出不合格、工具超时、部分成功、重复执行、Memory 不可用、权限不足、数据冲突、注入攻击、成本或时延超限以及外部依赖故障。每种失败模式必须定义：

- 检测信号和可观察症状。
- 是否可重试、重试上限和幂等条件。
- 安全停止状态、降级能力和禁止继续的条件。
- 补偿、回滚、数据修复和通知方式。
- 对用户可见的错误信息，不泄露敏感内部细节。
- 责任人、响应时限和升级路径。

人工接管必须是可执行流程，至少包含：

- 触发条件：高影响不确定性、重复失败、策略冲突、安全事件、审批要求或用户主动请求。
- 交接包：请求 ID、目标、已验证输入、数据分类、已执行步骤、工具结果、失败原因、剩余风险和建议动作。
- 控制权转移：停止自动工具调用，保存一致状态，明确人工责任人与可执行范围。
- 恢复条件：人工决定、修复验证、重新授权和需要时的重新评估。

禁止在等待人工接管期间继续执行有副作用动作。

## 12. 可观测性与审计

设计必须定义可用于重现、诊断和审计的信号，同时避免记录不必要的敏感内容：

- 贯穿输入、推理、工具、输出和人工接管的请求 ID、会话 ID 与 Trace ID。
- Agent ID、Design ID、Prompt 版本、模型版本、工具版本、策略版本和评测基线。
- 时延、吞吐、错误率、重试率、工具成功率、人工接管率、令牌与成本。
- 输入与输出的分类、校验结果、来源摘要和必要的脱敏哈希或引用。
- 工具调用、参数摘要、副作用、审批人、执行结果与结果验证。
- 拒绝、降级、策略命中、注入检测、越权尝试和安全事件。
- 日志、指标、追踪和审计记录的访问权限、保留期限、删除及告警规则。

设计必须说明如何关联一次用户请求与全部下游动作，以及如何在不暴露 Prompt 秘密或敏感数据的情况下重现问题。任何监控告警都必须有责任人和处理动作。

## 13. 评估方式、数据集与通过门槛

### 13.1 评估设计

每个 Agent 必须有与其风险匹配的离线评估、集成评估和发布后监控方案。评估设计必须记录：

- 评测目标及其 Requirement ID、Design ID、Test Case ID。
- 数据集名称、版本、来源、许可、时间范围、数据分类、去重和泄漏控制。
- 正常、边界、失败、对抗、注入、越权、敏感数据和人工接管样例。
- 基线方案、样本量、运行环境、模型与 Prompt 版本和可复现步骤。
- 质量、安全、可靠性、时延、成本和人工接管指标。
- 每项指标的计算方式、明确数值门槛、置信区间或允许误差。
- 失败样例归因、回归集加入规则和评估结果保存位置。

### 13.2 最低安全评估

无论业务指标如何，至少必须验证：

- Prompt 注入与间接注入不能绕过指令层级、工具权限和审批。
- 未授权数据不能被读取、写入、记忆、输出或发送给外部工具。
- Restricted 数据、密钥和隐藏指令不会出现在输出、日志或非批准 Memory 中。
- EXTERNAL 与 IRREVERSIBLE 动作不能在缺少逐次人工批准时执行。
- 重试、重复请求和部分失败不会造成重复副作用或不一致状态。
- 必须拒绝、降级或转人工的场景能够按设计触发。

### 13.3 设计评审通过门槛

Agent Design 只有同时满足以下条件，才能在开发前的设计评审中评为 PASS：

1. 本标准的必填设计项均有明确、可执行内容，且不存在未关闭的高风险问题。
2. 每项已批准需求均有 Design ID、Development Task ID 和 Test Case ID 的完整追踪链。
3. 质量、可靠性、时延、成本与安全指标均已定义预先批准的数值门槛、评测方法、数据集、责任人和执行阶段。
4. 开发前可完成的威胁建模、权限矩阵、工具副作用、审批边界、Memory 数据流和 Prompt 注入控制设计检查已经通过。
5. 设计期检查没有已知的关键安全违规、越权路径、敏感数据泄露路径或未经批准的不可逆动作；发现的问题已经关闭或阻断门禁。
6. 已执行的设计期实验或 PoC 证据绑定当前版本；依赖实现的评测已在 Development Plan 和 Test Plan 中固定版本、任务、测试案例与通过门槛。
7. 失败样例、剩余风险和限制已记录，并由有权限的责任人接受。

依赖具体实现才能执行的质量、可靠性、时延、成本和安全测试属于 DEVELOPMENT/TESTING 的验证任务，不得在代码存在前伪造为“已通过”。Design Gate 验证的是评估设计是否完整、设计期检查是否通过以及后续测试是否可执行，不是提前宣称实现质量达标。

不得用平均质量得分抵消关键安全失败，也不得在评测完成后降低门槛来制造通过结果。

## 14. 变更与重新评审

以下任一变化都必须更新 Agent Design、Traceability Matrix 和影响分析，并重新执行相应评估：

- Agent 职责、边界、自主程度或人工责任变化。
- 输入、输出、Prompt、模型或策略版本变化。
- 新增工具、扩大权限、改变副作用或审批方式。
- Memory 内容、读写规则、保留期限或隔离边界变化。
- 数据分类、供应商、运行地域或合规要求变化。
- 失败处理、回滚、监控或通过门槛变化。

影响架构、数据、接口、安全、成本、流程或长期维护的重大变化必须创建或更新 ADR。任何基线变化都会使原有 Agent 评审证据失去当前性，直至完成影响分析、回归评估和重新批准。

## 15. 评审检查

评审人必须确认：

- 职责、非职责、输入、输出、Prompt、工具、Memory、失败处理和评估方式完整。
- 边界、最小权限、数据分类、工具契约、副作用与审批可执行。
- Memory 的读取、写入、保留、删除、隔离和审计规则明确。
- Prompt 版本与注入防护、人工接管、可观测性和安全门槛均有验证方法。
