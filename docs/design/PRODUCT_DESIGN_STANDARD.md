# 产品设计标准（PRD）

## 1. 目的与适用范围

本标准规定 AI CTO 生成、评审和维护产品需求文档（PRD）时必须满足的最低要求。目标是让 PRD 中的每项需求都能被理解、追溯、评审和验收，并为后续 Architecture、Development Plan、Traceability Matrix 与 Test Case 提供稳定输入。

本标准适用于项目获准进入 DESIGN 后的 PRD 工作。PRD 应使用[产品需求文档模板](../../templates/PRD_TEMPLATE.md)，并与[项目立项门禁](../evaluation/PROJECT_APPROVAL_GATE.md)批准的范围和证据版本一致。PRD 完成或获批不等于授权开发；进入 DEVELOPMENT 仍须满足[阶段门禁检查清单](../evaluation/PHASE_GATE_CHECKLIST.md)中的 DESIGN → DEVELOPMENT 要求。

本文中的“必须”表示门禁要求，“应当”表示默认要求；偏离“应当”时必须记录理由、影响和批准人。

## 2. PRD 必需输入

AI CTO 在起草 PRD 前必须冻结以下输入。任何必需输入缺失时，应记录缺口并返回责任阶段补齐，不得补写成未经证实的事实。

| 输入 | 最低内容 | 校验要求 |
|---|---|---|
| 立项批准记录 | `APPROVED_FOR_DESIGN` 结果、批准范围、限制、批准人、日期和记录位置 | 批准对应当前项目、当前范围和当前证据版本，且没有未关闭条件 |
| Research 基线 | 文档路径、版本、日期、关键发现、反证、限制、Confidence 与来源 | 关键产品判断可追溯到可核验来源 |
| Evaluation 基线 | 文档路径、版本、日期、价值、范围、成功标准、资源、可行性、优先级与建议 | 使用当前 Research 证据；与批准范围一致 |
| 用户与问题证据 | 用户角色、痛点、场景及其访谈、数据、观察或其他来源 | 能说明“为谁解决什么问题”，并区分事实与假设 |
| 约束与风险 | 合规、安全、隐私、数据、成本、时间、技术、运营、许可证、红线和剩余风险 | 责任人、缓解措施、接受者和适用范围明确 |
| 决策与历史资产 | 相关 ADR、历史项目、可复用资产、Build vs Buy 结论 | 不与已接受决策冲突；引用版本可定位 |

若 PRD 起草期间出现足以推翻价值、范围或关键可行性结论的新证据，必须暂停基线确认，返回 EVALUATION 或 RESEARCH 复核，不得仅在 PRD 中局部修补。

## 3. 文档信息与版本基线

每份 PRD 必须在“文档信息”中记录：

- 项目名称与项目路径；
- PRD 编号和文档版本；
- 状态：`Draft`、`In Review`、`Approved` 或 `Superseded`；
- 文档负责人、评审人和批准人；
- 关联立项批准记录；
- Research、Evaluation、风险分析及相关 ADR 的路径、版本和日期；
- 当前范围基线、最后更新日期和变更记录位置。

版本使用 `v主版本.次版本.修订版本`：

- 首次批准前使用 `v0.x.y`，首次批准形成 `v1.0.0` 基线；
- 目标用户、问题、范围、核心需求、成功指标或验收口径发生实质变化时提升主版本；
- 在已批准目标内新增、删除或改变需求行为时提升次版本；
- 仅修正文字、格式或不改变含义的引用时提升修订版本。

批准记录必须指向一个确定版本。对旧版本的批准不得自动继承到新版本。

## 4. 需求标识与可追溯性

1. 每项功能需求必须使用稳定且唯一的 `Requirement ID`，格式为 `REQ-<领域>-<三位序号>`，例如 `REQ-AUTH-001`。
2. ID 不得包含优先级、版本号或实现顺序，因为这些属性可以变化；已删除 ID 不得复用。
3. 一个 ID 只表达一个可独立验收的行为或结果。含多个独立行为的需求必须拆分。
4. 场景、痛点、指标和验收标准应分别使用 `SCN-`、`PAIN-`、`MET-` 和 `AC-<Requirement ID>-<序号>` 标识。
5. 每项核心功能必须至少追溯到一个用户痛点或约束、一个使用场景、一个成功指标或明确的门禁理由，以及至少一项验收标准。
6. 进入后续设计时，Requirement ID 必须保持不变，并继续建立 Requirement → Design → Development Task → Test Case 的双向追溯关系。

需求拆分或合并时，应保留原 ID 的状态，并在变更记录中列出替代关系，不得通过改名掩盖范围变化。

## 5. PRD 的 10 项必需内容

以下十项全部必填。章节存在但内容为空、只有标题、使用含糊措辞或无法执行验收，均视为未完成。

| 序号 | 必需项 | 必须包含 | 可验收检查 |
|---|---|---|---|
| 1 | 产品背景 | 问题起因、当前状态、为什么现在处理、预期产品结果、与立项结论的关系及证据引用 | 读者能从证据回答“为什么做、为什么现在做”，且背景没有把方案假设写成既定事实 |
| 2 | 用户角色 | 角色 ID、角色定义、目标、职责或权限、使用环境、与其他角色的差异、明确排除的非目标用户 | 每个核心场景有唯一或明确协作的主体；角色边界无重叠歧义 |
| 3 | 用户痛点 | Pain ID、对应角色、当前行为、问题触发条件、频率或严重度、影响、证据与 Confidence | 每个痛点可追溯到证据或被明确标记为假设；至少一个核心需求回应每个纳入范围的痛点 |
| 4 | 使用场景 | Scenario ID、参与角色、触发器、前置条件、主路径、异常或替代路径、结束状态和期望结果 | 场景能够从入口执行到可观察结果；核心需求均被至少一个场景覆盖 |
| 5 | 核心功能 | Requirement ID、行为或结果、用户价值、优先级、前置与结束状态、依赖、关联场景和验收标准 | 每项均属于当前批准范围、必须随本基线交付且可独立验收；不存在“尽量提供”或“有时间再做”等可选表述 |
| 6 | 非核心功能 | Requirement ID、候选能力、用户价值、不纳入当前基线的原因、纳入条件、复核触发器或目标版本 | 每项明确位于当前范围外，不参与当前发布验收；纳入条件可被客观判断，不得伪装成隐含承诺 |
| 7 | 用户流程 | 入口、步骤编号、角色交接、决策分支、异常与恢复路径、退出状态，以及步骤到 Requirement ID 的映射 | 主流程、关键异常和权限边界均可走查；不存在没有流程位置的核心功能或没有需求支持的关键步骤 |
| 8 | 成功指标 | Metric ID、指标定义或公式、基线、目标值、时间窗口、数据来源、统计口径、责任人、护栏或停止阈值 | 指标能在指定时间和数据源上重复计算；目标包含数值、单位和期限，不能只写“提升体验” |
| 9 | 限制条件 | 限制类型、来源、适用范围、影响、责任人、验证方式、例外批准方式；覆盖适用的合规、安全、隐私、数据、成本、周期、技术与运营限制 | 每项限制能定位到来源并映射到受影响需求或验收项；关键限制没有被降格为无主假设 |
| 10 | 验收标准 | AC ID、关联 Requirement ID、前置条件、测试数据、操作或事件、预期结果、量化阈值、通过/失败判定 | 每项核心需求至少有一项可重复执行的测试；覆盖正常、关键异常、边界与权限场景，结果只有明确的通过或失败 |

## 6. 核心与非核心的明确边界

“核心”表示当前已批准 PRD 基线中承诺交付、参与发布验收的功能；“非核心”表示有价值但未被当前基线承诺、不参与当前发布验收的候选功能。两者是范围承诺，不是主观形容词。

- 每项功能必须且只能归入“核心功能”或“非核心功能”，不得同时出现。
- 当前范围内的功能需求必须列为核心；非核心功能必须同时列入范围外或明确的候选清单。
- 核心功能应聚焦完成目标所需的最小闭环，通常为 P0 或 P1。把 P2 或 P3 设为核心时，必须记录理由、范围影响和批准人。
- P0 不能被列为非核心；出现这种组合时说明范围或优先级至少一项错误，必须在评审前纠正。
- 非核心功能不能使用“最好支持”“尽可能”“视情况”“后续优化”等无法判定承诺的措辞，必须写明客观纳入条件。
- 优先级的判定遵循[需求优先级模型](./REQUIREMENT_PRIORITY_MODEL.md)，但优先级不能替代范围批准，也不能直接充当实施顺序。

## 7. 事实、假设与决策

PRD 中影响问题判断、范围、优先级、指标或验收的陈述必须归为以下类型：

| 类型 | 记录要求 | 使用限制 |
|---|---|---|
| 事实 | 来源位置、版本或发布日期、访问或采集日期、适用范围 | 无可核验来源时不得标记为事实；过期或冲突证据必须说明影响 |
| 假设 | 假设内容、依据、Confidence、验证方法、责任人、完成日期、证伪后的影响 | 未验证假设不得改写为事实；影响核心范围或验收的关键假设未关闭时，PRD 不得标记为 `Approved` |
| 决策 | 决策内容、备选方案、理由、影响、批准人、日期及记录位置 | 决策不得用来绕过证据、红线或阶段门禁；重大决策按项目规则创建 ADR |

未知信息应作为假设或证据缺口记录。AI CTO 可以提出假设和建议，但不得虚构来源、代替用户批准，或用高 Confidence 掩盖证据缺失。

## 8. 范围与非范围

PRD 必须分别维护“范围内”和“范围外”：

- 范围内写明本版本解决的角色、场景、功能、渠道、数据边界和适用环境；
- 范围外写明相关但不交付的能力、角色、场景、集成和环境，并说明排除原因；
- 每项范围声明必须能映射到 Requirement ID、Scenario ID 或明确约束；
- 范围内与范围外不得重叠；“未提及”不代表默认纳入；
- 任何范围变更都必须经过影响分析、版本更新和明确批准。

非功能需求虽然不计入上述十个产品内容项中的功能分类，仍是 PRD 和 DESIGN → DEVELOPMENT 门禁的必需输入。适用的性能、可靠性、安全、隐私、可访问性、兼容性、可观测性与运维要求必须有 ID、阈值和验收方法。

## 9. 成功指标规则

每个成功指标必须同时满足：

1. **定义稳定**：明确分子、分母、去重、时间区间和排除条件；
2. **有基线**：记录当前值与采集日期；尚无基线时，先完成测量，不得用主观描述替代；
3. **目标量化**：包含目标数值、单位、目标日期和适用人群或环境；
4. **数据可得**：指定数据源、采集方式、数据质量校验和责任人；
5. **有判定窗口**：明确观察周期和达到目标的判定方式；
6. **有护栏**：说明不可恶化的质量、安全、成本或用户结果，以及停止或回滚阈值。

产出数量、上线日期等交付指标不能单独证明产品成功；至少一个主指标必须反映目标用户结果或已批准的业务结果。

## 10. 验收标准规则

验收标准可以使用“前置条件—动作—预期结果”或 Given/When/Then 结构，但必须满足以下要求：

- 一个 AC 只验证一个清晰结果，并关联一个 Requirement ID；
- 写明测试环境、角色和权限、前置状态、测试数据、动作、期望输出与阈值；
- 涉及时间、数量、准确率、可用性或容量时给出单位、统计口径和允许误差；
- 覆盖正常路径，以及与风险相称的异常、边界、重复、并发、权限或恢复路径；
- 禁止使用“正常运行”“体验良好”“基本完成”“尽量快”等无法复测的判定；
- 验收失败必须能定位到需求，不得用整体演示替代逐项测试。

非核心功能在被正式纳入范围前可以只记录纳入条件；一旦转为核心，必须补齐验收标准并重新评审基线。

## 11. 评审、批准与变更规则

### 11.1 评审

PRD 至少经过以下视角评审：

- 产品或用户代表：确认角色、问题、价值、范围、核心/非核心和成功指标；
- 设计与架构责任人：确认场景、流程、约束、依赖和设计可追溯性；
- 开发与测试责任人：确认需求可实现、验收可执行、测试数据与环境可获得；
- 安全、合规、数据或运营责任人：在对应限制适用时确认风险与控制要求。

每条评审意见必须有负责人、处理结论和证据。阻断意见未关闭时不得批准。批准记录必须包含批准人、日期、版本、范围和记录位置；沉默、口头推断或对旧版本的批准均不生效。

### 11.2 变更

`Approved` 后的每项变更都必须记录：变更编号、日期、提出人、原因、受影响的 Requirement/Scenario/Metric/AC ID、范围与风险影响、关联文档、旧值、新值、决定、批准人和新版本。

以下变更属于实质变更，必须完成影响分析并重新评审、批准和基线化：

- 改变目标用户、痛点、核心场景或产品目标；
- 将功能移入或移出范围，或改变核心/非核心分类；
- 新增、删除、合并、拆分或改变需求行为；
- 改变 P0/P1 结论、成功指标目标或验收判定；
- 改变合规、安全、数据、成本、周期等关键限制；
- 使 Architecture、Development Plan、测试、风险或 ADR 失效的变化。

纯文字和格式修正可以走修订版本，但必须确认没有改变语义。禁止静默修改已批准 PRD。

## 12. PRD 完成定义

只有同时满足以下条件，PRD 才可标记为 `Approved`：

- [ ] 六类必需输入均有当前且可定位的版本，批准范围没有未关闭条件；
- [ ] 文档信息、状态、负责人、评审人、批准人与版本基线完整；
- [ ] 本标准规定的十项必需内容全部通过可验收检查；
- [ ] 每项需求有稳定 ID，核心需求到痛点/约束、场景、指标和 AC 的追溯无孤儿项；
- [ ] 事实、假设和决策已区分，影响核心范围或验收的关键假设均已关闭；
- [ ] 范围内外互斥，核心/非核心分类唯一，非核心没有隐含交付承诺；
- [ ] 优先级按 P0–P3 模型评审，P0 均通过严格门槛；
- [ ] 成功指标有基线、数值目标、期限、口径、数据源、责任人和护栏；
- [ ] 每项核心功能和适用的非功能需求都有可重复执行、结果明确的验收标准；
- [ ] 评审阻断项已关闭，剩余风险已由有权限的人接受；
- [ ] 用户明确批准当前范围和当前 PRD 版本，变更记录完整；
- [ ] PRD 与 Research、Evaluation、相关 ADR 及阶段门禁之间没有未解决冲突。

任一项未满足时，状态只能保持 `Draft` 或 `In Review`。PRD 通过本完成定义后，仍须连同 Architecture、Database/Agent Design、Development Plan、Traceability Matrix、验收测试、风险与回滚方案一起接受 DESIGN → DEVELOPMENT 门禁评审。
