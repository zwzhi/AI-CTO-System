# 架构设计标准

## 1. 目的与适用范围

本标准规定 Architecture 在进入开发授权评审前必须提供的内容、证据和完成条件。它适用于单体、分层、服务化、事件驱动、客户端、嵌入式、数据处理及其他形态的系统，不预设部署平台、编程语言、通信方式或架构风格。

架构文档应使用[系统架构设计模板](../../templates/ARCHITECTURE_TEMPLATE.md)，并遵守[文档关联规则](../protocol/DOCUMENT_RELATIONSHIP.md)和[阶段门禁检查清单](../evaluation/PHASE_GATE_CHECKLIST.md)。产品目标、范围、需求与验收标准以 PRD 为权威来源；Architecture 只引用并落实，不复制形成第二事实来源。

本文中的“必须”是开发授权前的硬性要求；“应”表示除非有经评审的理由，否则需要满足；“可以”表示可按项目特点选择。所有结论必须可由文档、图示、评审记录或验证计划核验。不得以实现代码代替架构说明。

## 2. 文档信息与版本基线

Architecture 必须在首页记录以下基线信息：

| 项目 | 必须记录的内容 |
|---|---|
| 文档身份 | 项目名称、Architecture 标识、文档版本、状态、存放路径 |
| 范围基线 | 获准进入 DESIGN 的范围及其门禁记录路径和版本 |
| PRD 基线 | PRD 路径，以及明确的版本号或提交标识；不得只写“最新版本” |
| 关联设计 | 适用的 Database Design、Agent Design、接口契约及其版本 |
| 决策基线 | 相关 ADR 编号、路径和状态 |
| 责任信息 | 作者、责任人、评审人、确认人、最后更新日期 |

评审确认后，文档版本、PRD 基线、接口基线和 ADR 集合共同构成架构版本基线。任何影响范围、组件边界、接口、数据、安全、非功能目标、部署或恢复方式的变更，都必须执行影响分析、更新版本和追溯关系并重新评审；属于重大决策的变更还必须按 ADR 规则处理。被替代版本应保留其状态和后继版本引用，不得静默覆盖历史结论。

## 3. PRD 与需求追溯

1. 每个架构组件、关键接口、关键数据流和重大设计决策必须拥有稳定且唯一的 Design ID。
2. 每个 Design ID 必须引用一个或多个 Requirement ID 或非功能需求 ID；若设计用于满足已记录的约束，也必须引用该约束的稳定标识或具体位置。
3. 文档必须包含 Design ID 与 Requirement ID 对照表，至少记录：Design ID、设计对象、Requirement ID、非功能需求 ID、相关 ADR、验证证据或验证计划。
4. 必须执行正向与反向检查：所有已批准且影响架构的需求均有设计落点，所有设计项均有需求、约束或经批准决策作为来源，不存在未解释的孤儿项。
5. Traceability Matrix 是端到端关系的权威索引；Architecture 保留具体设计内容和本地映射。任一需求或设计变更后，两处必须同步更新并重新检查孤儿项。
6. Architecture 若需要改变产品目标、范围或验收标准，必须先更新并重新确认 PRD，不得在架构文档中单方面扩大范围。

## 4. 九项必备架构内容与验收规则

以下九项均必须有独立、可定位的章节。章节不得仅有标题；即使系统很小，也必须给出与其复杂度相称的说明和证据。

### 4.1 系统边界

必须说明系统解决的职责、明确不承担的职责、用户或调用方、外部系统、物理或组织边界、信任边界、数据责任边界以及边界内外的责任人。外部托管能力也属于系统依赖，不能因不由项目实现而从边界中省略。

验收时应能从文字和系统上下文图一致回答：系统包含什么、排除什么、与谁交互、数据和控制权在何处跨越边界、每个边界由谁负责。范围必须与 PRD 基线一致，所有差异均有关闭记录。

### 4.2 模块划分

每个模块必须记录 Design ID、职责、所有者、输入、输出、持有的状态、对外能力、依赖、关联需求和非功能约束。模块边界应体现职责内聚和依赖方向；名称必须在正文、图示、接口清单和追溯表中一致。

验收时，每项关键职责只能有明确的主要归属，模块间没有未说明的职责重叠或循环依赖；每个模块均可追溯到需求或约束，并能在不阅读实现代码的情况下理解其用途、使用方式和依赖。

### 4.3 数据流

必须覆盖关键业务流和关键运维流，记录数据来源、接收方、处理或转换、持久化点、跨边界传输、同步或异步语义、敏感级别、完整性要求、失败分支和最终去向。涉及 Database Design 时，应引用其版本和实体或数据元素标识，不在 Architecture 中重复字段定义。

验收时，每条关键流程都能从入口追踪到出口，方向和顺序明确；所有跨信任边界、数据落点、异常路径及一致性要求均可识别，正文与数据流图不存在冲突。

### 4.4 服务关系

“服务”包括独立部署单元、进程、模块能力以及外部系统，不要求项目采用服务化架构。必须说明调用或消息关系、提供方、消费方、接口 ID、交互目的、契约位置与版本、数据语义、依赖方向、可用性责任、兼容策略、错误语义以及超时、重试、幂等或重复处理要求中的适用项。

必须维护依赖清单，至少包含依赖 ID、内部或外部属性、用途、所有者、版本或约束、关键程度、失败影响、替代或降级方式和验证方法。

验收时，关系图中的每条连线都能映射到接口或依赖记录；每个接口都有唯一提供方、已知消费方和责任人；不存在未声明的关键依赖、方向不明的调用或无兼容方案的契约变化。

### 4.5 技术选型

每项影响架构、数据、接口、安全、成本、流程或长期维护的选型，必须记录要解决的问题、约束、候选方案、比较标准、证据、选择理由、已知后果、退出条件和替代路径。比较维度应覆盖与项目相关的能力、成熟度、可维护性、兼容性、许可、供应风险、团队能力、成本和生命周期。

验收时，选择能回溯到需求和约束，未把个人偏好写成结论；重大选型已有 Accepted ADR，正文引用而不复制 ADR 的完整历史。标准不规定任何默认语言、框架、数据库、云服务或架构模式。

### 4.6 扩展方案

必须说明增长驱动因素、可独立扩展的单元、容量或并发维度、状态放置对扩展的影响、已知瓶颈、扩展触发信号、扩展步骤、兼容方式、成本边界以及缩容或退出方式。扩展既包括规模增长，也包括新增能力、接入方和区域等演进。

验收时，扩展方案与容量假设和性能目标相互一致；至少对预期增长场景给出可验证的触发条件、受影响组件、依赖和风险，不以“可水平扩展”等无法核验的结论代替设计。

### 4.7 性能考虑

必须从 PRD 的非功能需求或经批准假设出发，记录工作负载模型、峰值与常态特征、关键路径、延迟或处理时限、吞吐、并发、资源与容量预算、争用点、性能退化条件、测量口径以及验证环境和方法。目标必须包含数值、单位、统计口径、时间窗口和适用场景；尚无证据的数值必须标记为假设并指定验证责任人。

验收时，每个关键性能目标都有非功能需求 ID、对应组件、可观测信号、通过阈值和验证计划；容量估算可复核，关键路径没有未分析的性能预算缺口。

### 4.8 安全考虑

必须识别资产、数据分类、信任边界、威胁或滥用场景，并说明身份认证、授权、最小权限、机密信息管理、传输与存储保护、隐私、审计、依赖与供应链安全、配置安全和安全事件处置中的适用控制。每项控制必须注明保护对象、责任主体和验证方式。

验收时，威胁或合规要求能映射到控制和验证证据；跨信任边界的访问均有明确身份、权限和审计策略；敏感数据不会因日志、诊断或备份设计被无意扩大暴露范围；高风险残余项已有明确接受者。

### 4.9 部署方案

必须说明环境划分、逻辑部署拓扑、制品和配置边界、外部运行依赖、网络或进程边界、状态位置、部署顺序、健康判定、发布策略、数据变更协调、配置与机密信息注入、回滚路径、恢复责任和环境间差异。方案应表达逻辑要求，不强制具体平台。

验收时，评审者能依据文档确定各组件运行位置、启动和依赖顺序、上线与回滚的判定条件，以及状态和配置的保护方式；部署图、模块图和数据流在组件名称、边界和依赖上保持一致。

## 5. 横切设计要求

### 5.1 接口与依赖

接口契约至少必须定义接口 ID、提供方、消费方、用途、输入输出语义、版本与兼容规则、认证授权要求、错误分类、时限、容量约束、幂等或去重语义、可观测信号和责任人。接口可以是调用、事件、文件、人工交接或其他交换方式；本标准不规定协议。

关键依赖必须按其不可用、变慢、返回错误数据和版本不兼容等情形分析影响。外部依赖还必须记录服务承诺或已知限制、变更通知渠道、替代路径和退出风险。

### 5.2 非功能需求

Architecture 必须逐项落实适用的性能、容量、可用性、可恢复性、安全、隐私、兼容性、可维护性、可观测性、成本或资源约束。每项记录至少包含非功能需求 ID、场景、度量、目标与容差、测量窗口、适用环境、设计响应、验证方法和责任人。无法量化的要求必须改写成可判定场景和通过条件；不适用项应给出范围证据和评审结论。

### 5.3 可观测性

每个关键模块、接口、依赖和关键流程必须定义健康信号。文档应说明需要的日志、指标、链路或等价关联信息、业务事件和审计记录，及其采集位置、关联标识、保留要求、敏感信息处理、质量检查和责任人。

关键服务水平指标必须关联目标、告警阈值、观察窗口、通知对象和处置入口。验收证据应证明团队能够从信号发现故障、定位影响范围、判断降级是否生效并确认恢复，而不是只列出工具名称。

### 5.4 故障、降级与恢复

必须按关键场景记录故障 ID、触发条件、受影响需求和组件、检测信号、隔离范围、数据一致性影响、降级行为、用户可见结果、恢复步骤、回滚触发条件、恢复点目标、恢复时间目标、责任人和演练或验证方法。

降级必须明确保留与放弃的能力、安全边界和退出条件；重试、冗余、补偿、切换等机制只在满足失败语义且不会放大故障时采用。恢复后必须验证服务健康、数据完整性、积压处理和监控状态。不能自动恢复的场景必须有可执行的人工入口和升级路径。

### 5.5 ADR

涉及架构、数据、接口、安全、成本、开发流程或长期维护的重大决策必须创建唯一编号的 ADR。Architecture 记录 ADR 编号、路径、状态、所影响的 Design ID 和基线版本。开发授权所依赖的重大决策必须处于 Accepted 状态；Proposed 或存在互相冲突的有效 ADR 均视为未关闭项。

决策变化时不得改写旧 ADR，应新建 ADR、建立替代关系并同步更新 Architecture。若评审认定没有需要单独建 ADR 的重大决策，也应在架构评审记录中保留适用性结论和依据。

### 5.6 假设与风险

每项架构假设必须有假设 ID、依据、可信度、影响范围、验证方法、验证责任人、验证期限和失效后的处理。已验证或失效的假设保留状态和证据，不能从历史记录中删除。

每项风险必须有风险 ID、触发信号、发生可能性、影响、受影响需求或 Design ID、预防或缓解措施、应急方案、责任人、剩余风险和接受者。会阻断开发的风险必须在授权前关闭；可接受的剩余风险必须有明确接受记录。

## 6. 图示最低要求

Architecture 至少必须表达以下四个视图：

1. 系统上下文视图：系统边界、用户或调用方、外部系统、主要交互和信任边界。
2. 模块与关系视图：模块或部署单元、职责边界、接口和依赖方向。
3. 关键数据流视图：关键场景的数据来源、处理、存储、跨界传输和失败分支。
4. 部署视图：环境、逻辑运行节点、组件落位、网络或进程边界、状态和外部运行依赖。

一个图可以承载多个视图，但必须保持范围和层级清晰。每个图都必须有标题、用途、范围、版本、图例、方向、边界和与正文一致的 Design ID；正文必须引用图，图中的每个关键节点和连线必须能回到对应章节。图源应与文档共同版本化，并保证评审者无需特定厂商工具也能查看导出结果。仅有无法检索的截图、没有图例的线框或与正文名称不一致的图不通过验收。

## 7. 架构完成定义

Architecture 只有同时满足以下条件才可标记为“已确认”：

- 九项必备架构内容全部存在并通过各自验收，内容与项目复杂度相称。
- PRD、范围门禁、相关设计、接口和 ADR 的路径及明确版本已形成基线。
- 所有架构相关 Requirement ID 与非功能需求均有 Design ID 落点，正向和反向孤儿项检查通过。
- 接口与依赖清单完整，所有关键关系都有契约、责任人、失败影响和验证方法。
- 非功能目标可度量，可观测性足以发现、定位和确认恢复，性能与容量假设可验证。
- 故障、降级、恢复、回滚和部署方案具备明确触发条件、责任人和验证方式。
- 重大决策均有 Accepted ADR；假设、风险和剩余风险接受记录完整，不存在未关闭的开发阻断项。
- 四类最低图示与正文、追溯表和版本基线一致。
- 指定评审人已完成一致性、安全、运维和可实施性评审，评审问题均已关闭并留下确认记录。

架构文档完成不等于自动授权进入 DEVELOPMENT。最终转换仍必须满足 Design Approval Gate 和阶段门禁的全部要求，并由用户确认当前文档版本。
