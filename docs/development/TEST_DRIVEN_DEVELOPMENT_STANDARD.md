# 测试驱动开发标准

## 1. 目的与适用范围

本标准定义开发阶段必须遵循的测试驱动开发顺序、证据、追踪和例外控制。它适用于新功能、缺陷修复、重构、配置行为变化、接口变化、数据变化和安全控制变化，并保持对语言、测试框架、运行环境和交付平台中立。

测试活动必须依据当前批准的 Requirement、Architecture、Design 和 Development Plan。Test Case 与开发结果按 [Traceability Matrix 模板](../design/TRACEABILITY_MATRIX_TEMPLATE.md) 维护端到端追踪；开发授权遵循 [Design Approval Gate](../design/DESIGN_APPROVAL_GATE.md)。

## 2. 不可颠倒的开发顺序

每个可交付行为必须严格遵循：

**Requirement → Test Case → Implementation → Validation**

1. **Requirement**：确认当前 Requirement ID、验收标准、Design ID、Task ID、限制与风险均已批准且没有歧义。
2. **Test Case**：在编写实现之前定义能够判定需求是否满足的 Test Case，并完成适用的评审。
3. **Implementation**：只有目标测试完成定义并进入 RED 后，才允许编写使其通过的最小实现。
4. **Validation**：实现完成后执行目标测试和必要测试集，核对验收、回归、安全与非功能结果，并保存证据。

测试用例必须提前定义。禁止先完成代码，再新增、改写或挑选测试来为既有实现提供通过结果。若 Requirement、Design 或验收标准变化，必须先更新并重新批准权威源文档和 Test Case，再开始受影响实现。

## 3. 实现前 Test Case 定义

每个 Test Case 在实现开始前必须至少明确：

- 稳定 Test Case ID，以及关联的 Requirement ID、Design ID 和 Development Task ID；
- 被验证的单一行为或风险及其对应验收标准；
- 测试层级、环境、前置条件、受控测试数据和依赖状态；
- 可重复执行的步骤或输入；
- 可观察的预期结果、允许误差和明确通过条件；
- 失败时应观察到的结果，并能区分缺少实现、真实缺陷与环境故障；
- 证据保存位置、责任人，以及适用的清理、隔离和恢复措施。

一个 Task 包含多个独立行为或风险时，应拆分为可独立判定的 Test Case。测试定义不得依赖尚未实现的内部细节来替代需求行为，也不得使用无法判定的“运行正常”“无异常”等表述。

## 4. RED → GREEN → REFACTOR

每个最小行为增量都必须完整执行一次 RED → GREEN → REFACTOR；不得把多个行为全部实现后再批量补做循环。

### 4.1 RED：因缺少实现而按预期失败

1. 只添加或启用当前最小行为的测试，不添加使其通过的产品实现。
2. 在受控环境执行测试，确认它因目标实现缺失或目标缺陷仍存在而按照 Test Case 的预期方式失败。
3. 失败必须发生在目标断言处，实际结果与预期差异应能证明测试具有判别力。语法错误、测试本身错误、环境不可用、依赖故障、权限配置错误、超时噪声或人为强制失败都不是有效 RED。
4. 保存测试版本、执行环境、步骤或命令、时间、失败输出、失败原因分析和 Test Case ID，并关联对应 Task。
5. 在 RED 证据有效前不得开始目标实现。

“已有测试通过”不能冒充 RED。若新增测试在实现前已经通过，必须查明行为是否早已存在、断言是否过弱或范围是否错误；修正需求映射或测试后重新执行。不得把一次通过结果描述为预期失败，也不得仅凭口头推断省略 RED。

### 4.2 GREEN：只做使目标测试通过的最小实现

1. 仅编写使当前 RED 测试按预期通过的最小实现，不提前加入未经测试驱动的扩展、优化或顺带重构。
2. 先运行目标测试，确认它由预期失败转为通过；随后运行与修改直接相关的回归测试，确认没有破坏已批准行为。
3. 若测试仍失败，继续在当前最小范围内定位并修改；不得删除测试、放宽断言、改写预期结果或跳过失败用例来制造 GREEN。
4. 保存实现 Commit、测试版本、环境、通过结果及与 RED 证据的对应关系。

GREEN 只证明当前最小行为满足测试，不自动证明整个 Task、Requirement 或发布范围已经完成。

### 4.3 REFACTOR：全过程保持全绿

1. 仅在目标测试及相关回归测试为绿时开始重构。
2. 重构只能改善结构、可读性、重复、依赖边界或可维护性，不得悄然改变已批准的外部行为。
3. 以小步修改持续运行相关测试；重构开始前、关键步骤后和结束时都必须保持目标测试及必要回归测试全绿。
4. 一旦需要改变外部行为或测试预期，应停止当前重构，回到 Requirement 与 Test Case，启动新的 RED → GREEN → REFACTOR 循环。
5. 保存重构 Commit、连续测试结果和影响范围证据。

重构期间出现失败时，当前状态不是合格的 REFACTOR；必须恢复到最近全绿基线或修复重构引入的问题，并重新取得完整全绿证据。

## 5. Validation：完成级验证

完成级 Validation 与 GREEN 不同。GREEN 针对一个最小行为；Validation 必须基于当前最终 Commit 和批准基线执行该 Task 在 DEVELOPMENT 阶段规定的完整测试集合，并确认：

- 所有关联的开发级必跑 Test Case 均已执行且满足预定义通过条件；Phase 6 Test Case 可以保持 `NOT_RUN`，但必须完整、可执行并与当前基线一致；
- Requirement 验收标准和 Design 约束均有直接证据；
- 目标环境、依赖、数据和配置与证据记录一致；
- 正常、边界、失败、安全和回归场景均按适用性覆盖；
- 计划在 DEVELOPMENT 验证的非功能要求及权限、恢复、兼容或迁移风险已通过；计划在 Phase 6 执行的部分已完成用例、环境、数据、责任人和判定标准准备；
- 结果可由其他评审人复核，失败或阻塞没有被隐藏；
- 最终 Commit SHA、Test Case ID、Task ID、Requirement ID 和 Design ID 在 Traceability Matrix 中一致。

任何开发级必跑测试失败、未运行、被跳过、证据过期或执行版本与待评审 Commit 不一致时，Validation 不成立，任务不得声明完成。Phase 6 用例的合规 `NOT_RUN` 不阻断 Task Validation，但用例缺失、不可执行、版本不一致或错误标记为 PASS 会阻断 Development Approval Gate。

## 6. 必要覆盖

测试集合必须根据 Requirement 和风险选择层级，不以固定数量或单一覆盖率指标代替行为验证。至少评估并覆盖：

- **正常场景**：主要用户或系统路径及明确输出；
- **边界场景**：最小值、最大值、空值、长度、容量、时间和状态边界；
- **失败场景**：无效输入、依赖失败、部分成功、中断、重试、恢复和错误传播；
- **安全场景**：身份、权限、越权、输入攻击、敏感数据、审计、秘密和副作用控制；
- **回归场景**：本次修改可能影响的既有需求、接口、数据、性能和历史缺陷；
- **非功能场景**：适用的性能、容量、并发、可靠性、兼容性、可观测性和恢复目标。

若某类场景经事实判断不适用，必须记录判断依据、评审人和所依据的当前 Requirement / Design；不得通过不说明理由的省略降低覆盖。

## 7. Bug 修复流程

Bug 修复必须先建立能够稳定复现缺陷的 Test Case，并执行取得 RED：测试应在未修复的受影响基线上因该缺陷按预期失败。随后才允许编写最小修复取得 GREEN，并在 REFACTOR 期间保持相关测试全绿。

修复完成后必须执行缺陷复现测试、受影响功能测试、安全与边界测试以及必要回归测试。不得先修改代码再写复现测试，不得把缺陷当前行为写成新的正确预期，也不得删除历史回归用例来接受复发。无法稳定复现时，Task Status 必须为 `BLOCKED`，并把收集可观测证据和改进复现条件记录为 Next Action；不能以猜测性修复替代 RED。

## 8. 证据与追踪

每次循环必须形成可审计记录：

| 阶段 | 必要证据 | 追踪要求 |
|---|---|---|
| Requirement | 当前批准版本、验收标准和风险 | Requirement ID → Design ID → Task ID |
| Test Case 定义 | Test Case 内容、评审记录和实现前时间顺序 | Test Case ID → Requirement ID / Design ID / Task ID |
| RED | 仅测试变化的版本、按预期失败的输出、环境与原因分析 | Test Case ID → RED Commit 或等价不可变差异证据 → Task ID |
| GREEN | 最小实现 Commit、目标与相关回归测试通过结果 | Commit SHA → Task ID / Requirement ID / Design ID / Test Case ID |
| REFACTOR | 重构 Commit、修改前后及过程中的全绿证据 | Commit SHA → Task ID / Test Case ID |
| Validation | 最终基线、完整测试结果、评审与证据位置 | 五层追踪链更新为最终 Commit SHA |

每个重要测试或实现修改必须形成 Git 记录。Commit 必须引用 Task ID；Test Case 必须映射到验证它的 Requirement、Design、Task 和相关 Commit。若合并策略改变 Commit SHA，应保留原循环证据并建立到最终 SHA 的不可歧义映射。

证据必须来自实际执行，不得伪造、回填时间顺序、重用不对应当前 Commit 的结果或以自动生成摘要替代原始可复核记录。

## 9. 无法执行 RED 时的处理

RED → GREEN 的顺序没有代码实现例外。缺少测试框架、外部环境不可用、进度压力、实现简单、历史代码无测试、测试编写困难、已有测试通过或用户口头同意，都不能授权先编写目标实现再补测试。

无法取得有效 RED 时，Development Task 必须标记为 `BLOCKED`，记录 Requirement、Test Case、预期失败、事实原因、风险、责任人、解除条件和 Next Action。团队可以先建设测试支撑、准备隔离环境、缩小可验证切片或改用不会产生破坏性副作用的测试方法；这些动作仍不得包含目标行为实现。

正在发生的安全或生产事故可以按获批事件响应流程执行隔离、降级、撤销凭据、关闭入口或回退版本等遏制动作，但这些动作不构成该 Development Task 的实现、GREEN 或完成证据，也不得直接作为目标实现进入开发基线。事故受控后，正式修复必须从未修复的隔离基线开始，先取得缺陷复现 RED，再编写最小修复。若无法恢复可验证的未修复基线，任务继续阻塞并升级决策，不允许用事后补测替代 RED。

任何跳过、伪造或事后重建 RED 的变更都必须被 Code Review 判为 `CHANGES_REQUIRED`；无法在当前批准范围内恢复正确顺序时，应丢弃目标实现差异并重新开始，或将方案退回 Design / Evaluation。用户可以决定停止、重新设计或接受项目暂不推进，但不能把“代码完成后再补测试”批准为符合本标准。

## 10. 明确禁止

- 在 Test Case 定义和有效 RED 之前编写目标实现；
- 代码完成后补测试，或依据既有实现反向降低验收标准；
- 用已有测试通过、测试加载失败、环境故障、随机失败或人为强制失败冒充 RED；
- 在 GREEN 中加入当前测试未要求的功能、优化或重构；
- 删除、跳过、注释、弱化测试或修改正确预期来消除失败；
- 在 REFACTOR 中改变外部行为而不启动新循环，或在非全绿状态继续重构；
- 只执行目标测试而省略必要的安全、边界、失败和回归验证；
- 使用与待交付 Commit、环境或数据不一致的旧测试证据；
- 伪造测试结果、回填顺序或把未执行、阻塞状态描述为通过；
- 把事件响应遏制、环境限制或任何其他偏离描述为符合 TDD 的代码实现例外。

## 11. 完成条件

一个 Task 只有在其所有行为均完成 Requirement → Test Case → Implementation → Validation，且每个最小增量具有有效 RED、最小 GREEN、持续全绿 REFACTOR、最终 Validation、代码评审和完整五层追踪时才可完成。任何顺序颠倒、必要证据缺失、未关闭测试失败、未解决 `BLOCKED` 或未处置偏离都会阻断完成。
