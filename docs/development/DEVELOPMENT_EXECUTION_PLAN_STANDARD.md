# Development Execution Plan 标准

## 1. 目的与授权边界

本标准规定 Development Plan 的输入、结构、排序、依赖、关键路径、测试与 Review、Git 与环境、状态变更及完成条件，使开发执行能够按精确基线推进并形成端到端证据。

Development Plan 应使用[开发计划模板](../../templates/DEVELOPMENT_PLAN_TEMPLATE.md)，遵守[Development Task 管理标准](./TASK_MANAGEMENT_STANDARD.md)、[文档关联规则](../protocol/DOCUMENT_RELATIONSHIP.md)和[Traceability Matrix 模板](../design/TRACEABILITY_MATRIX_TEMPLATE.md)。计划是开发任务、顺序、依赖和验证方法的权威来源，但不是开发授权。

计划可以在 DESIGN 阶段编制、评审和基线化，并作为[Design Approval Gate](../design/DESIGN_APPROVAL_GATE.md)的输入。只有 Gate 针对计划引用的同一精确版本基线给出有效、无条件的 `APPROVED_FOR_DEVELOPMENT`，计划才可进入执行。计划已完成、已评审、已排期或资源已到位均不能替代该授权。

## 2. 计划输入与基线

### 2.1 强制输入

Development Plan 必须来源于已批准的 PRD、已批准并确认可用于当前范围的 Architecture，以及当前批准范围的完整 Task 列表，并精确引用版本。以下输入共同构成计划基线：

| 输入 | 最低要求 |
|---|---|
| 范围基线 | 当前范围、立项结果、限制和批准记录可访问，范围与 PRD 一致 |
| PRD | 状态满足当前范围使用要求；记录路径、精确版本或提交、Requirement ID 集合、批准人和日期 |
| Architecture | 已批准并确认可用于当前范围，且引用同一 PRD；记录路径、精确版本或提交、Design ID 集合、批准或确认人和日期 |
| 专项设计 | 适用的 Database Design、Agent Design、接口契约及其精确版本，或有效的可审计 N/A 记录 |
| ADR | 当前范围内相关重大决策清单；作为计划依据的 ADR 状态必须为 Accepted |
| 完整 Task 列表 | 每项符合 Task 管理标准，拥有 Task ID、Requirement ID、Design ID、输入输出、依赖、风险、验收和测试要求 |
| Test Plan / Test Case | 覆盖全部范围内 Task 与 Requirement，Test Case ID、环境、数据、预期结果、阈值和证据位置明确 |
| Traceability Matrix | Requirement → Design → Task → Commit 状态 → Test 的当前原子链和完整性检查 |
| 风险与回滚 | 开发、集成、迁移、发布、数据、安全、资源和依赖风险，以及可执行回滚或等价控制 |
| 仓库与环境基线 | 仓库位置、目标分支或基线提交、环境清单、访问与配置责任、已知环境差异 |

没有完整 Task 列表时不得用粗粒度阶段、百分比或人员安排代替。所谓“完整”必须同时满足：每个范围内 Design ID 至少有一个 Task；每个 Task 可回溯到 Requirement ID 与 Design ID；每个 Task 至少有一个 Test Case；共享关系已逐条展开；孤儿项、重复含义和未关闭变更影响为零。

### 2.2 精确引用规则

每个基线引用必须包含可访问路径、版本号或不可变提交、状态、适用章节、责任人、批准或确认人和日期。不得只写“最新版”、分支名称、口头确认或无版本网页。外部文档不能提供不可变版本时，必须保存受控快照或内容哈希、记录所有者和取得日期，并说明变更通知方式。

计划首页必须记录项目、计划 ID、计划版本、状态、范围基线、计划负责人、评审人、最后更新日期、上一版本和变更记录位置。计划版本与全部输入版本组成不可拆分的计划基线；任一输入变化都必须先做影响分析，不能沿用旧基线的批准结论。

## 3. Development Plan 必需内容

每份 Development Plan 必须包含以下内容，且每项均可执行、可验证、可追溯：

| 必需内容 | 必须回答的问题 |
|---|---|
| 开发阶段 | 每个阶段的目标、范围、Task ID、进入条件、退出条件、交付物、负责人、环境和证据是什么 |
| 任务顺序 | 每项 Task 的计划位置、前驱与后继、优先约束、可并行组、集成点和完成条件是什么 |
| 依赖关系 | Task、外部系统、决策、资源、环境、数据与授权之间有哪些有向依赖，何时视为满足，失败如何处理 |
| 里程碑 | 哪些可判定结果构成阶段或交付检查点，目标窗口、责任人、证据和延期影响是什么 |
| 预计风险 | 哪些风险可能影响 Task、关键路径、质量、资源或里程碑，触发信号、概率、影响和应对是什么 |
| 资源需求 | 需要哪些角色能力、可用容量、环境、数据、权限、工具、服务、预算或时间窗口，何时需要以及由谁保证 |

计划还必须包含目标与范围、精确版本基线、完整 Task 清单、关键路径、并行与串行策略、测试与 Review 活动、Git 与环境安排、集成/迁移/发布/回滚、文档更新、状态与变更控制，以及计划与开发执行的完成定义。

## 4. 阶段与 Task 清单

### 4.1 开发阶段

阶段用于组织 Task 和控制交接，不得作为 Task、完成证据或授权。每个阶段必须记录：

- 阶段 ID、目标、范围内 Task ID 和范围外事项；
- 进入条件、硬依赖、所需资源和环境；
- 串行链、并行组、集成点和 Review 点；
- 计划输出、退出条件、必须通过的测试和证据；
- 里程碑、责任人、风险、回滚或停止条件；
- 与前后阶段的交接产物和接收责任人。

阶段名称和数量应由项目依赖与交付边界决定，本标准不预设开发方法、技术平台或固定阶段模型。阶段退出必须由 Task 与证据判定，不能以时间到期或主观完成百分比判定。

### 4.2 完整 Task 清单

计划中的每个 Task 必须满足 Task 管理标准的全部必填字段。计划主表至少还要呈现 Task ID、Requirement ID、Design ID、所属阶段、前驱、后继、并行组、责任人、环境、Test Case ID、Commit 状态或 SHA、Review 状态、Readiness、完成条件和任务明细的精确引用。

任务明细可以直接写入计划，也可以位于被计划精确引用的版本化子记录；无论采用哪种形式，任务明细、排序表和 Traceability Matrix 必须属于同一基线。不得把实际 Task 隐藏在会议纪要、自由文本、个人看板或未版本化系统中。

## 5. 顺序、依赖与关键路径

### 5.1 任务顺序

Task 顺序必须从输入输出和依赖推导，而不是只按优先级或人员偏好排列。每项 Task 必须注明前驱、后继、最早可开始条件、计划完成窗口、集成点和顺序理由。优先级相同不代表可以并行；顺序靠后也不代表可以省略其测试或 Review。

计划必须能通过依赖图或等价的结构化关系执行正向和反向检查。依赖图应是无环有向图；发现循环时必须调整设计边界、引入明确契约或继续拆分 Task，不能以协调会议解释循环。

### 5.2 依赖记录

每条依赖至少记录：依赖 ID、类型、前置方、后继 Task、所需产物或状态、版本或接口契约、责任人、满足条件、目标时间、当前状态、失败影响、替代或降级路径和验证证据。依赖类型至少考虑：

- 任务输出与接口契约；
- 决策、批准和合规条件；
- 环境、数据、权限和外部服务；
- 人员能力、专用资源和时间窗口；
- 测试、Review、迁移、集成、发布与回滚前置条件。

外部依赖也必须进入计划，不得因为不由项目控制而省略。其负责人应是负责协调和升级的内部责任人。

### 5.3 关键路径

计划必须基于依赖图和有依据的工期或工作量区间识别关键路径，并记录：

- 关键路径上的 Task、依赖、Review、测试、环境准备和里程碑；
- 估算口径、单位、假设、数据来源、置信范围和责任人；
- 可用缓冲、资源瓶颈、外部等待和最可能的延期传播路径；
- 关键路径变化的监控信号、复算责任人和重排触发条件。

不得只把优先级最高或工期最长的 Task 称为关键路径。任何关键路径 Task、依赖或估算发生实质变化，都必须重新计算后续里程碑影响。

## 6. 并行与串行策略

Task 只有在以下条件均满足时才可并行：输入独立或已冻结共享契约；输出边界不冲突；没有未声明的共享状态或独占资源；环境和测试数据容量足够；集成顺序、冲突处理、Review 和回归责任明确；任一 Task 失败不会使其他 Task 的证据失效。

存在输出依赖、共享迁移、不可逆操作、同一安全边界、独占环境、未冻结接口、同一 Review 门槛或前一结果决定后一范围时，必须串行。计划应为每个并行组记录组 ID、成员 Task、共享契约、同步点、集成 Task、冲突所有者和退出条件；为每条串行链记录不可并行的事实依据。

不得以“增加人手”直接假定可并行。资源变化后仍需重新检查边界、依赖、集成成本和关键路径。

## 7. 里程碑、预计风险与资源需求

### 7.1 里程碑

每个里程碑必须包含里程碑 ID、目标结果、覆盖 Task ID、目标日期或窗口、进入条件、退出条件、责任人、评审人、所需测试与 Review、证据位置、延期影响和继续/停止决定。里程碑是可判定检查点，不是“大致完成”“完成大部分”或百分比汇报。

计划至少覆盖与当前范围相关的任务就绪、关键集成、验收、迁移或发布准备、回滚验证和文档交付检查点。不存在某类活动时，应引用范围与设计证据说明，而不是删除对适用性的判断。

### 7.2 预计风险

计划风险记录必须包含 Risk ID、类别、触发信号、概率、影响、受影响 Task/依赖/里程碑、预防措施、缓解措施、应急动作、责任人、监控频率、剩余风险、接受者和关闭证据。风险范围至少检查产品范围、技术、数据、安全、隐私、合规、质量、成本、资源、环境、外部依赖、集成、迁移、发布、回滚和运营。

开发阻断风险必须在执行前关闭。非阻断剩余风险可以由有权限的人明确接受，但风险接受不能替代测试、回滚、安全或合规控制。

### 7.3 资源需求

资源计划必须按阶段和 Task 记录：所需角色与能力、责任边界、可用容量、需要时间窗口、替补或升级路径、开发与测试环境、数据、权限、凭据、工具、外部服务、预算或配额、专用设备以及 Review 能力。资源需求必须有提供者、确认状态和最晚就绪时间。

资源尚未确认时必须记录为依赖或阻断，不得虚构人员姓名、可用容量、预算或环境。资源不足的处理顺序是调整范围、顺序、并行度或里程碑并重新批准，不得通过降低验收、测试、Review 或安全要求吸收缺口。

## 8. 测试与 Review 活动

计划必须把测试和 Review 作为有依赖、有资源、有里程碑的执行活动，而不是 Task 完成后的附注。

### 8.1 测试计划化

- 每个 Task 至少关联一个 Test Case ID；Test Case 引用 Requirement ID、Design ID、Task ID 和执行后形成的 Commit SHA。
- 开始实现前完成测试设计，执行遵循 RED → GREEN → Refactor → Commit → Review → Validation。
- 计划覆盖适用的单元、契约、集成、端到端、验收、回归、性能、容量、安全、权限、兼容、故障和恢复验证。
- 每项测试记录环境、数据、前置条件、执行责任人、目标窗口、预期结果、阈值、失败处置和证据位置。
- DESIGN 阶段使用 `NOT_RUN`；执行后只以可访问证据更新为 `PASS`、`FAIL` 或 `BLOCKED`，不得预填通过。

### 8.2 Review 计划化

计划必须定义每个 Task 和里程碑适用的 Review 类型、评审范围、评审人或所需能力、进入条件、证据、通过条件、意见关闭方式和升级路径。除一般代码或产物 Review 外，还应按风险安排架构、接口、数据、安全、隐私、运维、迁移和回滚 Review。

Review 不得由提交存在本身替代。Task 进入 `ACCEPTED` 前，所有阻断意见必须关闭并保留结论；非阻断意见若延期，必须形成有责任人和批准范围的后续 Task 或风险记录。

## 9. Git 与环境安排

### 9.1 Git 基线与证据

计划必须记录仓库、目标分支、基线 Commit、分支或集成策略、Task ID 的 Commit 引用规则、Review 流程、合并条件、版本或制品标识、冲突责任人和证据保存位置。策略可以因项目而异，但必须保证：

- DESIGN 阶段 Traceability Matrix 的 Commit 槽为 `NOT_CREATED`；
- 每个重要 Commit 引用至少一个 Task ID，并能回溯到 Requirement、Design 和 Test；
- 实际 SHA 不可变，历史改写或替代必须保留新旧关系；
- 合并前所需 Review 和测试已通过，失败或阻断状态不得被合并动作掩盖；
- 进入测试或交付前，完成 Task 不得残留 `NOT_CREATED`。

### 9.2 环境基线

每个开发、集成、测试、预发布或等价环境必须记录用途、所有者、访问控制、配置来源、依赖版本、数据来源与分类、机密信息处理、容量、可用窗口、重置或恢复方式、监控、与目标环境的已知差异和就绪验证。

环境差异必须映射到受影响 Task、测试和风险。没有可用环境、权限、数据或恢复能力时，相关 Task 必须保持未就绪或 `BLOCKED`；不得使用未经批准的生产数据、共享凭据或不可审计环境绕过限制。

## 10. 状态、进度与变更

### 10.1 计划状态

Development Plan 使用以下文档状态：

| 状态 | 含义 |
|---|---|
| DRAFT | 输入、Task、依赖或安排仍不完整，不可提交门禁 |
| IN_REVIEW | 基线已可评审，问题尚可能导致修订，不可执行 |
| BASELINED | 当前版本完整并冻结，可作为 Gate 输入；该状态不授予开发权限 |
| SUPERSEDED | 已被新版本替代，只保留历史引用，不得继续执行 |

Task 的执行状态遵循 Task 管理标准。实际完成情况、阻塞和下一步以 Development Progress 为权威来源；计划只记录获批的安排和基线变化，不以频繁覆盖计划来伪装实际偏差。

### 10.2 变更控制

新增、删除、拆分、合并或重定义 Task，改变 Requirement/Design 映射、顺序、依赖、关键路径、阶段、里程碑、资源、测试、Review、Git、环境、发布或回滚安排时，必须：

1. 登记 Change ID、原因、提出人、旧值、新值、受影响范围、风险、责任人与决定；
2. 从 PRD 和 Design 向下检查 Task、Commit 和 Test，并从受影响 Test/Commit 向上回溯 Requirement 与 Design；
3. 重新计算依赖图、并行度、关键路径、资源和里程碑；
4. 更新计划版本、Task 记录、Traceability Matrix、风险/回滚与 Development Progress；
5. 对重大决策先更新或创建 ADR，并同步 Architecture；
6. 若变更影响已获授权基线，暂停受影响范围，将相关链标记为 `IMPACT_REVIEW_REQUIRED`，重新基线化并取得新授权后再执行。

仅修正不改变语义的文字或链接可以提升修订版本，但仍须记录变更并确认追踪关系未受影响。不得在用户批准后修改计划内容并沿用原 `APPROVED_FOR_DEVELOPMENT`。

## 11. 完成定义

### 11.1 计划基线完成

Development Plan 只有同时满足以下条件才可标记为 `BASELINED`：

- PRD、Architecture、完整 Task 列表及所有适用输入均有精确、有效且一致的版本引用；
- 开发阶段、任务顺序、依赖关系、里程碑、预计风险和资源需求全部可执行；
- Task 原子性、输入输出、Readiness、验收和测试要求通过评审；
- 依赖图无循环，关键路径有估算依据，并行与串行安排有事实依据；
- 测试、Review、Git、环境、集成、迁移、发布、回滚和文档活动均有责任人、顺序和通过条件；
- Traceability Matrix 对当前阶段完整，Commit 槽为 `NOT_CREATED`、计划测试为 `NOT_RUN`，活动链 ALIGNED；
- 孤儿项、失效引用、未关闭变更影响、未决重大决策和开发阻断风险为零；
- 评审问题已关闭，剩余风险由有权限的人基于当前版本明确接受。

`BASELINED` 只表示计划完整。它既不表示开发已完成，也不授权启动开发。

### 11.2 执行启动条件

计划只有在以下条件同时满足时才可启动：当前 `BASELINED` 计划及其全部输入被同一有效 Gate 记录精确覆盖；Gate Result 为 `APPROVED_FOR_DEVELOPMENT`；用户批准范围与版本一致且无未关闭条件；首批 Task 达到 `READY`；环境、权限、数据、责任人和硬依赖已就绪。

任一条件失效时，未开始 Task 不得启动，受影响的进行中 Task 必须暂停并进入影响分析。

### 11.3 开发执行完成

计划内开发执行只有同时满足以下条件才算完成：

- 当前范围内全部适用 Task 为 `ACCEPTED`，或以 `CANCELLED` 退出且对应 Traceability Chain 具有经批准、追踪完整的 `RETIRED` 记录；
- 所有约定里程碑通过退出条件，关键集成、迁移、发布准备与回滚验证完成；
- 每个完成 Task 均有实际 Commit SHA、已关闭 Review 和通过的 Test Case 证据；
- 五层 Traceability Matrix 正向、反向和孤儿项检查通过，完成 Task 不残留 `NOT_CREATED`，开发级必跑测试不残留 `NOT_RUN`；Phase 6 用例可以保持明确的 `NOT_RUN`；
- 功能、非功能、边界、失败、安全、兼容、恢复、回归和验收测试按计划通过；
- 偏差、阻断和风险已关闭或按权限接受，且不存在红线、安全、合规或数据完整性阻断；
- Development Progress、必要设计与运行文档、变更记录、发布与回滚证据已更新并完成交接。

开发执行完成仍应接受下一阶段适用门禁；不得仅凭 Task 数量、Commit 数量、工时消耗或里程碑日期宣告通过。

## 12. 禁止事项与计划评审

禁止使用没有版本的 PRD 或 Architecture、缺失 Task 的阶段计划、仅按人员排列的日程、没有依赖图的任务列表、没有证据的关键路径、把测试和 Review 放在计划外、预填 Commit 或测试通过、用百分比代替里程碑退出条件，以及把 `BASELINED` 或管理层同意解释为开发授权。

计划评审必须逐项检查输入基线、Task 完整性、阶段与顺序、依赖与关键路径、并行/串行、里程碑、风险、资源、测试、Review、Git、环境、发布/回滚、状态、变更和完成定义。任一强制项缺失、冲突、不可执行或不可追溯时，计划保持 `DRAFT` 或 `IN_REVIEW`，不得通过总体评分、口头承诺或资源投入视为完成。
