# 代码评审标准

## 1. 目的与适用范围

本标准规定开发变更的评审输入、职责、强制检查、证据、严重级别、结果和复审条件。它适用于源代码、测试、配置、依赖、构建与部署定义、数据迁移、脚本及会影响交付行为的文档变更，并保持对代码托管平台、编程语言、框架和自动化工具中立。

代码评审是实现进入共享基线前的独立工程判断，不替代 [Design Approval Gate](../design/DESIGN_APPROVAL_GATE.md) 的开发授权，也不替代测试、风险接受或用户批准。追踪记录应与 [Traceability Matrix 模板](../design/TRACEABILITY_MATRIX_TEMPLATE.md) 和 [Development Plan 模板](../../templates/DEVELOPMENT_PLAN_TEMPLATE.md) 一致。

## 2. 评审输入基线

发起评审前，作者必须冻结并提供可访问、版本明确且彼此一致的输入：

1. 当前批准范围、Requirement 版本及验收标准；
2. 当前 Architecture、相关 Design ID 和全部适用 ADR，且重大决策已 Accepted；
3. Development Task ID、任务范围、完成条件和依赖；
4. 精确的起始 Commit、结束 Commit、完整 Commit 列表和可复核差异；
5. Test Case ID、RED → GREEN → REFACTOR 证据、最终测试结果和执行环境；
6. 更新后的 Traceability Matrix，以及 Requirement → Design → Task → Commit → Test 的正反向映射；
7. 适用的安全、隐私、性能、数据、迁移、兼容、发布和回滚风险材料；
8. 已知限制、未关闭问题、历史评审意见及其处置证据。

评审只对冻结的精确 Commit 范围有效。评审开始后新增、删除、改写或重排任何会改变内容的 Commit，原评审基线即失去当前性；新基线必须重新提供差异、追踪和受影响测试证据。

缺少任一强制输入、链接不可访问、版本不一致或范围无法判定时，不得给出 APPROVED。

## 3. 变更范围检查

评审人首先确认“所评即所批”：

- 每个修改都属于当前 Task 和批准的 Requirement / Design 范围；
- Commit 列表、差异、生成文件、依赖、配置、迁移和文档影响均已完整展示；
- 没有无关重构、顺带功能、隐藏生成变化、调试内容、临时绕过或未批准副作用；
- 删除、重命名、接口变化、数据变化和默认值变化已列出全部消费者与迁移影响；
- 一对多或多对一的 Task、Commit 和 Test 关系已在 Traceability Matrix 中展开；
- 修改规模仍可可靠评审；范围过大时应拆分为保留行为和依赖顺序的原子变更。

发现超出批准范围的内容时，不得以评审同意替代 Requirement、Architecture、Design 或 ADR 的变更流程。作者必须移除越界内容，或先完成相应源文档、影响分析和授权更新。

## 4. 角色与职责

| 角色 | 职责 |
|---|---|
| 作者 | 提供完整基线、差异、追踪、测试与风险说明；逐项回应发现；通过新 Commit 修正问题，不自行批准其变更 |
| 主评审人 | 独立理解需求与设计，检查完整差异和证据，记录可操作发现，确认处置，并给出唯一评审结果 |
| 专项评审人 | 对安全、隐私、性能、数据、测试、运维或领域规则进行专业检查；高风险变化必须由具备相应能力且有权限的人承担 |
| 任务责任人 | 确认变更仍符合 Task 范围、依赖与完成条件，并维护 Development Plan 和追踪状态 |
| 风险接受人 | 仅在权限范围内接受非阻断剩余风险；不能接受违反 Requirement、Architecture、ADR、安全红线或缺失必要测试 |

主评审人必须与作者保持足够独立，不能只依据作者摘要、自动报告或先前版本结论。无法胜任某专项时，应要求具备能力的专项评审人加入，而不是缩小检查范围。

### 4.1 Review Profile 与 Review Packet

AI CTO 可使用 [Review Profile & Packet Standard](./AI_CTO_REVIEW_PROFILE_STANDARD.md) 为当前变更生成最小职责计划和冻结输入 Packet。该扩展只提供风险分流、基线/Diff 指纹和结构化发现合同：不固定 Reviewer 数量，不把逻辑只读当作系统权限隔离，也不授予 Reviewer 写入、提交、部署或批准权限。

Review Profile 不能减少本标准的六项强制评审。Profile 计划中的 `PASS` 或 `NON_BLOCKING_FINDINGS` 也不能单独产生最终批准；主评审人必须在精确 Packet 基线和完整差异上，继续输出本标准规定的 `APPROVED`、`CHANGES_REQUIRED` 或 `REJECTED`。

## 5. 六项强制评审

以下 6 项必须逐项检查并保存结论与证据；任一项不得省略或被综合评分抵消。

| 强制评审项 | 必须核验的内容 | 典型证据 |
|---|---|---|
| 1. 符合 Architecture | 组件与系统边界、接口、数据流、依赖、部署边界、故障处理、可观测性和恢复方式与当前 Architecture / Design 一致；实现未引入未经批准的新边界或耦合 | Architecture / Design 版本链接、差异定位、集成或故障验证 |
| 2. 符合 ADR | 所有适用重大决策均有 Accepted ADR；实现遵循已选方案、约束与后果；没有采用 Proposed、Superseded 或相互冲突的决策 | ADR 清单、状态与版本、实现对应位置、后续行动证据 |
| 3. 符合 Requirement | 每项行为可追溯到已批准 Requirement 和验收标准；正常与异常路径符合范围，未遗漏、扭曲或扩大需求 | Requirement 版本、Task 映射、Test Case 与验收结果 |
| 4. 安全风险 | 身份、权限、输入、输出、秘密、敏感数据、依赖、日志、审计、注入、越权、资源滥用、错误泄露和副作用已按威胁与数据分类检查；关键风险已关闭 | 威胁或风险记录、安全测试、依赖与配置检查、修复证据 |
| 5. 性能问题 | 时间、空间、I/O、网络、并发、锁、重试、缓存、容量、退化路径和资源释放符合非功能要求；没有无界增长、放大效应或未经验证的热点 | 性能 Requirement、基准或负载结果、复杂度与容量分析、监控指标 |
| 6. 必要测试 | Test Case 在实现前定义并具有有效 TDD 证据；正常、边界、失败、安全和回归覆盖与风险匹配；测试在待评审 Commit 和声明环境真实执行，断言能判定需求 | Test Case、RED / GREEN / REFACTOR 记录、测试日志、覆盖映射和最终验证证据 |

评审人还应检查正确性、可读性、可维护性、错误处理、兼容性和可逆性，但这些检查不能替代以上六项强制结论。

Review Profile 可以把专项职责映射到上述强制项，但只能作为输入组织和证据归并方式。缺失 Profile、预算不足或 Packet 过期时，应降低结论为 `CHANGES_REQUIRED` 或 `REJECTED`，不得以“已启动多个 Reviewer”弥补证据缺口。

## 6. 评审方法与流程

1. 核验输入基线、评审权限和变更范围，确认链接与版本可访问。
2. 从 Requirement、Architecture 和 ADR 建立预期行为与约束，再阅读 Commit 与完整差异。
3. 按六项强制评审逐项检查实现、测试和证据；高风险领域分配专项评审。
4. 记录每个发现的严重级别、位置、依据、影响和所需动作，不以笼统偏好代替可验证理由。
5. 作者以新 Commit 修正并提供更新后的测试、追踪和影响证据；不允许通过隐藏差异或改写共享历史关闭问题。
6. 评审人核对每项处置，在最终精确 Commit 基线上重新检查受影响内容和必要回归范围。
7. 主评审人只使用 APPROVED、CHANGES_REQUIRED 或 REJECTED 记录最终结果，并保存完整评审证据。

评审应阅读足以判断行为的上下文，而不是只看新增行。抽样、作者演示、历史批准或总体得分不能替代完整差异和高风险路径检查。

## 7. 发现严重级别

| 严重级别 | 判定 | 对评审结果的约束 |
|---|---|---|
| BLOCKER | 可能造成安全突破、数据损坏或泄露、合规违反、不可恢复故障，或变更缺少有效授权 / 基线 | 未关闭时只能为 CHANGES_REQUIRED；若问题源于根本性错误方向且当前变更无法安全修订，则为 REJECTED |
| MAJOR | Requirement、Architecture、ADR、正确性、性能、可靠性或必要测试存在实质缺口 | 未关闭时只能为 CHANGES_REQUIRED；修订后必须复审和重测 |
| MINOR | 不改变正确性与风险结论，但会显著影响清晰度、一致性或长期维护 | 应在当前变更修正；确需保留时必须有理由、责任人和有权限的明确接受，且不得掩盖六项强制缺口 |
| NOTE | 非强制建议、后续改进机会或信息性说明 | 不阻断批准，但不得借 NOTE 降级本应属于 BLOCKER、MAJOR 或 MINOR 的问题 |

严重级别由可能影响与发生条件共同决定。作者不同意严重级别时，应提供 Requirement、Design、测试或风险证据讨论；不能仅凭偏好降级。安全红线、未授权范围和缺失必要测试不得通过风险接受降级。

## 8. 唯一评审结果

最终结果只允许以下三种，不设置条件批准、部分批准、默认批准或口头批准：

| 结果 | 使用条件 | 后续动作 |
|---|---|---|
| APPROVED | 六项强制评审全部满足；范围与基线一致；必要测试通过且证据当前；Task / Commit / Test 追踪完整；BLOCKER 与 MAJOR 全部关闭；保留的 MINOR 已有合规处置且不影响正确性、安全或验收 | 可按分支保护和合并门禁进入下一步；批准只适用于记录的精确 Commit 基线 |
| CHANGES_REQUIRED | 存在可在当前范围内修正的缺陷、证据缺口、未关闭 BLOCKER / MAJOR、必要测试问题、追踪问题或范围混入 | 禁止合并；作者修订、重测并更新追踪后，对新基线进行复审 |
| REJECTED | 变更与 Requirement、Architecture 或 ADR 根本冲突，方向未经授权，存在不可接受安全 / 数据风险，或需要重新设计、拆分 Task 或退回前序门禁才能继续 | 停止当前变更进入共享基线；返回相应源文档、设计或任务流程，重新获得授权后再提交新的评审基线 |

不得把“自动检查成功”“没有人反对”“只剩小问题”或“将在合并后修复”记录为 APPROVED。只要批准条件没有全部满足，结果必须是 CHANGES_REQUIRED 或 REJECTED。

## 9. 自动检查的边界

静态分析、格式检查、类型检查、测试执行、覆盖报告、依赖扫描、安全扫描、性能测量和自动评审建议只能提供证据与线索，不能替代代码评审，也不能自动产生 APPROVED。

评审人必须判断工具规则是否覆盖当前 Requirement、Architecture、ADR、威胁和性能风险，核对误报、漏报、配置、排除项、执行版本与结果时效。工具未发现问题不等于设计正确；工具失败也必须按真实影响处理，不能被无理由忽略或重复运行到偶然成功。

## 10. 评审证据

每次评审必须保存不可覆盖或可审计版本的记录，至少包含：

- 评审标识、日期、作者、主评审人与专项评审人；
- Requirement、Architecture、Design、ADR 和 Task 的精确版本引用；
- 起始与结束 Commit、全部 Commit SHA、差异和目标分支；
- 六项强制评审各自的分析、结论与证据链接；
- 每个发现的严重级别、文件或制品位置、影响、依据、所需动作和责任人；
- 处置该发现的 Commit SHA、测试证据和复核说明；
- Test Case ID、测试环境、执行版本、结果和原始证据位置；
- Traceability Matrix 版本、变更影响状态、剩余风险及接受记录；
- 三种唯一结果之一、决定理由和生效的精确 Commit 范围。

评审讨论可以作为辅助上下文，但不能代替最终结构化记录。链接失效、引用“最新版本”、缺少 Commit 范围或证据不对应当前基线时，评审记录无效。

## 11. 批准条件与复审

APPROVED 必须同时满足：

1. 输入完整、范围获批且冻结基线未变化；
2. 六项强制评审都有可复核证据并符合要求；
3. 所有 BLOCKER 与 MAJOR 已通过修订、测试和复核关闭；
4. 必要测试和回归在最终 Commit 上通过，没有被跳过、弱化或使用旧结果；
5. Requirement → Design → Task → Commit → Test 正反向追踪完整，链接和版本有效；
6. 安全、性能、数据、兼容、迁移和回滚风险已按适用性关闭或由有权限的人接受非阻断剩余风险；
7. 合并后不会引入未评审内容，分支保护和交付门禁能够继续执行。

出现以下任一情况必须复审：新增或修改 Commit；解决合并冲突；变更 Requirement、Architecture、Design、ADR、Task 或 Test Case；测试、依赖、配置、环境或风险基线变化；发现新的安全、性能、数据或回归影响；目标分支变化导致行为差异。

复审必须以新精确基线重新核对全部受影响强制项，并在影响可能跨边界时扩大到完整差异和相关回归范围。先前 APPROVED 对新基线不生效；主评审人必须重新记录三种唯一结果之一。修订次数、截止时间或自动检查通过均不能免除复审。
