# Git 工作流标准

## 1. 目的与适用范围

本标准规定开发阶段的分支、提交、合并、证据和例外管理。它适用于源代码、测试、配置、构建与部署定义、迁移、脚本和技术文档等受版本控制的交付物，并保持对代码托管平台、编程语言、构建系统和部署方式中立。

开发活动必须与当前已批准的范围和版本基线一致。开始开发前应取得有效的 [Design Approval Gate](../design/DESIGN_APPROVAL_GATE.md) 授权，并按 [Traceability Matrix 模板](../design/TRACEABILITY_MATRIX_TEMPLATE.md) 和 [Development Plan 模板](../../templates/DEVELOPMENT_PLAN_TEMPLATE.md) 维护 Requirement ID → Design ID → Development Task ID → Commit SHA → Test Case ID 的追踪链。

本文使用“合并请求”统称任何提供变更差异、评审讨论、批准记录和合并证据的等价机制。

## 2. 强制原则

1. 每个重要修改都必须形成不可变的 Git Commit 记录；不得只以工作区文件、聊天记录、构建产物或口头说明作为完成证据。
2. 每个 Commit 必须可追溯到 Development Task ID，并通过 Task 回溯到 Requirement ID 和 Design ID；相关 Test Case ID 与验证证据必须进入同一追踪链。
3. Commit 必须原子化：一个提交表达一个可说明、可评审、可验证且可安全撤销的意图。
4. 受保护分支只能在完成必要评审和测试后合并；失败、缺失、过期或与当前基线不一致的证据不得用于批准。
5. 禁止将密码、令牌、私钥、个人敏感数据、生产凭据或其他秘密写入 Commit、分支、标签、评审内容和测试证据。
6. 不得改写已作为共享基线、评审基线、发布基线或追踪证据引用的 Commit 历史。确需纠正时，应以新的可审计提交和影响记录处理。

## 3. 分支策略

| 分支 | 职责与基线 | 创建与流向 | 保护要求 |
|---|---|---|---|
| `main` | 保存已发布或随时可发布的稳定基线，是发布与回滚的权威来源 | 正常情况下只接收经批准的 `develop` 合并；生产紧急修复可接收从受影响 `main` 基线创建的 `fix/*`，修复随后必须同步回 `develop` | 禁止直接推送和未评审合并；要求当前评审、必要测试、追踪完整、冲突已解决和可执行回滚证据；发布点使用不可变 Commit 标识 |
| `develop` | 保存下一发布版本的集成基线，接收已完成的功能与常规修复 | 从当前 `main` 建立或重建；接收 `feature/*` 与以 `develop` 为基线的 `fix/*`；达到发布条件后合并到 `main` | 禁止直接推送和绕过评审；合并前要求分支更新到当前集成基线、必要测试通过、追踪更新且无未解决阻断问题 |
| `feature/*` | 承载一个明确 Task 或一组不可分割、已批准且可独立验证的功能变更 | 从最新 `develop` 创建，只合并回 `develop`；合并后删除，禁止直接流向 `main` | 分支名应包含稳定 Task ID 和简短意图；不得混入无关修复、重构或未批准范围；合并前完成代码评审和相关测试 |
| `fix/*` | 承载缺陷修复、安全修复或回归修复 | 常规修复从 `develop` 创建并合并回 `develop`；生产紧急修复从受影响的 `main` 创建，经门禁合并到 `main` 后立即同步到 `develop`，并处理两个基线的差异 | 必须关联缺陷 Task 和复现测试；不得以紧急为由省略安全检查、必要测试、评审、追踪或回滚；跨基线同步必须有独立验证证据 |

推荐分支名为 `feature/TASK-XXXX-short-description` 或 `fix/TASK-XXXX-short-description`。名称用于定位，权威追踪仍以 Development Plan、Commit SHA、评审记录和 Traceability Matrix 为准。

### 3.1 正常流向

1. 从当前、干净且已同步的 `develop` 创建 `feature/*` 或常规 `fix/*`。
2. 在工作分支内按批准范围完成原子提交、测试、追踪更新和自查。
3. 以冻结的 Commit 范围发起评审；评审期间新增内容变更会形成新基线，并触发受影响部分复审与重测。
4. 满足合并条件后进入 `develop`。集成后的冲突解决或行为变化必须重新验证。
5. `develop` 达到发布条件后，按批准的精确基线合并到 `main`；发布与回滚都引用不可变 Commit。

### 3.2 紧急修复流向

生产紧急修复必须从实际受影响的 `main` Commit 建立 `fix/*`。修复通过缺陷复现、必要安全与回归测试、评审和回滚检查后方可合并到 `main`。同一修复必须随后合并或等价移植到 `develop`；若无法直接同步，应记录差异、风险、补偿措施、责任人和验证证据，直至两个活动基线的影响关闭。

## 4. Commit 标准

### 4.1 必备提交类型

提交主题必须以与修改主要意图一致的类型开头。下列五种类型必须受支持并按其语义使用：

| 类型 | 用途 |
|---|---|
| `feat:` | 新增或扩展已批准的用户可见能力或系统能力 |
| `fix:` | 修复可复现的缺陷、安全问题或回归 |
| `refactor:` | 在不改变已批准外部行为的前提下调整内部结构 |
| `docs:` | 仅修改受控文档、说明或追踪材料 |
| `test:` | 新增或修改测试用例、测试数据或测试基础定义，不包含产品行为实现 |

如治理基线允许其他类型，其定义和使用条件必须先被记录；不得用宽泛类型掩盖本应归入以上五类的修改。

### 4.2 提交内容与追踪

每个 Commit 的主题应简洁描述单一意图，正文或等价元数据必须记录：

- Development Task ID；
- 关联的 Requirement ID 与 Design ID，或可回溯到它们的权威 Task 链接；
- 相关 Test Case ID、测试状态和证据位置；
- 影响范围、重要风险和必要的迁移或回滚说明；
- 若为评审问题修订，关联问题标识和处置说明。

Commit SHA 生成后必须写入 Traceability Matrix。合并、变基、压缩或移植导致 SHA 改变时，应保留原始评审证据，并把最终不可变 SHA 与原记录建立明确映射。

### 4.3 重要修改与原子性

“重要修改”包括任何改变需求行为、接口、数据、权限、安全控制、性能特征、依赖、配置、构建、部署、迁移、回滚、测试判定或受控文档事实的变化。每项重要修改至少有一个 Commit；一个 Commit 不得混合多个无依赖意图，也不得夹带格式化、生成文件或无关清理来扩大评审面。

原子 Commit 必须能够独立说明目的和影响。TDD 的 RED 提交可以按标准保留预期失败证据，但不得以失败状态合并到受保护分支；GREEN 与 REFACTOR 的提交必须分别保持其意图清晰。若单个可交付修改必须跨多个 Commit，应在合并请求和追踪矩阵中展开它们与同一 Task、Requirement、Design 和 Test Case 的关系。

## 5. 评审、测试与合并条件

合并到 `develop` 或 `main` 前必须同时满足：

1. 变更范围属于当前批准基线，所有 Commit 均可回溯到 Task、Requirement 和 Design。
2. 独立评审已按当前精确 Commit 范围完成，阻断问题已关闭；自动检查不能代替代码评审。
3. 与变更相关的单元、集成、验收、安全、性能和回归测试已按适用性执行，结果满足预先定义的通过标准。
4. 测试证据能定位环境、版本、命令或步骤、时间、结果和保存位置，不使用作者声明代替证据。
5. Traceability Matrix 已更新为最终 Commit SHA，Test Case、Review 和变更影响记录一致。
6. 合并冲突已通过理解语义的方式解决；冲突解决产生的内容变化已经复审和重测。
7. 发布、迁移或不可逆影响适用时，回滚或等价恢复控制已经验证并获批准。

不得通过降低测试断言、删除失败用例、缩小评审差异、拆分隐藏关联变更或使用过期批准来满足合并条件。

## 6. 秘密与敏感信息处理

提交前必须检查暂存内容和完整差异，确保秘密与非必要敏感数据未进入版本历史。测试和文档只能使用获准的脱敏数据或安全替代值。

一旦发现秘密进入 Git 历史，应立即停止传播和合并，撤销或轮换对应凭据，按安全事件流程评估访问与泄露范围，并采用经批准的方法清理历史。历史清理会改变 Commit 标识，因此必须冻结受影响操作、通知相关责任人、更新追踪与基线引用，并重新执行评审和验证。仅删除最新文件内容不构成完整处置。

## 7. 正常 Git 状态

发起评审、合并、发布或交接时，仓库必须处于可解释且可复现的正常状态：

- 当前分支与任务计划一致，不处于 detached HEAD；
- 工作区和暂存区干净，不存在未说明的修改、冲突或重要未跟踪文件；
- 不存在进行中的 merge、rebase、cherry-pick、revert 或其他未完成历史操作；
- 本地基线与所声明的共享基线关系明确，待推送、待拉取和分叉情况已处理或记录；
- HEAD、评审 Commit 范围、测试版本和 Traceability Matrix 引用同一基线；
- 忽略规则没有隐藏必须纳管的源文件、测试、配置、迁移或证据索引；
- 所需提交均可访问，引用链接有效，历史中没有已知秘密。

开发过程中可以存在有意的未提交修改，但责任人必须能够说明其 Task、状态和去向；这类状态不得作为完成、评审通过、合并、发布或交接的基线。

## 8. 例外处理

例外是由于已确认的外部约束或紧急事件，无法在规定时间内遵循某一非安全性流程步骤的、范围受限且有期限的偏离。时间压力、操作习惯、工具不熟悉、测试失败或评审人暂不可用本身不构成例外。

任何例外都必须在执行偏离前获得有权限的用户明确批准，并记录：适用分支与 Commit 范围、关联 Task / Requirement / Design、事实原因、无法遵循的具体规则、风险、最小补偿控制、责任人、有效期、恢复正常流程的动作、验证和回滚方式。沉默、推断、历史惯例或口头转述不构成批准。

秘密禁入、追踪完整性、数据保护、不可逆风险控制和最终评审测试不得被例外取消。紧急情况下可以压缩等待时间，但不能把未验证修改直接视为已批准。例外到期、基线变化或触发条件消失后必须立即恢复正常流程，关闭影响记录，并补齐经批准的证据；否则相关变更不得继续合并或发布。

## 9. 完成证据

一项 Git 工作流任务只有在以下证据彼此一致时才完成：最终 Commit SHA、分支与合并记录、评审结论、测试证据、Task / Requirement / Design / Test Case 追踪、变更影响记录，以及适用的发布和回滚记录。缺少任一强制证据时，任务保持未完成状态，不得用分支已合并或文件已出现代替。

## 10. Finalization Integrity

Commit subject、Commit body、合并请求标题 / 说明和交接摘要必须从批准范围、实际 Diff、评审结果和测试 Evidence 生成。会话中被否决且未进入基线的方案不应成为提交或交付物的命名中心；真实删除、迁移、兼容性、安全、审计和外部操作事实必须保留。

高保障提交或合并前，按 [Finalization Integrity Standard](../governance/FINALIZATION_INTEGRITY_STANDARD.md) 执行 `Preflight → Freeze → Authorized Action → Readback → Postflight`。Hook、平台包装或合并后内容发生变化时，必须重新读取并检查；文本扫描通过不等于语义正确或评审通过。
