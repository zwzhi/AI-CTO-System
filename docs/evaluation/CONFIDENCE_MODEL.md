# Confidence 可信度模型

## 1. 目的

Confidence 用于说明**一项结论被证据支持到什么程度**，帮助 AI CTO 判断该结论目前可以支撑哪类决策，以及下一步需要怎样补证。它适用于 Research、Evaluation、Build vs Buy、生命周期状态转换和 `PROJECT_STATE.md` 中的 Confidence/Evidence 记录。

Confidence 必须绑定到具体结论及其适用边界，而不是笼统地给整份文档或项目贴标签。

## 2. 核心原则

1. **结论与证据绑定**：每个等级都必须指向来源、证据 ID、版本/提交、验证日期和适用范围。
2. **事实、推断、用户确认分离**：三者可以共同支持决策，但不得互相冒充。
3. **Confidence 与项目评分分离**：项目评分回答“是否值得做”，Confidence 回答“我们有多确定”。高分低 Confidence 表示潜力高但尚未准备好决策；低分高 Confidence 表示证据充分地证明价值有限。
4. **关键结论短板决定总体可信度**：总体 Confidence 取所有关键结论中的最低等级，不取平均值。非关键细节的低等级不应无故拖低总体等级，但必须保留标注。
5. **证据质量优先于数量**：大量转载、同源报道或重复指标仍可能只有一个证据源。资料数量不能等同于权威性、直接性、时效性、适用性或可复现性。
6. **高等级不代表永远正确**：版本、环境、需求、法规和时间窗口变化后必须重新评估。

## 3. 等级定义

| 等级 | 名称 | 含义 | 最低证据要求 | 可支持的决策范围 | 不得据此直接作出的决策 |
|---|---|---|---|---|---|
| **Level 1（L1）** | AI 推测 | 基于模型知识、类比、逻辑推演或尚未核实的假设形成的判断 | 写明假设、推理链、未知点和可能反证；不得伪造来源 | 形成调研问题、备选方向、风险清单和低成本可逆实验 | 立项批准、重大采购、生产承诺、不可逆架构或合规结论 |
| **Level 2（L2）** | 公开资料支持 | 有可追溯的公开资料支持，但尚未在目标项目环境中验证 | 至少一个与结论直接相关且可访问的来源；记录来源类型、版本/提交、发布日期/访问日期、适用边界和冲突信息。关键结论应优先使用第一方或独立交叉来源 | 候选筛选、初步评分、方案比较、可逆的低风险选型和 PoC 立项 | 把文档声明当作目标环境已验证结果；仅凭营销资料作高风险或不可逆承诺 |
| **Level 3（L3）** | 项目实际验证 | 已在目标项目或足够等价的环境中，通过代码审查、构建、测试、PoC、试用、合同核验或专项检查验证 | 绑定具体版本/提交；记录环境、数据、步骤、验收标准、实际结果、产物路径、异常与覆盖边界；他人能够复核或复现 | 设计与实现选择、预算和排期收敛、有限范围上线，以及在风险门禁通过后的重大技术决策 | 把一次性、小样本或非生产等价验证外推为长期稳定性、长期成本和全规模结论 |
| **Level 4（L4）** | 长期历史数据验证 | 有持续运行、重复项目或足够长历史窗口的数据，能观察稳定性、趋势、成本和异常 | 明确时间窗口、样本/业务量、版本变化、数据来源和质量；包含运行指标、事件/故障、维护升级、成本及偏差；记录适用环境和复核日期 | 长期容量与成本规划、组织级标准化、规模化推广、可靠性基线和战略复用 | 将过期、环境不相似或幸存者偏差明显的历史数据无条件套用到新场景 |

等级表示证据成熟度，不表示结论的好坏。负面结论同样可以达到 L3 或 L4。

## 4. 证据质量判定

评估证据时至少检查：

| 质量维度 | 检查问题 |
|---|---|
| 权威性 | 来源是否有资格证明该事实，例如许可证原文、官方发布、合同、测试产物或生产指标？ |
| 直接性 | 证据是否直接支持当前结论，还是经过多层转述或类比？ |
| 时效性 | 证据是否适用于当前日期、版本、价格、法规和维护状态？ |
| 适用性 | 环境、规模、数据、部署方式和目标需求是否一致？ |
| 可复现性 | 他人能否按记录复核来源或重复验证？ |
| 独立性 | 多份资料是否真正独立，还是引用同一原始说法？ |
| 完整性 | 是否同时记录失败、异常、反证和覆盖不到的范围？ |
| 一致性 | 不同来源或实测是否互相支持；冲突是否已解释？ |

以下情况不会仅因数量增加而升级 Confidence：

- 多篇文章转载同一个未核实说法。
- 多个 Stars、下载量或热度指标共同证明“项目可靠”。
- 多个营销页面重复同一供应商声明。
- 多次使用相同小样本、相同环境或相同错误方法测试。
- 来源很多，但均未绑定目标版本、目标场景或可复核证据。

## 5. 关键结论与总体 Confidence

关键结论是其错误会改变立项、路径选择、红线结果、预算、排期、合规判断或退出方案的结论。默认包括：

- 核心需求与非功能要求是否满足。
- 技术可行性与关键集成是否成立。
- 安全、隐私、合规、License 和知识产权是否可接受。
- 成本、交付时间与关键资源估算是否可信。
- 上游/供应商持续维护和退出能力是否可接受。
- 决策推荐所依赖的其他决定性假设。

总体 Confidence 的计算规则：

1. 列出所有关键结论及其等级。
2. 取其中最低等级作为总体 Confidence。
3. 同时写明造成短板的结论；不得只报一个等级。
4. 若关键结论尚未识别完整，总体等级不得高于 L1。

示例：技术适配为 L3、License 兼容性为 L2、TCO 为 L1，则总体 Confidence 为 **L1**，短板是 TCO；不能平均成 L2，也不能因技术验证充分而忽略成本假设。

## 6. 升级规则

Confidence 只对已补证的具体结论升级，不允许因同一文档中另一项结论证据充足而连带升级。

| 升级路径 | 必须新增的证据 |
|---|---|
| L1 → L2 | 找到直接、可追溯且适用于目标版本/场景的公开来源；记录来源日期、适用边界与冲突信息 |
| L2 → L3 | 在目标或等价环境完成可复核验证，并保存版本、环境、步骤、验收标准、结果与产物 |
| L3 → L4 | 累积足够时间窗口和代表性样本的运行历史，覆盖正常运行、变更、维护、成本和异常事件 |

升级还必须满足：

- 新证据与结论范围一致；局部验证只能提升局部结论。
- 所有最低证据要求均满足，而非只满足其中一项。
- 反证和失败结果已纳入解释。
- 评估人记录升级日期、原等级、新等级和升级理由。

## 7. 降级与失效规则

发生以下任一情况时，应立即复核，并降到当前证据实际能支持的最高等级：

- 目标版本、提交、架构、配置、数据规模或部署环境发生实质变化。
- 来源失效、内容过期、许可证/合同/法规变化或维护状态改变。
- 实测无法复现、验收口径错误、样本不具代表性或数据质量不足。
- 出现与原结论冲突的新证据、生产事故、安全漏洞或成本偏差。
- 原证据只覆盖局部范围，却被外推到更广结论。
- 历史数据的时间窗口或环境已不再适用于当前决策。

降级不得只在备注中写“可能过期”而继续沿用原等级。应更新结论标注、总体 Confidence、受影响的评分/Build vs Buy 结果和下一动作。

## 8. 冲突、未知与时效管理

- 证据冲突时，优先比较直接性、权威性、时效性、适用性和可复现性；冲突解除前采用能被共同证据支持的较低等级。
- 无法核实的信息明确标记为“未知”，并说明它是否属于关键结论。未知关键结论通常保持 L1。
- 每项关键结论应记录“最后验证日期”和“复核触发器”。法律、价格、安全、版本和项目活跃度等变化快的信息应在决策前重新核实。
- 不设置脱离场景的永久有效期。由结论所有者根据变化速度、影响和可逆性指定复核时间或事件触发器。
- 用户确认只能证明“用户作出了该选择或接受了该风险”，不能把未经验证的技术事实自动提升到 L3。

## 9. 结论标注格式

### 9.1 行内标注

使用以下格式紧邻结论：

`[Confidence: L2｜证据：E-01、E-03｜版本：v1.4.0/abc123…｜验证：2026-07-13｜边界：官方支持声明，未在目标环境实测]`

### 9.2 关键结论表

| 结论 ID | 结论 | 事实/推断/用户确认 | 证据 ID | 版本/提交与环境 | Confidence | 适用边界与反证 | 最后验证 | 复核触发器 |
|---|---|---|---|---|---|---|---|---|
| C-01 | <填写> | <事实/推断/用户确认> | <填写> | <填写> | <L1/L2/L3/L4> | <填写> | <YYYY-MM-DD> | <填写> |

### 9.3 文档级摘要

```markdown
- 总体 Confidence：<L1/L2/L3/L4>
- 关键结论短板：<填写结论 ID、当前证据和局限>
- 可支持的决策：<填写>
- 当前不可支持的决策：<填写>
- 升级动作：<填写最小补证动作、负责人和完成标准>
- 最后复核日期：<YYYY-MM-DD>
- 复核触发器：<填写>
```

## 10. 决策范围与门禁使用

| 当前最低等级 | 默认处理 |
|---|---|
| L1 | 保持为假设；可继续 Research 或做可逆实验，不得包装为已验证事实 |
| L2 | 可进入候选比较和初步 Evaluation；高影响、难回滚或生产承诺前通常需要实际验证 |
| L3 | 在验证边界内可支持设计、实现和有限上线；长期可靠性、规模化和战略标准化仍需历史数据 |
| L4 | 在历史数据适用边界内可支持长期与规模化决策；环境变化时仍需复核 |

具体项目可针对风险设置更高门槛。任何硬性门禁未通过时，即使 Confidence 较高也不得批准；同样，项目评分很高但关键结论 Confidence 不足时，应先补证而不是自动立项。

## 11. 生命周期中的使用方式

- **RESEARCH**：为来源、事实、推断、风险和建议逐项标记 Confidence。
- **EVALUATION**：项目评分与 Confidence 分开输出，并识别决定性短板。
- **Build vs Buy**：每个矩阵分数引用证据与 Confidence，总体取关键结论最低等级。
- **阶段转换**：在 `PROJECT_STATE.md` 更新 Current Stage、Confidence、Evidence 和 Next Action；低 Confidence 的关键假设未处理时不得跨过必要阶段。
- **记忆与复盘**：`PROJECT_MEMORY.md` 只保存摘要和源文档链接；新证据导致升级、降级或决策变化时保留历史记录。

## 12. 评估检查清单

- [ ] Confidence 绑定到具体结论，而不是只给项目一个模糊标签。
- [ ] 来源、版本/提交、环境、日期、适用边界和证据 ID 可追溯。
- [ ] 事实、推断和用户确认已区分。
- [ ] 等级满足对应的最低证据要求。
- [ ] 总体 Confidence 取关键结论短板，未取平均或多数等级。
- [ ] Confidence 未并入项目评分或路径矩阵分。
- [ ] 未把资料数量、Stars、转载或营销声明等同于高质量证据。
- [ ] 反证、未知、冲突和无法覆盖的范围已记录。
- [ ] 升级、降级、最后验证日期和复核触发器已明确。
- [ ] 当前等级可以支持和不能支持的决策范围已写清。
