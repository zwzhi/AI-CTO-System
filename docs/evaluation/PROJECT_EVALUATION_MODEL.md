# 项目评估模型

## 1. 目的与边界

本模型用于在 `EVALUATION` 阶段以统一的 100 分制比较项目候选。评分回答“在当前范围和假设下，这个项目值得优先投入到什么程度”，不回答“是否已经批准立项”。

评分必须与以下内容分开报告：

- 各维度的证据与判断依据。
- 结论的 Confidence。
- 风险红线检查结果。
- `RESEARCH` 与 `EVALUATION` 的完成状态。
- 用户立项确认。

总分只能形成优先级建议，不能自动批准项目进入 `DESIGN`。该原则遵循 [ADR-0002：项目评分与立项门禁分离](../adr/ADR-0002-PROJECT-EVALUATION-AND-APPROVAL.md) 和 [项目生命周期状态机](../protocol/PROJECT_LIFECYCLE.md)。

## 2. 权重与计分规则

| 维度 | 权重 | 可选得分 |
|---|---:|---|
| 商业价值 | 20 | 0、5、10、15、20 |
| 用户需求强度 | 20 | 0、5、10、15、20 |
| 技术可行性 | 15 | 0、3.75、7.5、11.25、15 |
| 开发成本 | 10 | 0、2.5、5、7.5、10 |
| 数据资产价值 | 15 | 0、3.75、7.5、11.25、15 |
| 复用价值 | 10 | 0、2.5、5、7.5、10 |
| 战略价值 | 10 | 0、2.5、5、7.5、10 |
| **合计** | **100** | **0–100** |

每个维度只使用五个锚点：`0%`、`25%`、`50%`、`75%`、`100%`。

设第 `i` 个维度权重为 `Wᵢ`，锚点比例为 `Aᵢ ∈ {0, 0.25, 0.5, 0.75, 1}`：

`维度得分 Dᵢ = Wᵢ × Aᵢ`

`项目总分 S = ΣDᵢ`

保留锚点产生的精确小数，汇总时不逐项四舍五入；总分以最多两位小数报告。若现状介于两个锚点之间，选择较低锚点，除非有明确证据支持较高锚点。不得自行使用锚点之外的分数。

“开发成本”采用反向成本评分：成本越低、交付越快、长期负担越小，得分越高。其余维度均为价值或可行性越高，得分越高。

## 3. 通用评分步骤

1. 固定评估对象、范围、时间窗口和关键假设，避免不同范围的候选直接混评。
2. 为每个维度收集可追溯证据，注明来源、日期，并区分事实与推断。
3. 按本模型的五档标准选择锚点。
4. 每个维度记录得分、一句话判断依据、证据、关键假设和待验证项。
5. 汇总总分，再单独报告 Confidence 与风险红线。
6. 将总分用于候选排序或资源讨论，将立项判断交给独立的审批门禁。

不同维度不得重复计算同一价值。例如，收入和成本节约计入商业价值；是否符合长期方向计入战略价值；未来形成的数据飞轮计入数据资产价值。

## 4. 各维度评分标准

### 4.1 商业价值（20 分）

衡量项目带来的收入、成本节约、风险损失降低或可量化任务价值，不把战略协同重复计入本维度。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 没有可识别的净价值，或预期损失明显高于收益 |
| 25% | 5 | 价值方向成立但影响局部、规模很小，或收益机制尚不清晰 |
| 50% | 10 | 有明确受益对象和可量化机制，预计收益可覆盖主要投入 |
| 75% | 15 | 对目标业务有显著影响，收益规模、时间窗口和实现路径较清晰 |
| 100% | 20 | 可带来持续、规模化、变革性的经济或任务价值，且边际收益显著 |

判断依据：

- 当前收入、成本、损失或任务基线。
- 预计影响范围、单次价值、发生频率和实现时间。
- 付费意愿、单位经济性、预算或业务负责人承诺。
- 收益是否可持续，以及是否会被新增运营成本抵消。

示例：客服分流助手预计每月节省 300 小时，按现有人工成本计算收益显著，但尚未验证生产环境节省率，评分 `15/20`。

### 4.2 用户需求强度（20 分）

衡量问题的频率、严重程度、覆盖人数、替代方案满意度以及用户采取行动的意愿。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 无明确用户或问题，用户没有使用意愿 |
| 25% | 5 | 偶发、轻微的“锦上添花”需求，现有方案基本足够 |
| 50% | 10 | 问题重复出现并影响效率或体验，但仍可接受现有替代方案 |
| 75% | 15 | 高频且明显痛苦，用户已主动寻找、购买或搭建替代方案 |
| 100% | 20 | 关键任务被持续阻断，现有方案不可接受，用户表现出强烈且紧迫的行为承诺 |

判断依据：

- 用户访谈、工单、搜索、使用日志和流失原因。
- 问题发生频率、严重度、持续时间和受影响用户比例。
- 用户当前投入的时间、金钱和绕行成本。
- 试用、预订、付费、迁移或提供数据等行为证据。

示例：工单日志显示 70% 的客服每天手工归类问题，12 名一线用户均在维护个人表格绕行，评分 `15/20`。

### 4.3 技术可行性（15 分）

衡量在现有技术、团队能力、系统约束和运行要求下实现目标的可行程度。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 违反硬约束，或在目标环境中没有可信实现路径 |
| 25% | 3.75 | 理论上可能，但存在未解决的基础能力、接口或性能阻碍 |
| 50% | 7.5 | 有合理方案，关键集成、质量、规模或安全问题仍未验证 |
| 75% | 11.25 | 关键路径已通过原型或同类实践验证，剩余问题可管理 |
| 100% | 15 | 目标环境端到端路径已验证，依赖、边界、性能和运维方案均明确 |

判断依据：

- 原型、技术实验、基准测试和同类生产案例。
- API、数据、权限、模型、基础设施和供应商依赖。
- 团队经验、关键能力缺口和学习成本。
- 性能、可靠性、安全性、可观测性和回滚要求。

示例：客服系统 API 已打通，分类原型达到目标准确率，但生产权限和峰值吞吐仍待验证，评分 `11.25/15`。

### 4.4 开发成本（10 分）

衡量从建设到维护的总投入。分数越高表示成本越低，而不是项目规模越大。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 明显超出预算、时间或团队容量，或成本边界无法估计 |
| 25% | 2.5 | 需要长期专门团队、新基础设施或高额外部采购，投入与价值不成比例 |
| 50% | 5 | 可在计划资源内交付，但开发、集成和长期维护负担显著 |
| 75% | 7.5 | 小团队可在较短周期交付，新增依赖和运维负担有限 |
| 100% | 10 | 主要通过已有能力复用或配置完成，边际开发和维护成本极低 |

判断依据：

- 人日、周期、角色数量和并行项目机会成本。
- 集成数量、迁移工作、测试范围和上线复杂度。
- 云资源、模型调用、许可证和供应商费用。
- 维护、监控、支持、合规和退出成本。

示例：两名工程师预计四周完成，复用现有鉴权和日志能力，仅新增一个受控集成，评分 `7.5/10`。

### 4.5 数据资产价值（15 分）

衡量项目能否合法、持续地形成高质量、可复用、具有差异化的数据资产或反馈闭环。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 不产生有用数据，或数据权利、合规或质量问题使其不可用 |
| 25% | 3.75 | 只产生短期、通用或高度噪声的数据，难以留存和复用 |
| 50% | 7.5 | 可形成结构化数据并支持分析或优化，但独特性和复用途径有限 |
| 75% | 11.25 | 数据权利和治理明确，数据随使用持续增长并改善产品效果 |
| 100% | 15 | 形成难以复制的高质量数据飞轮，能持续提升多项产品能力或防御力 |

判断依据：

- 数据来源、授权、隐私、保留期限和可迁移性。
- 数据规模、质量、标注成本、更新频率和代表性。
- 是否能形成反馈闭环并改善模型、流程或决策。
- 对其他项目的可用性、独特性和替代难度。

示例：项目可沉淀经脱敏的意图标签和纠错反馈，授权与保留规则明确，可持续提升分类质量，但数据规模尚未验证，评分 `11.25/15`。

### 4.6 复用价值（10 分）

衡量产出的组件、接口、流程、知识或基础设施能否被其他已知项目重复使用。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 完全一次性实现，不能合理复用 |
| 25% | 2.5 | 只有少量代码或经验可借鉴，且与当前场景高度耦合 |
| 50% | 5 | 可抽取模块或流程，至少有两个明确的潜在复用场景 |
| 75% | 7.5 | 可形成有稳定接口的共享组件或服务，多个已知项目有现实需求 |
| 100% | 10 | 可成为平台级基础能力，覆盖广泛且已有明确采用计划和维护责任 |

判断依据：

- `projects/` 和项目记忆中的实际需求，不以抽象“可能复用”代替。
- 组件边界、接口稳定性、配置能力和耦合程度。
- 接入成本、文档、测试、版本兼容和维护责任。
- 可复用对象的数量、时间窗口和采用承诺。

示例：意图分类服务可通过统一 API 服务三个已知项目，接口和维护责任可明确，但尚未成为平台标准，评分 `7.5/10`。

### 4.7 战略价值（10 分）

衡量项目与当前长期目标、核心能力建设、差异化定位和关键时间窗口的匹配程度。

| 锚点 | 得分 | 评分标准 |
|---:|---:|---|
| 0% | 0 | 与当前战略冲突，或会分散关键资源并削弱核心方向 |
| 25% | 2.5 | 与战略仅有间接关系，主要是机会性尝试 |
| 50% | 5 | 明确支持一个当前目标，但不是关键路径 |
| 75% | 7.5 | 直接推进优先战略，补齐重要能力缺口，并与其他项目形成协同 |
| 100% | 10 | 是核心战略不可替代的关键能力，具有明确时效性、差异化或长期防御价值 |

判断依据：

- 已确认的路线图、年度目标、用户稳定偏好和能力缺口。
- 与现有项目组合的协同、替代或资源冲突。
- 时间窗口、竞争差异化、关键依赖和长期选择权。
- 是否有明确战略负责人和持续投入意愿。

示例：客服自动化是当前优先方向，该项目补齐通用意图识别能力并服务多个计划，但不是唯一关键路径，评分 `7.5/10`。

## 5. 证据不足的处理

### 5.1 不编造，也不默认取中值

每个锚点都必须有判断依据。只有 AI 推测、没有任何可引用事实时，该维度标记为 `NE（No Evidence）`，不得为了凑总分默认给 50%。

### 5.2 区分正式总分与暂定下界

- 七个维度都有可辩护的数值时，计算正式总分。
- 存在 `NE` 时，不发布正式总分；可为排定调研顺序计算“暂定下界”，将 `NE` 按 0 计入。
- 暂定下界必须写成“至少 X/100，N 个维度证据不足”，不得与完整评分的项目直接排名。

`NE` 不等于已经证明该维度价值为零。补充证据后重新选锚点，并保留评分变化原因。

### 5.3 把缺口转化为验证动作

对每个 `NE` 或低证据维度记录：

- 缺少的事实或数据。
- 最小验证方式。
- 负责人或信息来源。
- 复评触发条件。

若高分依赖未经验证的关键假设，应保留当前最佳估计，同时显式标注该假设并降低相应结论的 Confidence；不得把假设写成事实。

## 6. Confidence 与分数分离

项目分数表示当前对价值、需求、可行性、成本和协同的估计；Confidence 表示这些估计被证据支持的可信程度。两者必须分别报告：

- Confidence 不加入 100 分，也不作为第八个评分维度。
- 不使用“总分 × Confidence”生成混合分。
- 低 Confidence 不自动改写维度锚点，但会触发补证、调研或门禁阻断。
- 同为 `75/100` 的两个项目，可以因 Confidence 不同而获得不同的下一动作。

示例输出：

> 总分：`75/100`  
> Confidence：按 Confidence Model 单独评定  
> 关键证据缺口：生产节省率、峰值吞吐  
> 风险红线：未触发，但数据权限待关闭  
> 建议：先完成限定范围验证，不视为自动立项

## 7. 风险红线

风险红线不属于 100 分，不能被任何维度的高分抵消。至少检查：

- 法律、监管、合同或平台规则禁止的行为。
- 未经授权处理敏感数据、个人信息或受限数据。
- 不可接受且无有效缓解措施的安全、隐私或人身风险。
- 知识产权、许可证或数据使用权存在阻断性问题。
- 关键操作不可回滚、不可审计，可能造成重大不可逆损害。
- 对单一不可控依赖的失败没有替代、降级或退出方案。

红线状态使用：

- `未触发`：已有证据表明当前范围不触发红线。
- `待确认`：信息不足，必须先完成调查。
- `已触发`：存在阻断性风险，且尚无获准的消除方案。

出现 `待确认` 或 `已触发` 时，仍可保留评分用于说明机会成本，但决策状态必须标记为“阻断”，不得仅凭高总分进入 `DESIGN`。风险关闭、例外批准和最终阶段门禁以 Project Approval Gate 为准，并保留可追溯证据。

## 8. 评估输出要求

每次项目评估至少输出：

| 项目 | 必填内容 |
|---|---|
| 评估范围 | 候选名称、版本、包含与不包含的范围 |
| 维度评分 | 七个维度的锚点、得分和一句话判断 |
| 证据 | 来源、日期、事实与推断的区分 |
| 关键假设 | 会显著改变分数的假设及验证方式 |
| 总分 | 正式总分，或带 `NE` 数量的暂定下界 |
| Confidence | 按独立 Confidence Model 记录 |
| 风险红线 | 未触发、待确认或已触发，并附依据 |
| 下一动作 | 补证、调研、暂缓、进入审批或重新定义范围 |

## 9. 汇总示例

以“客服工单分流助手”为例：

| 维度 | 得分 |
|---|---:|
| 商业价值 | 15 |
| 用户需求强度 | 15 |
| 技术可行性 | 11.25 |
| 开发成本 | 7.5 |
| 数据资产价值 | 11.25 |
| 复用价值 | 7.5 |
| 战略价值 | 7.5 |
| **总分** | **75/100** |

该分数表示项目在当前证据下具有较高的比较价值，不表示已获准立项。仍须单独检查 Confidence、风险红线、Research 与 Evaluation 完成状态，并取得用户明确的立项决定。
