# AI 评测标准

## 1. 目的与强制边界

本标准规定含 AI 能力项目在 Phase 6 中如何评测输出质量、准确率、稳定性、幻觉风险、Prompt 效果、Agent 成功率、Token 成本和响应时间，并要求所有结论绑定精确模型、Prompt、工具、数据集、环境与代码版本。

AI 项目不能只依赖传统功能测试。功能测试可以证明接口可调用、流程可运行或格式正确，但不能单独证明输出有用、事实可靠、多次运行稳定、Prompt 有效、Agent 能完成目标、幻觉风险可接受或成本和时延受控。AI 评测必须作为[测试策略标准](./TEST_STRATEGY_STANDARD.md)中的正式 Phase 6 测试，与系统、安全、权限、数据、恢复和 UAT 共同执行。

本标准保持模型提供方、平台、框架、评测库和 Agent 实现中立，不规定任何具体 Agent 代码。

## 2. 适用性与可审计 N/A

只要当前批准范围的用户结果、业务判断、安全控制或质量声明依赖模型推理、生成式输出、分类 / 评分、检索增强、Embedding、重排、Prompt 编排、工具调用或自主任务流程，本标准即适用。

对适用的 AI 项目，八个强制维度均不得标记 N/A：

- 没有自主 Agent 时，“Agent 成功率”按完整 AI 任务或编排工作流成功率评测；
- 没有自然语言 Prompt 时，“Prompt 效果”按模型输入模板、指令、特征构造或推理配置的效果评测；
- 某维度风险较低时可以设置与风险相称的阈值和样本，但不能省略该维度。

只有经事实核验确认当前项目不含任何 AI 决策或 AI 输出依赖的非 AI 项目，才能申请项目级 N/A。N/A 记录必须包含：

| 字段 | 要求 |
|---|---|
| N/A Record ID | 稳定唯一标识与不可覆盖版本 |
| 当前范围与基线 | 项目范围版本、Repository、Base SHA、HEAD SHA、文档版本 |
| 适用性声明 | 明确声明当前范围不依赖 AI 能力，而不是只写“无 AI” |
| 核验边界 | 已检查的模块、依赖、数据流、外部服务、配置、用户流程和运行路径 |
| 事实 Evidence | 依赖清单、架构 / 数据流检查、代码或配置查询、执行日志及其他可复核链接 |
| 责任与批准 | 申请人、独立领域评审人、批准人和含时区时间戳 |
| 复核触发器 | 新模型、AI 服务、Prompt、Embedding、智能排序、生成输出、工具编排或范围 / 依赖变化 |
| 状态 | `PROPOSED`、`APPROVED`、`REJECTED` 或 `SUPERSEDED` |

只有 `APPROVED`、指向当前精确基线且复核触发器未发生的 N/A 有效。未找到模型调用但没有检查外部服务、配置和数据流，不足以批准 N/A。N/A 不能由作者单独批准，也不能作为 AI 评测 PASS。

## 3. 评测原则

1. 先定义用例、数据集、统计口径和阈值，再运行候选系统；不得看到结果后改阈值。
2. 所有候选与对照使用同一批准数据、重复次数、工具权限和统计方法，除非差异本身就是评测变量。
3. 原始运行全部保留。失败、拒答、超时、工具错误和高成本运行不能被静默删除或只选择最佳结果。
4. 总体平均值不能掩盖关键用户、语言、领域、风险或攻击分片失败。
5. 自动评分不能单独评判它无法可靠度量的主观质量、事实依据或高风险影响；必须结合人工评测。
6. 评测结果只对绑定的版本组合有效，任何影响行为的版本变化都触发影响分析和重评。
7. 八个强制维度逐项通过；不允许用一个高分抵消另一个失败项。

## 4. Evaluation Baseline 版本绑定

每次正式评测创建唯一 Evaluation ID，并在运行前冻结 Evaluation Baseline。至少绑定：

| 对象 | 必填版本信息 |
|---|---|
| 项目与追踪 | Requirement ID、Design ID、Task ID、Test Case ID、Chain ID、评测风险与验收标准 |
| 代码与构建物 | Repository、Branch、Base SHA、HEAD SHA、构建物标识、配置版本 |
| 模型 | 模型标识、精确版本 / 快照、提供方式、推理参数、随机性参数、上下文限制和安全配置 |
| Prompt | System / Developer / User 指令、模板、示例、输出 Schema 的版本或内容哈希，以及组合顺序 |
| 工具 | 工具清单、接口 / Schema 版本、权限、超时、重试、幂等与副作用控制 |
| 检索与记忆 | 索引 / 知识库版本、语料快照、切分与召回配置、缓存和记忆状态 |
| 数据集 | Dataset ID、版本 / 内容哈希、切分、样本数、分片、Gold / Rubric 版本和授权 |
| 环境 | Environment ID、运行时、依赖、地域、网络、限流、并发、时钟和硬件 / 资源类别 |
| 执行控制 | Evaluation Plan 版本、重复次数、种子策略、案例顺序、超时、失败重试和证据位置 |
| 责任 | Evaluation Owner、Dataset Owner、Prompt / Model Owner、执行人、人工评审人和批准人 |

“默认模型”“当前 Prompt”“最新数据集”“线上环境”等可变引用不合格。不能取得不可变模型快照时，必须记录提供方返回的精确模型标识、采集时间、所有可观察参数和漂移监控；漂移发生后旧结果标记为 `INVALIDATED`。

模型、Prompt、工具定义或权限、检索语料、数据集、环境、代码 Commit、推理参数、Rubric 或统计方法任一变化，都形成新的 Evaluation Baseline。旧运行保留，但不得继续证明新基线。

## 5. 阈值预注册

每个强制维度必须在任何正式运行开始前写入 Threshold Register，并由 Evaluation Owner、业务 / 产品责任人和适用领域评审人批准。阈值必须是具体数值、布尔条件、范围或相对基线界限；“表现良好”“尽量低”“不明显退化”均无效。

Threshold Register 每行必须包含 Metric ID、维度、关联 Requirement / Risk、公式、单位、分母、数据集与分片、样本量、重复次数、聚合方法、阈值与比较符、置信区间判定、关键失败上限、批准人和批准时间。批准时间必须早于第一条正式 Run 的开始时间。

用于选阈值的 Pilot / Calibration 数据必须与正式 Evaluation 数据隔离并单独版本化。看到正式结果后确需改变目标时，必须先完成需求 / 风险变更批准，创建新的 Threshold Register 与 Evaluation ID，并把旧结论保留为历史 `FAIL` 或 `INVALIDATED`；不得追溯改写为 PASS。

## 6. 八个强制维度

| 维度 | 必须预定义的度量与口径 | 阈值要求 |
|---|---|---|
| 输出质量 | 基于批准 Rubric 的正确性、相关性、完整性、清晰度、格式 / 风格和任务特有质量；记录量表锚点、人工与自动评分关系 | 预设总体最低分、每个关键分片最低分、低质量样本上限和任何一票失败条件 |
| 准确率 | 按任务选择 Exact Match、正确案例率、Precision、Recall、F1、排序 / 数值误差等；分母包含所有计划有效尝试 | 预设主指标最低值、关键类别最低值、容差与 95% 置信区间判定 |
| 稳定性 | 同一案例独立重复运行的成功一致性、输出类别一致率、分数方差、极差或关键事实一致性 | 每案例至少 3 次运行；预设最小一致率、最大方差 / 极差及关键分片要求 |
| 幻觉风险 | 不受批准来源支持的可验证主张数 ÷ 全部可验证主张数，同时记录错误引用、捏造来源和关键幻觉数量 | 预设总体与分片最大比率；会造成严重安全、法律、财务、隐私、数据或不可逆影响的关键幻觉允许数固定为 0 |
| Prompt 效果 | 候选 Prompt / 输入配置相对冻结对照的任务成功、质量、准确、拒答、格式错误与安全结果差异 | 预设最小改善值或非劣界限，并为每项关键指标设置不得退化的边界 |
| Agent 成功率 | 无未授权人工救援、无未授权副作用且满足全部终态验收的完整 AI 任务数 ÷ 全部计划任务尝试数 | 预设总体与关键任务最低成功率、最大重试 / 人工接管率；未授权工具动作或不可逆副作用允许数固定为 0 |
| Token 成本 | 每次任务输入、输出、缓存、推理和工具相关 Token；报告总量、每尝试、每成功任务、失败消耗、P50 / P95 | 预设每成功任务与 P95 上限、总预算上限和异常消耗上限；不能只报告成功样本 |
| 响应时间 | 从接收完整请求到最终可用结果的端到端时间，并单列模型、工具、检索、排队和重试时间；报告 P50 / P95 / 最大值和超时率 | 预设 P50 / P95、最大可接受时限与超时率上限；明确冷启动、并发和流式首响应是否另行计量 |

项目可以增加安全、公平性、鲁棒性、越权、敏感数据、注入、拒答、可解释性或业务指标，但不能删除上述八项。每个 Metric 必须指向至少一个 Test Case 和 Evidence 位置。

## 7. 评测数据集

正式 Dataset 必须版本化并记录：

- 数据来源、授权、许可、时间范围、语言 / 地域 / 用户分布、去重方法和内容哈希；
- Train / Tune / Calibration / Evaluation 的隔离方式，以及防止 Prompt、开发者或自动优化过程看到 Gold 的控制；
- 样本选择、总体代表性、正常 / 边界 / 失败 / 对抗案例和已知限制；
- Gold Answer、可接受答案集合或 Rubric 的产生方法、评审人、版本与争议处理；
- 关键分片及其样本数，包括高风险、长尾、语言、领域、权限、工具副作用和历史失败；
- 个人信息、机密、版权、保留、脱敏、访问日志和删除要求；
- 数据生成参数、随机种子、顺序和每次运行前的状态重置方法。

Evaluation 数据不得在评测过程中根据候选表现增删。发现标签错误时必须保留原版本、登记 Data Issue、由 Dataset Owner 独立批准修订，并对所有候选在新数据版本上完整重跑，不能只重跑失败候选。

## 8. 重复运行协议

每个正式评测案例必须进行至少 3 次相互独立的重复运行。声称配置确定性也必须通过重复运行证明；需要更多次数的高方差或高风险任务由 Threshold Register 预先规定。

重复运行必须：

1. 为每次尝试分配唯一 Run ID，记录案例、重复序号、种子或随机性参数；
2. 在运行前按批准方法重置会话、记忆、缓存、数据和工具副作用；
3. 使用预先固定或可复现随机化的案例顺序，避免候选间顺序偏差；
4. 对所有候选采用相同并发、限流、超时和重试策略；
5. 保存每一次原始输入、输出、工具轨迹、来源引用、Token、时延、错误和终态；
6. 将拒答、格式错误、超时、工具失败、人工接管和副作用计入预定口径；
7. 禁止只保留最佳运行、把重复运行当作多次机会后择优，或在没有预注册规则时多数投票改写单次结果。

工具可能产生写入、消息、交易或其他外部副作用时，评测必须在经批准的隔离环境或可逆控制下运行，记录每个动作和回滚结果。无法安全隔离时结果为 `BLOCKED`，不能绕过该案例。

## 9. 人工评测

输出质量、开放式准确性、幻觉、业务可用性或其他无法由确定性规则充分判断的指标必须包含人工评测。Human Evaluation Plan 在运行前至少冻结：

- Rubric 维度、量表、每个分值的正反例锚点和一票失败条件；
- 样本选择方法、样本量、关键分片和案例展示顺序；
- 评审人资格、利益冲突、培训 / 校准集和访问权限；
- 盲评方式；评审人不应看到候选名称、预期商业结论或其他评审人的评分；
- 分歧、弃权、无法判断和升级给领域专家的规则；
- 一致性统计、通过阈值、裁决人和 Evidence 保留方式。

主观主指标和高风险样本至少由两名合格评审人独立评分。关键高风险分片必须逐项人工复核；其他分片可以采用预先批准的抽样，但不能在看到自动分数后只挑选有利样本。报告必须给出评审人间一致性；低于阈值时先校准或裁决并保留原评分，不能静默平均。

人工评测涉及敏感内容时，必须执行最小暴露、脱敏、心理安全、审计与保留控制。人工偏好不能取代 Requirement 或事实来源。

## 10. 统计口径

### 10.1 统一分母

计划尝试总数为批准 Evaluation Case 数 × 每案例预注册重复次数。所有已开始的有效尝试均进入分母，包括错误输出、拒答、超时、工具失败和需要未授权人工救援的尝试。

基础设施故障只有在预注册规则判定确实未到达被测系统时才可标记为 `INVALIDATED` 并重跑；原 Run 仍须保留并单列数量、原因和 Evidence。不得把困难样本、低分、长时延或高 Token 消耗解释为无效样本。

### 10.2 聚合与分片

每项指标同时报告总体和预注册关键分片的样本数、实际值与阈值。采用 Macro、Micro、加权平均、Top-k、容差区间或自定义评分时必须在执行前说明公式和权重。任何关键分片失败都使该 Metric `FAIL`，即使总体平均通过。

### 10.3 不确定性与重复性

比例指标报告 95% 置信区间。最低要求型指标使用预注册的保守判定，通常要求置信区间下界达到阈值；风险上限型指标通常要求上界不超过阈值。若项目采用其他统计判定，必须在运行前写明理由、方法和批准人。

稳定性至少报告每案例和总体的一致率、均值、标准差或适用离散度，以及重复运行中最差结果。人工评分报告评审人间一致性和裁决数量。报告均值时同时报告样本数与分布，不得只给单一平均值。

### 10.4 成本与时延

Token 成本至少报告总 Token、每次尝试、每个成功任务、失败尝试消耗、P50、P95 和预算占用；货币换算如被使用，必须绑定价格表版本和币种。响应时间使用端到端同一计时边界，报告 P50、P95、最大值、超时率和样本并发条件。

## 11. 运行状态与失败处理

Evaluation Run Result 使用与[测试策略标准](./TEST_STRATEGY_STANDARD.md)一致的词汇：

| Result | 含义 |
|---|---|
| `NOT_RUN` | 当前 Evaluation Baseline 尚无有效正式运行 |
| `PASS` | 当前案例或 Metric 的所有预设判定均满足，Evidence 完整 |
| `FAIL` | 至少一个预设判定未满足或发生一票失败事件 |
| `BLOCKED` | 前置环境、数据、权限或安全控制不满足，无法完成 |
| `INVALIDATED` | 结果因版本、方法、数据或 Evidence 变化不再证明当前基线 |

任一强制 Metric 或关键分片低于阈值，整体 AI Evaluation 必须为 `FAIL`；不得使用加权总分、人工解释或其他指标余量抵消。关键幻觉、未授权工具动作、敏感数据违规或不可逆副作用一旦发生，立即停止相关运行、保留 Evidence、登记 Bug 并按影响分级。

失败后必须：

1. 按[缺陷管理标准](./BUG_MANAGEMENT_STANDARD.md)创建 Bug ID，关联 Evaluation ID、Run ID、Test Case、五层 Chain 和 Evidence；
2. 区分模型、Prompt、工具、数据、环境、代码、Rubric 或统计方法的根因，不以“模型波动”代替分析；
3. 形成修复 / 缓解、回滚和防复发方案；代码或配置修复遵守 TDD 和 Review；
4. 更新受影响版本并创建新的 Evaluation Baseline；
5. 重跑失败案例、全部受影响分片、核心回归和 Threshold Register 要求的完整集合；
6. 保留旧 `FAIL` / `INVALIDATED` 记录，禁止覆盖或只展示新结果。

`BLOCKED`、`NOT_RUN` 或 `INVALIDATED` 不能视为通过。P0 Blocker 或 P1 Critical Bug 按[缺陷管理标准](./BUG_MANAGEMENT_STANDARD.md)阻断 Testing PASS 和发布。

## 12. Evidence 要求

每个 Evaluation 必须建立可访问、访问受控且不可覆盖的 Evidence Package，至少包含：

- Evaluation ID、Test Case、Requirement / Design / Task / Commit / Chain 与 Threshold Register；
- 模型标识和参数、完整 Prompt 组合、工具 Schema / 权限、检索 / 记忆配置；
- Dataset、Gold、Rubric、Environment、代码和依赖的版本 / 哈希；
- 每个 Run 的输入、原始输出、引用来源、工具调用与副作用、状态转换、错误、Token、时延和时间戳；
- 自动评分程序或计算说明、原始逐样本分数、聚合公式、分片结果和置信区间；
- 人工评审人的匿名稳定标识、资格、原始评分、意见、一致性、分歧与裁决；
- 失败、Blocker、Bug、修复、重跑、回归和版本失效记录；
- 敏感信息脱敏、访问、保留、完整性校验和 Evidence 采集责任人。

摘要图表或排行榜不能替代逐 Run 原始 Evidence。不能保存敏感原文时，必须保存经批准的脱敏记录、内容哈希、访问审计和可由授权评审人复核的受控原件位置。

## 13. 角色与独立性

| 角色 | 职责 |
|---|---|
| Evaluation Owner | 冻结计划、基线、阈值、重复运行、统计口径和总报告 |
| Model / Prompt Owner | 提供版本、设计意图、变更记录与修复，不得单独批准自己的评测结果 |
| Tool / Environment Owner | 证明工具权限、副作用控制、环境版本、可恢复性和运行就绪 |
| Dataset Owner | 管理来源、切分、Gold、分片、泄漏、隐私与版本变更 |
| Evaluation Executor | 按冻结协议运行并完整保存所有尝试，不选择性删除结果 |
| Human Evaluator | 按盲评 Rubric 独立评分，声明资格和利益冲突 |
| Domain / Safety Reviewer | 复核事实、安全、隐私、合规、数据或其他高风险结果 |
| Business / Product Owner | 批准业务阈值、关键分片和 Agent / 工作流成功定义 |
| Test Owner | 将 AI 评测并入 Phase 6 Test Report，核对 Bug 与回归闭环 |

高风险输出、关键幻觉、安全、隐私与工具副作用的最终结论必须有独立领域评审；自动评测器、模型自评或单一输出所有者不能单独批准。

## 14. Evaluation Report 与最终判定

Evaluation Report 必须记录：

- Evaluation Baseline 中所有版本、责任人、批准时间和相对 Evidence 链接；
- 八个强制维度的 Metric、阈值、样本 / 分片、重复次数、统计口径、实际值、置信区间和 Result；
- 每次运行结果数量，包括 `NOT_RUN`、`PASS`、`FAIL`、`BLOCKED`、`INVALIDATED`；
- 人工评测样本、评审人一致性、分歧与裁决；
- Bug、关键失败、重开、修复、回归和剩余风险；
- Token 总量 / 每成功任务成本、响应时间分布、超时和失败消耗；
- 已知限制、数据代表性、环境差异和结果可推广边界；
- 最终 `PASS` 或 `FAIL`、Evaluation Owner、独立评审人、Test Owner、批准人和时间。

AI Evaluation 最终结论只有 `PASS` 或 `FAIL`。只有八个强制维度及其关键分片全部达到预设阈值、所有必跑 Run 完成、Evidence 完整、关键一票失败事件为 0、未关闭 P0 Blocker / P1 Critical Bug 为 0，才能为 `PASS`。任何维度 `FAIL` / `BLOCKED` / `INVALIDATED`，或仍有 `NOT_RUN`，最终结论均为 `FAIL`。

AI Evaluation `PASS` 不能替代系统测试、安全测试、UAT 或 Release 授权；项目级非 AI N/A 也不能记录为 AI Evaluation PASS。

## 15. 审计检查

评审人必须确认适用性判定有效，八个维度齐全，阈值早于正式运行批准，模型 / Prompt / 工具 / 数据集 / 环境 / Commit 精确绑定，每案例至少三次独立运行，人工评测与统计口径可复算，失败未被筛除，Bug 与重跑闭环完整，Evidence 可访问，状态词汇合法。任一项不满足时评测不能通过。
