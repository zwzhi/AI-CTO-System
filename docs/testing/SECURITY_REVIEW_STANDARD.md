# 安全评审标准

## 1. 目的与适用范围

本标准规定候选版本在 Testing 与发布准备期间必须执行的安全评审，包括输入基线、责任角色、六类强制检查、证据要求、硬阻断、唯一结果、复审与基线失效规则。它适用于代码、配置、依赖、数据、接口、部署定义、运行手册以及会改变系统安全边界的文档或流程变更，并保持对代码托管、测试、部署和云平台中立。

本标准遵循 [项目生命周期](../protocol/PROJECT_LIFECYCLE.md) 与 [阶段门禁检查清单](../evaluation/PHASE_GATE_CHECKLIST.md)，并与 [Development Approval Gate](../development/DEVELOPMENT_APPROVAL_GATE.md) 和 [ADR-0005](../adr/ADR-0005-TESTING-AND-RELEASE-AUTHORIZATION.md) 一致。

安全评审只判断冻结候选基线的安全状态。安全结果为 `APPROVED` 不等于测试完成、用户验收完成、`READY_FOR_RELEASE`、生产部署批准或已发布；发布仍须通过 [Release Approval Gate](../release/RELEASE_APPROVAL_GATE.md) 和 [Testing Release Gate](../release/TESTING_RELEASE_GATE.md)。

## 2. 评审边界与基本原则

1. **精确基线**：评审必须绑定唯一候选版本，不接受“当前版本”“最新版”或仅指向可变分支的记录。
2. **逐项结论**：API Key、用户数据、权限、第三方、数据存储和日志敏感信息六类检查必须分别记录结论与证据，不能用总分抵消单项失败。
3. **最小权限与最少数据**：权限、密钥、用户数据和日志均以完成批准目的所需的最小范围为上限。
4. **证据优先**：声明、演示、自动扫描无告警或历史批准不能代替当前基线的可复核证据。
5. **禁止条件批准**：不存在口头批准、默认批准、部分批准、限期后自动批准或“发布后修复”。
6. **风险接受有边界**：有权限的风险接受人只能接受不触发硬阻断的剩余风险，不能接受密钥泄露、越权、用户数据泄露、违法处理或其他安全红线。

## 3. 角色与职责

| 角色 | 职责 |
|---|---|
| Security Review Owner | 冻结评审基线，组织六类检查，确认发现、硬阻断和唯一结果，保存不可覆盖记录 |
| Security Reviewer | 独立核验威胁、控制与证据；对发现分级并确认修复后的复测结果 |
| System / Development Owner | 提供架构、数据流、依赖、配置、变更和控制说明；按发现完成修复，不批准自己的高风险例外 |
| Data Owner / Privacy Owner | 确认用户数据分类、处理目的、保留、删除、共享和适用义务 |
| Access Owner | 确认身份、角色、服务账号和管理权限边界，批准最小权限矩阵 |
| Operations Owner | 提供密钥管理、存储、日志、备份、恢复、监控与事件响应证据 |
| Third-party Owner | 维护外部服务、组件和数据接收方清单，证明权限、版本、风险与退出控制 |
| Risk Acceptance Owner | 仅在授权范围内接受非硬阻断剩余风险，并记录期限、监控、责任人与重审触发器 |

高风险范围必须由具备相应能力且与实现责任保持足够独立的评审人检查。自动化工具可提供证据，但不能独立给出 `APPROVED`。

## 4. 评审基线与强制输入

发起评审前必须冻结并记录以下输入：

1. Security Review Record ID、项目、评审范围、评审时间、Owner 与 Reviewer。
2. 候选版本标识，包括源版本或内容摘要、构建产物摘要、配置版本、依赖清单、数据 Schema / 迁移版本和目标环境标识；不适用项须按第 5 节记录。
3. 当前批准的 Requirement、Architecture、Database / Agent Design、适用 ADR、数据流和信任边界。
4. 自上次安全评审或批准基线以来的完整变更清单及影响分析。
5. 数据清单与分类、处理目的、数据流向、存储位置、保留与删除规则、第三方共享关系。
6. 身份、角色、权限、服务账号、管理入口、租户 / 对象边界和例外权限矩阵。
7. API Key、密钥、令牌、证书和其他凭据清单；记录用途、Owner、权限范围、保存位置、轮换与吊销状态，但不得在评审记录中写入秘密值。
8. 第三方服务、库、模型、SDK、API、数据处理者和外部日志 / 监控接收方清单及精确版本或合同基线。
9. 存储、加密、备份、恢复、数据迁移、日志、审计、脱敏和事件响应控制说明。
10. 当前基线实际执行的安全测试、权限测试、数据保护验证、依赖 / 漏洞检查、秘密扫描和日志抽样证据。
11. 安全发现登记表，包含 Finding ID、严重度、影响、复现条件、Owner、状态、修复版本、验证证据和剩余风险。
12. 先前评审记录、已接受剩余风险及其到期日、监控信号和重审触发器。

任一强制输入缺失、不可访问、版本不明、相互冲突或未指向同一候选基线时，不得给出 `APPROVED`。

## 5. 证据与 N/A 要求

每项证据至少包含：Evidence ID、对应检查项、精确候选基线、方法或命令类别、执行环境、执行人、时间、输入、预期结果、实际结果、原始记录位置和 PASS / FAIL 结论。证据必须可访问、可复核、不可被无痕覆盖，并避免在证据本身复制秘密或用户敏感数据。

以下材料可以作为证据的一部分，但不能单独证明安全通过：无上下文截图、工具汇总分数、未记录规则与排除项的扫描结果、作者自述、历史版本结果和只证明正常路径的演示。

仅当当前范围在事实层面不触发某项子检查时才能使用 N/A。每个 N/A 必须记录检查边界、当前基线、事实依据、已核验的数据流或调用、领域评审人、批准时间和复核触发器。六类强制检查本身不能整体标记为 N/A；例如没有第三方时，仍须提供依赖与外联清单为空的核验证据。

## 6. 六类强制安全检查

### 6.1 API Key、密钥与凭据

- 建立 API Key、访问令牌、证书、签名密钥、数据库凭据、Webhook Secret 和服务账号凭据的完整清单，并明确 Owner、用途、环境和到期 / 轮换规则。
- 凭据不得出现在源文件、配置模板、构建产物、测试数据、问题记录、日志、错误响应、文档示例或可恢复的版本历史中；秘密扫描须覆盖候选差异及适用历史范围。
- 凭据必须由受控的秘密存储或等价机制注入，传输和读取受保护，生产与非生产环境隔离，不使用共享个人凭据。
- 每个凭据仅具备必要资源、操作、环境和有效期；高权限凭据有额外审批、使用审计和紧急吊销路径。
- 轮换与吊销流程可执行；发现疑似泄露时，先吊销或隔离，再轮换、调查使用记录并验证旧值失效，不能只从文件删除。
- 测试证据覆盖缺失、过期、错误作用域、被吊销和未授权使用等失败路径，且错误信息不泄露秘密。

### 6.2 用户数据与隐私

- 用户数据按敏感度分类，并记录收集来源、明确目的、合法依据或适用授权、使用者、下游接收方和跨边界流向。
- 仅收集、处理和输出实现批准目的所必需的数据；默认值、遥测、调试、AI Prompt / Context、导出和缓存不得静默扩大范围。
- 用户身份、联系方式、认证信息、行为数据、内容、财务 / 健康等敏感数据按分类执行访问、脱敏、传输、存储和显示控制。
- 保留、查询、更正、导出、删除、匿名化和账号终止路径符合批准需求与适用义务；删除须覆盖副本、缓存和约定范围内的第三方。
- 非生产、演示和测试数据使用合成或充分脱敏数据；使用真实用户数据必须有明确授权、隔离、期限和清理证据。
- 异常响应、批量操作、搜索、导出、共享、租户切换和 AI 输出均验证不会泄露其他用户或超出目的的数据。

### 6.3 身份、权限与越权防护

- 身份验证、会话、角色、资源、操作和管理边界与批准架构一致；默认拒绝，匿名、普通、管理和服务身份边界明确。
- 权限检查在可信执行边界实施，不能只依赖界面隐藏、客户端参数、提示文本或调用者自律。
- 用户、租户、对象、字段和操作级授权均有正向与反向测试，覆盖水平越权、垂直越权、标识符替换、批量接口和间接调用。
- 管理员、紧急账号、服务账号、自动化身份和第三方身份采用最小权限；高权限操作有强认证、审批或等价保护以及可审计记录。
- 会话创建、刷新、失效、退出、密码或密钥变更后的撤销路径已验证；重放、固定、伪造和权限缓存过期风险得到控制。
- AI 或自动化工具调用受明确 allowlist、参数校验、权限边界、预算 / 资源限制和人工接管控制约束，不能通过自然语言绕过授权。

### 6.4 第三方与供应链

- 列出全部第三方服务、开源 / 商业组件、SDK、模型、插件、外部 API、内容源、数据接收方和子处理者，记录版本、Owner、用途与数据 / 权限范围。
- 核验来源、完整性、维护状态、已知漏洞、安全公告和更新策略；锁定可复现版本，不使用来源不明或不可审计的产物。
- 第三方仅接收必要数据和权限；认证、Webhook 签名、回调校验、网络边界、速率限制、错误处理和故障降级符合风险要求。
- 涉及用户数据时，数据用途、保留、区域、再共享、删除、事件通知和退出安排已明确，并与用户承诺及适用义务一致。
- 外部服务中断、响应被篡改、超时、限流、版本变化和账户失陷均有安全失败模式，不因降级绕过权限或泄露数据。
- 已定义替换、禁用、撤销访问和清理数据的退出路径；关键第三方不能只依赖无法验证的营销声明。

### 6.5 数据存储、备份与恢复

- 记录数据库、对象、文件、缓存、队列、搜索索引、向量存储、设备端存储、备份和临时文件中的数据类别、位置和 Owner。
- 敏感数据在传输和静态保存时使用与风险匹配的保护；密钥与数据分离管理，访问最小化并留有必要审计。
- Schema、约束、迁移、并发、完整性和失败恢复已验证；迁移与回滚不得造成静默丢失、重复、跨租户混淆或未授权暴露。
- 保留期限、自动清理、用户删除、法律或业务保留例外可执行且可验证；缓存、备份和副本有明确的一致性与删除边界。
- 备份范围、频率、加密、访问、恢复点和恢复时间目标明确；恢复演练证明可用，且恢复后仍保持权限与数据完整性。
- 非生产副本、导出文件、本地缓存、诊断快照和退役介质受到与其数据分类一致的保护和销毁控制。

### 6.6 日志、错误与敏感信息

- 日志、追踪、指标标签、审计记录、错误消息、崩溃报告、调试输出和第三方可观测平台不得记录 API Key、令牌、密码、Cookie、完整认证头或其他秘密。
- 用户敏感数据只在明确必要且获批准的字段中记录，并按规则掩码、哈希、截断或省略；自由文本、请求 / 响应体、Prompt、工具参数和数据库错误是重点检查对象。
- 生产日志级别、调试开关、采样、字段 allowlist / denylist、错误序列化和堆栈输出已在候选配置中验证，而非只检查默认配置。
- 日志访问遵循最小权限，导出与第三方接收方有数据边界；保留、删除、防篡改、时间同步和审计查询符合安全与运营要求。
- 使用代表性正常、失败、越权、第三方异常和高敏数据样本验证脱敏；扫描无发现不能替代人工抽样和数据流核对。
- 安全事件所需的主体、动作、对象、结果和关联标识可追踪，同时不通过过量记录制造新的泄露面。

## 7. 发现分级与硬阻断

| 级别 | 判定 | 对结果的约束 |
|---|---|---|
| CRITICAL | 可造成大规模或高敏数据泄露、身份接管、任意越权、秘密被主动滥用、不可恢复数据破坏、违法处理或关键供应链失陷 | 属于硬阻断，结果必须为 `BLOCKED` |
| HIGH | 在现实条件下可造成显著未授权访问、敏感数据暴露、权限扩大、关键控制绕过或高影响完整性 / 可用性损害 | 关闭并复审前不得 `APPROVED`；若已触发第 7.1 节场景则为 `BLOCKED`，否则为 `CHANGES_REQUIRED` |
| MEDIUM | 防御纵深、局部数据处理、配置或证据存在实质缺口，但未达到硬阻断条件 | 通常为 `CHANGES_REQUIRED`；仅在控制有效且有权责任人接受剩余风险后才可能 `APPROVED` |
| LOW | 不改变核心安全结论的有限改进项 | 可修复；保留时须有理由、Owner、期限和监控，不得被用来降级更高问题 |

### 7.1 硬阻断场景

出现以下任一情况，安全评审必须为 `BLOCKED`，且不能通过风险接受、功能开关、缩小测试范围或承诺发布后修复绕过：

- 仍然有效或可能被滥用的 API Key、令牌、证书或其他秘密已暴露，尚未完成隔离、吊销、轮换和影响调查。
- 存在可利用的认证绕过、跨用户 / 跨租户越权、管理权限获取、任意工具调用或未受控高权限操作。
- 已发生或候选版本可现实导致高敏用户数据泄露、违法或未经授权处理，且未完成遏制与必要决策。
- 敏感数据存储、迁移、备份或删除存在不可接受的丢失、混淆、暴露或不可恢复风险。
- 关键第三方或供应链来源、完整性、权限或数据处理边界无法建立，或者存在未缓解的可利用关键漏洞。
- 日志、错误、追踪或外部可观测链路持续暴露秘密或高敏用户数据，且无法在候选版本生效前可靠阻断。
- 安全测试证明存在 CRITICAL 风险，或关键安全证据被篡改、候选基线无法唯一确定、评审权限 / 必要访问缺失而无法可信判断安全状态。
- 适用法律、合同、监管或组织红线明确禁止按当前设计、数据用途或部署边界继续。

硬阻断关闭后也不会自动转为 `APPROVED`；必须以新记录和有效基线重新执行评审。

## 8. 唯一评审结果

安全评审最终结果严格限定为以下三种：

| Security Result | 使用条件 | 后续动作 |
|---|---|---|
| `APPROVED` | 六类强制检查均为 PASS 或有效 N/A；CRITICAL / HIGH 未关闭数为 0；硬阻断为 0；证据完整且对应冻结基线；非阻断剩余风险已由有权责任人明确接受 | 可作为 Release Approval Gate 的安全输入；不单独授权阶段转换、部署或发布 |
| `CHANGES_REQUIRED` | 不存在硬阻断，但有可在当前已批准方向和可控范围内修正的控制、测试、证据或非关键风险缺口 | 保持当前阶段，登记 Finding、Owner、修复与完成条件；修订、复测并对新基线重新评审 |
| `BLOCKED` | 存在任一硬阻断；或无法建立可信基线、授权、关键证据或安全处置路径；继续将造成不可接受风险 | 立即停止发布准备，先遏制风险；按问题性质升级决策或退回 DEVELOPMENT、DESIGN、EVALUATION / RESEARCH，再以新基线重审 |

`BLOCKED` 与 `CHANGES_REQUIRED` 不能互换：前者表示当前方向、权限、证据条件或风险状态不允许安全继续；后者表示方向仍有效且缺口有明确、可验证、在范围内的修正路径。不存在第四种结果。

## 9. 评审流程

1. Security Review Owner 核验当前阶段授权，冻结候选源版本、产物、配置、依赖、数据和环境基线。
2. Reviewer 建立威胁、信任边界、数据分类、凭据、权限、第三方、存储和日志清单，核验 N/A。
3. 按第 6 节逐项检查控制，并在冻结基线上执行所需扫描、权限 / 数据 / 失败路径测试和人工抽样。
4. 对每个发现记录严重度、依据、影响、复现、责任人和关闭条件；发现硬阻断时先执行遏制动作。
5. Reviewer 核对修复版本、定向测试与回归，确认旧秘密失效、数据影响受控和副作用关闭。
6. Security Review Owner 复算 CRITICAL / HIGH、未关闭发现和硬阻断数量，只记录三种唯一结果之一。
7. 将结果及证据提供给 Release Approval Gate；安全结果与候选基线不一致时不得沿用。

## 10. 安全评审记录

每次评审保存独立记录；复审创建新 Record ID 并引用上一记录。

### 10.1 基本信息

| 字段 | 必须记录的内容 |
|---|---|
| Security Review Record ID | 唯一、不可复用的标识 |
| 项目与评审范围 | 版本化范围与非范围 |
| 候选基线 | 源版本 / 内容摘要、产物摘要、配置、依赖、Schema / 迁移、目标环境 |
| 评审时间 | 含时区的时间戳 |
| Owner / Reviewer | 姓名或有权限的责任角色 |
| 上一记录 | Record ID 与链接；首次记录为 `NONE` |

### 10.2 逐项与发现记录

## 11. 基线失效与复审

`APPROVED` 只对记录中的精确候选基线和安全环境生效。发生以下任一情况，旧结果立即失去当前性，不能作为发布证据：

- 源内容、构建产物、配置、Feature Flag、依赖、模型、Prompt、工具权限、Schema、迁移或部署定义改变。
- API Key、证书、秘密存储、身份提供方、角色、权限、服务账号或网络 / 信任边界改变。
- 用户数据类别、用途、来源、输出、保留、删除、区域、共享方或日志字段改变。
- 第三方、版本、权限、合同 / 数据处理条件、子处理者、外联目标或退出控制改变。
- 目标环境、存储、备份、日志、监控、错误处理或事件响应控制改变。
- 出现新的安全公告、关键漏洞、泄露迹象、权限异常、数据事件或证据完整性问题，足以改变原结论。
- 证据超过项目规定的有效期，评审人权限失效，或 Release Version Baseline 与安全基线不再完全一致。

修复或变更后必须创建新 Security Review Record ID，引用旧记录，重新冻结基线并复核全部受影响检查及必要回归。若候选内容、依赖、权限、数据流或环境改变，应重新执行六类完整检查；不得只关闭旧 Finding 后沿用旧 `APPROVED`。复审仍只能产生 `APPROVED`、`CHANGES_REQUIRED` 或 `BLOCKED`。

## 12. 与生命周期门禁的关系

- DEVELOPMENT → TESTING 仍只能由 [Development Approval Gate](../development/DEVELOPMENT_APPROVAL_GATE.md) 的有效 `APPROVED_FOR_TESTING` 授权；安全评审不得替代该记录。
- 安全评审可以在 TESTING 中分批收集证据，但 Release Approval Gate 使用的最终 `APPROVED` 必须对应完整、冻结的 Release Version Baseline。
- `CHANGES_REQUIRED` 或 `BLOCKED` 都禁止给出 `READY_FOR_RELEASE`。修复若改变了由 `APPROVED_FOR_TESTING` 冻结的候选基线，项目必须按变更性质回到 DEVELOPMENT 或更早阶段，重新取得 Testing 授权并重跑受影响测试。
- 安全 `APPROVED` 只是 TESTING → RELEASE 的必要条件之一。只有 [Testing Release Gate](../release/TESTING_RELEASE_GATE.md) 在 Release Approval Gate 为 `READY_FOR_RELEASE` 且全部阶段前提有效时，才可将 `PROJECT_STATE` 的 Current Stage 转为 `RELEASE`。
